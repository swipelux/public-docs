---
title: "Automated rules"
description: "Create, inspect, pause, and archive an eligible funds-received rule."
---

Use a rule to move funds automatically after they become available in a selected custodial wallet. Build the rule from current account and destination resources, then keep its status synchronized.

## Before you start

Confirm the current trigger and target resources are eligible for the rule. The trigger must be a custodial wallet, and the target must be the account or destination you intend to use.

If the target is a destination, prepare it through [Recipients and destinations](/integration/recipients) and wait for the state required by the intended movement. If the target is another customer account, read that account before creating the rule.

Follow [API reliability](/integration/api-reliability) for every rule write.

The trigger reacts after funds become available on the watched wallet. It does not select a deposit method or promise when an incoming movement will settle. If an issued bank account settles into that wallet, the rule observes the resulting available funds.

## Choose the trigger and target

| Field | Choice |
| --- | --- |
| `trigger.type` | Use `funds_received` to react when funds become available on `trigger.accountId`. |
| `action.target.type` = `account` | Send to another custodial wallet account identified by an `acc_` ID. |
| `action.target.type` = `destination` | Send to a recipient destination identified by a `dst_` ID. |

Choose one target type. Keep the trigger and target IDs from their current API responses instead of copying display values.

Only one non-archived rule can watch a trigger account. Before creation, list the customer's current rules with [`GET /v3/customers/{customerId}/rules`](/api-reference/rules/get-v3-customers-by-customer-id-rules). This lets your interface offer an update or archive path instead of blindly attempting a duplicate.

## Create the rule

Create the standing instruction with [`POST /v3/customers/{customerId}/rules`](/api-reference/rules/post-v3-customers-by-customer-id-rules):

```json
{
  "trigger": {
    "type": "funds_received",
    "accountId": "${RULE_TRIGGER_ACCOUNT_ID}"
  },
  "action": {
    "type": "transfer",
    "target": {
      "type": "account",
      "id": "${RULE_TARGET_ACCOUNT_ID}"
    }
  },
  "label": "Treasury consolidation"
}
```

Store `data.id` as the rule ID and `data.status` as the current status. Also retain the returned trigger and target so you can show what the rule watches without reconstructing it from local assumptions.

The create response describes the standing instruction, not an individual movement. Keep later transfers and their states separate from the rule resource.

## Inspect the current rule

Read [`GET /v3/customers/{customerId}/rules/{ruleId}`](/api-reference/rules/get-v3-customers-by-customer-id-rules-by-rule-id) before you display, update, or replace a rule. Refetch the current rule before acting because its status may have changed since creation.

Use the returned status to decide whether your interface should offer pause, resume, or no further changes. Keep archived rules readable in your history, but do not treat them as active automation.

Also compare the current trigger and target with what your application expects. If an operator intends to change the movement endpoint, continue to the replacement sequence below.

## Update or archive the rule

Pause the rule or change supported metadata with [`PATCH /v3/customers/{customerId}/rules/{ruleId}`](/api-reference/rules/patch-v3-customers-by-customer-id-rules-by-rule-id):

```json
{
  "status": "paused",
  "label": "Paused while destination changes"
}
```

Read the rule again after the update. Pause temporarily suspends the same rule; it remains non-archived and still occupies the trigger.

To replace a rule on the same trigger, archive the existing rule first with [`DELETE /v3/customers/{customerId}/rules/{ruleId}`](/api-reference/rules/delete-v3-customers-by-customer-id-rules-by-rule-id), then create the replacement. Archiving is terminal, and the archived rule stays readable.

## Next step

Persist the rule ID, show its current trigger, target, and status, include rules in your periodic reconciliation through [Sync and reconciliation](/integration/sync-and-reconciliation), and directly refetch the current rule before an operator changes or acts on it.
