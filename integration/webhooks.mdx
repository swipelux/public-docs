---
title: "Webhooks"
description: "Register an endpoint, process events durably, refetch current state, and recover missed changes."
---

Use webhooks to react quickly to resource changes while keeping the API as your current-state read path. Register endpoints and refetch resources from your backend with `X-API-Key`.

## Register an endpoint

Create one endpoint with [`POST /v3/webhooks`](/api-reference/webhooks/post-v3-webhooks). This example subscribes only to transfer state changes:

```bash
export API_BASE='https://platform.swipelux.com'
export SWIPELUX_API_KEY='replace-with-your-api-key'
export WEBHOOK_CREATE_KEY='webhook-endpoint-2026-08-05'

curl --request POST \
  "${API_BASE}/v3/webhooks" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: ${WEBHOOK_CREATE_KEY}" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "url": "https://example.com/webhooks/swipelux",
  "events": ["transfer.state_changed"]
}
JSON
```

Store response `data.id` as `WEBHOOK_ID` and `data.status` as `WEBHOOK_STATUS`. Use the ID for later endpoint changes and confirm that the status is suitable before relying on delivery. Follow [API reliability](/integration/api-reliability) for the idempotency rule on configuration writes.

## Process an event

The [full webhook catalog](/api-reference) defines every supported payload. This is the exact representative [`transfer.state_changed`](/api-reference/webhooks/transfer-state-changed) envelope:

```json
{
  "id": "evt_abc123",
  "type": "transfer.state_changed",
  "createdAt": "2026-07-04T12:00:00.000Z",
  "attempt": 1,
  "resource": {
    "type": "transfer",
    "id": "tr_abc123"
  },
  "data": {
    "object": {
      "id": "tr_abc123",
      "customerId": "cus_abc123",
      "state": "processing",
      "createdAt": "2026-07-04T12:00:00.000Z",
      "updatedAt": "2026-07-04T12:30:00.000Z"
    },
    "previous": {
      "state": "awaiting_funds"
    }
  }
}
```

Persist the event `id` as the unique key in a durable inbox before you run side effects. If that inbox record is already completed, treat the duplicate delivery as a no-op. If a pending or failed record remains after a crash, resume the incomplete work instead of discarding it.

After the inbox write, process the event and mark the record completed only when its required work has finished. Keep enough local context to retry your own incomplete processing safely.

## Refetch current state

Use `resource.type` and `resource.id` as locators, then make an authenticated read for current state. For the representative transfer event, use `resource.id` as `TRANSFER_ID` and call [`GET /v3/transfers/{transferId}`](/api-reference/money-movement/get-v3-transfers-by-transfer-id):

```bash
curl --request GET \
  "${API_BASE}/v3/transfers/${TRANSFER_ID}" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

Drive customer-visible status and downstream decisions from this response. Use the event projection to locate the resource, not as a replacement for the authenticated current-state read.

## Replay a delivery

Call [`GET /v3/webhooks/portal`](/api-reference/webhooks/get-v3-webhooks-portal) when an operator needs documented delivery logs, retries, or manual replay. The response contains the returned `url`; open it for that operator workflow and keep the webhook ID with your incident record.

When a replay reaches your endpoint, send it through the same durable inbox. Completed event IDs remain deduplicated, while incomplete records resume their work.

## Recover missed changes

Webhook handling is the fast path. Reconciliation is the recovery path when an event is delayed, missed, or cannot be completed. Run the checkpoint-and-cursor workflow in [Sync and reconciliation](/integration/sync-and-reconciliation), then apply each resource's current state through the same local update path.

Next, implement that reconciliation job and test it alongside endpoint replay before you [go live](/integration/production-readiness).
