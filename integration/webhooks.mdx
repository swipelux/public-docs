title: "Webhooks"

Webhooks notify your integration about committed resource changes. Call webhook configuration operations from your backend with `X-API-Key`. Do not expose `X-API-Key` to a browser or client.

## Configure endpoints

- [`POST /v3/webhooks`](/api-reference/webhooks/post-v3-webhooks) creates an endpoint. The request requires a destination `url` and an `events` allowlist.
- [`GET /v3/webhooks`](/api-reference/webhooks/get-v3-webhooks) lists the authenticated merchant's configured endpoints and their current `active` or `archived` status.
- [`PATCH /v3/webhooks/{webhookId}`](/api-reference/webhooks/patch-v3-webhooks-by-webhook-id) updates the destination URL, the event allowlist, or both.
- [`DELETE /v3/webhooks/{webhookId}`](/api-reference/webhooks/delete-v3-webhooks-by-webhook-id) archives the endpoint.

## Generated event contracts

The generated webhook reference defines these 12 payload contracts:

| Event | Generated payload page |
| --- | --- |
| [`customer.created`](/api-reference/webhooks/customer-created) | Customer creation committed |
| [`customer.updated`](/api-reference/webhooks/customer-updated) | Customer facts, metadata, or related-party changes committed |
| [`customer.archived`](/api-reference/webhooks/customer-archived) | Customer archive cascade committed |
| [`capability.created`](/api-reference/webhooks/capability-created) | Capability created |
| [`capability.status_changed`](/api-reference/webhooks/capability-status-changed) | Capability public status changed |
| [`application.status_changed`](/api-reference/webhooks/application-status-changed) | Institution application status changed |
| [`recipient.status_changed`](/api-reference/webhooks/recipient-status-changed) | Recipient status changed |
| [`destination.status_changed`](/api-reference/webhooks/destination-status-changed) | Recipient destination status changed |
| [`account.created`](/api-reference/webhooks/account-created) | Account created |
| [`account.status_changed`](/api-reference/webhooks/account-status-changed) | Account status or default-account state changed |
| [`account.details_changed`](/api-reference/webhooks/account-details-changed) | Issued bank-account routing details changed |
| [`transfer.state_changed`](/api-reference/webhooks/transfer-state-changed) | Transfer public state changed |

For both create (`POST`) and update (`PATCH`) requests, the current open-enum `events` allowlist consists of the 12 generated names above plus `api.deprecation` and `transfer.created`. Names can be added over time, and unknown names are rejected at write time against the current catalog. The generated event reference has no webhook payload page for `api.deprecation` or `transfer.created`; do not infer a payload shape for either name.

## Canonical envelope

Every generated event schema requires `id`, `type`, `createdAt`, `attempt`, `resource`, and `data`. The stable event `id` is the deduplication key. `resource.type` and `resource.id` identify the changed resource. The `attempt` value is always `1` and remains unchanged by delivery retries.

This is the exact generated example for a transfer state change:

```json
{
  "id": "evt_abc123",
  "type": "transfer.state_changed",
  "createdAt": "2026-07-04T12:00:00.000Z",
  "attempt": 1,
  "resource": {
    "type": "transfer",
    "id": "tr_abc123"
  },
  "data": {
    "object": {
      "id": "tr_abc123",
      "customerId": "cus_abc123",
      "state": "processing",
      "createdAt": "2026-07-04T12:00:00.000Z",
      "updatedAt": "2026-07-04T12:30:00.000Z"
    },
    "previous": {
      "state": "awaiting_funds"
    }
  }
}
```

`data.object` is required for every generated event. `data.previous` is also required for [`capability.status_changed`](/api-reference/webhooks/capability-status-changed), [`application.status_changed`](/api-reference/webhooks/application-status-changed), [`recipient.status_changed`](/api-reference/webhooks/recipient-status-changed), [`destination.status_changed`](/api-reference/webhooks/destination-status-changed), [`account.status_changed`](/api-reference/webhooks/account-status-changed), [`account.details_changed`](/api-reference/webhooks/account-details-changed), and [`transfer.state_changed`](/api-reference/webhooks/transfer-state-changed).

## Process events safely

This workflow applies only to the 12 generated event contracts above. `api.deprecation` and `transfer.created` have no generated payload schema, so do not process them with this canonical envelope workflow until a generated contract is published.

Treat `data.object` as a partial or redacted locator and advisory projection, not the authority for current state.

1. Parse the required envelope fields.
2. Persist a `pending` record in a durable inbox keyed by event `id`.
3. Only completed records are no-ops. Stale, failed, or otherwise incomplete records remain resumable; if a crash occurs after pending insertion but before processing, resume the record instead of discarding it.
4. Refetch or reconcile authenticated current state with the event-specific operation below. If the current read cannot be resolved, retain the inbox item for recovery and do not perform destructive downstream actions from the projection alone.
5. For local effects, commit the local effects and `completed` status atomically when possible.
6. For external effects, write a durable outbox or retry record, use idempotent downstream handling, and complete the inbox item only after the durable handoff.

The public contract does not guarantee exactly-once delivery, and this inbox and outbox workflow does not claim it.

## Recover missed changes

`updatedAfter` is an inclusive RFC 3339 lower bound explicitly documented for missed-webhook recovery on the list operations below.

1. Start from your last successful checkpoint with an overlap window chosen by your system.
2. Query the applicable list operations with `updatedAfter`.
3. Follow every cursor page.
4. Deduplicate returned records by resource id and reconcile them with the event matrix above. Use the scoped list result when the contract has no successful direct current read, including customer archives and applications.
5. Advance the checkpoint only after the complete overlap window succeeds.

| Customer related parties | [`GET /v3/customers/{customerId}/related-parties`](/api-reference/customers/get-v3-customers-by-customer-id-related-parties) |

## Replay configuration writes safely

Follow [Request safety](/integration/request-safety). Generate a fresh key for each intended configuration change.

- [`POST /v3/webhooks`](/api-reference/webhooks/post-v3-webhooks) requires `Idempotency-Key`. After transport uncertainty, reuse the same key only with the identical body. On a replay, the documented successful response includes `Idempotency-Replayed: true`.
- [`PATCH /v3/webhooks/{webhookId}`](/api-reference/webhooks/patch-v3-webhooks-by-webhook-id) requires `Idempotency-Key`. After transport uncertainty, reuse the same key only with the identical body. On a replay, the documented successful response includes `Idempotency-Replayed: true`.
- [`DELETE /v3/webhooks/{webhookId}`](/api-reference/webhooks/delete-v3-webhooks-by-webhook-id) requires `Idempotency-Key`. After transport uncertainty, reuse the same key only with the identical request. On a replay, the documented successful response includes `Idempotency-Replayed: true`.

## Contract boundary

The public contract does not define webhook signing, HMAC, signature headers, or verification secrets.

The public contract does not document retry counts, retry timing, or backoff.

The public contract does not guarantee at-least-once or exactly-once delivery.

The public contract does not guarantee event ordering or any other delivery or security guarantee. Do not assume one.
