title: "Quotes and transfers"
description: "Choose an exact amount, execute a quote, and follow the current transfer state."
---

Use a quote to lock the priced movement you intend to execute, then read the resulting transfer for current progress, tasks, and any applicable funding details.

## Check resource compatibility

Before quoting, confirm these resources still match the movement:

- The current capability is `ready`, belongs to the customer, and matches the intended flow.
- For a stablecoin-funded movement, the source is an active `issued` custodial account. Its current status is `ready`, and it supports the input currency.
- For stablecoin movement, the source and destination use the same currency and network.
- A fiat payout destination is current and `ready`, and supports the output currency and method.

## Choose the exact amount

Create a quote with [`POST /v3/quotes`](/api-reference/money-movement/post-v3-quotes). Supply one amount side and both currencies.

Use response-derived IDs for the customer, ready capability, source account when required, and destination. An `acc_` destination identifies a customer account; a `dst_` destination identifies a recipient destination. The selected resources must still be compatible when you execute the quote.

<Tabs>
  <Tab title="Exact in">

For exact in, set `in.amount` and omit `out.amount`. The response calculates the output amount.

```json
{
  "customerId": "${CUSTOMER_ID}",
  "capabilityId": "${STABLECOIN_CAPABILITY_ID}",
  "in": {
    "amount": "1.234567",
    "currency": "USDC",
    "accountId": "${SOURCE_WALLET_ID}"
  },
  "destinationId": "${WALLET_DESTINATION_ID}",
  "out": {
    "currency": "USDC"
  }
}
```

  </Tab>
  <Tab title="Exact out">

For exact out, set `out.amount` and omit `in.amount`. The response calculates the source amount.

```json
{
  "customerId": "${CUSTOMER_ID}",
  "capabilityId": "${CAPABILITY_ID}",
  "in": {
    "currency": "USDC",
    "accountId": "${SOURCE_WALLET_ID}"
  },
  "destinationId": "${RECIPIENT_DESTINATION_ID}",
  "out": {
    "amount": "100.00",
    "currency": "USD"
  }
}
```

  </Tab>
</Tabs>

Store the quote `data.id`, `data.status`, `data.expiresAt`, returned legs, rate, and fees. These response values form the priced snapshot; do not rebuild executable amounts from the rate alone.

Exact in fixes what leaves the source. Exact out fixes what the destination should receive. In either case, use the decimal string returned by the API and avoid floating-point arithmetic in your application.

After a stablecoin-funded exact-out quote returns, call [`GET /v3/customers/{customerId}/accounts/{accountId}`](/api-reference/accounts/get-v3-customers-by-customer-id-accounts-by-account-id). From that response, read the current source account `balances[].available` for the input currency. Compare it with the returned `data.in.amount` before execution. If the available balance is insufficient, fund or change the source. After resources change, create a new quote before executing. Fiat-funded exact-out quotes do not use this source-account balance gate because `in.accountId` is ignored for fiat funding.

## Execute before expiry

Read the latest quote with [`GET /v3/quotes/{quoteId}`](/api-reference/money-movement/get-v3-quotes-by-quote-id). Use `expiresAt` as the execution deadline, and execute only while the current quote status permits it. If the quote is no longer executable, create a new quote from freshly read resources.

Create the transfer with [`POST /v3/transfers`](/api-reference/money-movement/post-v3-transfers):

```json
{
  "quoteId": "${QUOTE_ID}"
}
```

Store the transfer `data.id`. The transfer creation request references the chosen quote; it does not repeat the quote's amounts or destination.

Use [API reliability](/integration/api-reliability) for the quote and transfer writes.

Keep quote and transfer IDs as separate fields. The quote records the priced choice; the transfer records the executed movement and can continue changing after creation.

## Follow the current transfer

Read [`GET /v3/transfers/{transferId}`](/api-reference/money-movement/get-v3-transfers-by-transfer-id) after creation and after each event. Store and evaluate `data.state`, `data.stateDetail`, and `data.openTaskIds` from the latest response.

Treat `state` as the public lifecycle value. Use `stateDetail` only as the current explanation and action signal; do not hard-code a complete reason catalog. An empty `openTaskIds` list means no transfer-scoped task is currently open, not that a non-terminal transfer has finished.

Read the current transfer before making an operator decision. A previously stored state can be useful for history, but it must not override the latest resource.

## Follow transfer tasks

When task IDs are open, fetch [`GET /v3/transfers/{transferId}/tasks`](/api-reference/money-movement/get-v3-transfers-by-transfer-id-tasks). Submit against each task's current `revision` and current `requirements`. Refetch after a submission because either value can change.

Use [Capabilities and requirements](/integration/onboarding/capabilities-and-requirements#complete-requirements) for the shared task completion pattern.

## Use funding details only when returned

For an applicable inbound transfer, fetch [`GET /v3/transfers/{transferId}/instructions`](/api-reference/money-movement/get-v3-transfers-by-transfer-id-instructions). Read the nullable `data.instructions` response and render only the fields returned for its type.

For bank details, when `reference.required` is `true`, present the exact `reference.value`. Keep the returned amount, currency, optional local amount, and expiry attached to the same transfer. Never reuse these values for a different transfer.
