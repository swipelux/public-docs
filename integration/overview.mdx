Swipelux API workflows start with a customer and progress through capabilities, required tasks, destinations, quotes, and transfers. Read each resource instead of assuming what is available.

<Note>
  The supported-capability response lists known variants, including entries whose `availability` is `disabled` or whose customer is ineligible. Select only an entry whose `availability` is `available` or `beta` and whose `eligibility.eligible` is `true`. Known ineligible variants fail when requested.
</Note>

Downstream availability also depends on current resource status. Do not assume that an account shape, destination, or transfer action is available.

## Object map

1. **Customer.** Create the person or business that owns the workflow with [`POST /v3/customers`](/api-reference/customers/post-v3-customers).
2. **Supported capabilities and requested capability.** Read [`GET /v3/customers/{customerId}/capabilities/supported`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-supported), select a requestable entry, then request it with [`POST /v3/customers/{customerId}/capabilities/{capabilityId}`](/api-reference/capabilities/post-v3-customers-by-customer-id-capabilities-by-capability-id). Omitted or empty `institutions` lists select registry defaults. A non-empty list explicitly overrides defaults; use only public institution ids returned by the supported-capability response.
3. **Application, tasks, and submissions.** Follow the capability's application and open tasks. List tasks with [`GET /v3/customers/{customerId}/tasks`](/api-reference/tasks/list-customer-tasks), then answer the current task revision through [`POST /v3/customers/{customerId}/tasks/{taskId}/submissions`](/api-reference/task-submissions/create-customer-task-submission).
4. **Account or recipient destination.** Create a customer-owned account with [`POST /v3/customers/{customerId}/accounts`](/api-reference/accounts/post-v3-customers-by-customer-id-accounts). For a third-party destination, create a recipient with [`POST /v3/customers/{customerId}/recipients`](/api-reference/recipients/post-v3-customers-by-customer-id-recipients), then add its destination with [`POST /v3/customers/{customerId}/recipients/{recipientId}/destinations`](/api-reference/recipients/post-v3-customers-by-customer-id-recipients-by-recipient-id-destinations).
5. **Quote.** Price a movement against a ready capability and destination with [`POST /v3/quotes`](/api-reference/money-movement/post-v3-quotes).
6. **Transfer.** Execute the quote with [`POST /v3/transfers`](/api-reference/money-movement/post-v3-transfers), then read the transfer and its current state with [`GET /v3/transfers/{transferId}`](/api-reference/money-movement/get-v3-transfers-by-transfer-id).

The requested capability can create work before it becomes ready. Applications connect that request to tasks, and submissions provide the answers required by the current task revision. Continue only when the relevant capability and downstream resources report a status that permits the next operation.
