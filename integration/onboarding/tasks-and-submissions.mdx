---
title: "Tasks and submissions"
description: "Resolve capability tasks through current task details, hosted sessions, and immutable submissions."
---

Tasks describe the current work blocking or advancing a customer capability. Read the live task before acting because its revision, requirements, sessions, and status can change.

## Follow capability and application task ids

Read [`GET /v3/customers/{customerId}/capabilities/{capabilityId}`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-by-capability-id). The capability's `openTaskIds` includes open tasks associated with the capability or one of its applications, including shared customer tasks reached through an active dependency.

Read [`GET /v3/customers/{customerId}/capabilities/{capabilityId}/applications`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-by-capability-id-applications). Each application also has `openTaskIds` for that institution flow. The same task id can therefore be visible through both the capability and an application relationship.

Treat these arrays as pointers to current work. Fetch each id through the customer-scoped task detail operation instead of constructing a different task route.

## Fetch the authorized action surface

Use [`GET /v3/customers/{customerId}/tasks`](/api-reference/tasks/list-customer-tasks) to list customer-owned tasks. Its `verificationSessions` and `tosSessions` entries are URL-free summaries. Fetch customer-scoped task detail with [`GET /v3/customers/{customerId}/tasks/{taskId}`](/api-reference/tasks/get-customer-task) to receive the authorized action surface.

In the detail response, `verificationSessions` entries include a `url`, and `tosSessions` entries include a `url`. The current schema describes each as a stable first-party Swipelux action URL over HTTPS. It also includes `expiresAt`; that field is nullable and currently constrained to `null`, so do not infer a lifetime or expiry window.

Your backend must fetch task detail with `X-API-Key`. Return only the task data your client needs, and do not expose `X-API-Key` to a browser or client. The contract does not add other hosted-session security properties.

## Build one current submission

Submit answers with [`POST /v3/customers/{customerId}/tasks/{taskId}/submissions`](/api-reference/task-submissions/create-customer-task-submission). This operation declares `Idempotency-Key` and creates one complete immutable attempt for the current remediation round. The entire JSON request body is limited to 524,288 bytes.

Copy the task's current `revision` into `taskRevision`. Build a complete answer set from the current actionable requirements. Each entry uses its `requirementId`; match the requirement's `request.type` to the corresponding `answer.type`. Include `alternativeKey` only when answering one of a requirement's alternatives.

The contract example shows the envelope and two answer variants:

```json
{
  "taskRevision": 3,
  "answers": [
    {
      "requirementId": "req_01JSOURCE",
      "answer": {
        "type": "profile",
        "value": "Revenue from annual software subscriptions."
      }
    },
    {
      "requirementId": "req_01JIDENTITY",
      "alternativeKey": "passport",
      "answer": {
        "type": "document",
        "documentIds": [
          "doc_01JPASS"
        ]
      }
    }
  ]
}
```

Do not reuse this answer set for another task or revision. Requirement-specific payloads are not universal; derive them from the current task detail. For document answers, upload the files first and use their ids as described in [Documents](/integration/onboarding/documents).

If the response is `task_submission_incomplete`, inspect `missingRequirementIds` and rebuild one complete request. If the response is `task_changed`, use `currentRevision`, `currentStatus`, and `taskUrl` to read the task again; the stale submission is not reusable.

Read redacted submission summaries with [`GET /v3/customers/{customerId}/tasks/{taskId}/submissions`](/api-reference/task-submissions/list-customer-task-submissions). This list omits answer values, alternatives, and document ids.

## Monitor current resources

After every action or status event, refetch the current task, application, and capability. Follow each id in the fresh `openTaskIds` arrays through customer-scoped task detail, act only from the current response, and repeat the loop.

Their vocabularies are separate:

- **Capability status:** `pending`, `ready`, `restricted`, `rejected`, `canceled`
- **Application status:** `requested`, `in_review`, `action_required`, `ready`, `rejected`, `disabled`, `canceled`
- **Task status:** `action_required`, `in_review`, `satisfied`, `rejected`, `canceled`
- **Submission outcome:** `in_review`, `accepted`, `changes_requested`, `rejected`
- **Requirement status:** `action_required`, `in_review`, `accepted`, `rejected`, `canceled`, `superseded`
- **Hosted-session status:** `action_required`, `in_review`, `completed`, `rejected`, `canceled`

- **`ready`:** The capability is usable. You can stop the capability readiness loop for this lifecycle.
- **`pending`:** Continue monitoring current resources. Refetch after every action or status event and follow any fresh `openTaskIds`.
- **`restricted`:** This is not a stop condition. Refetch the current resources and follow every fresh `openTaskIds` entry before using the current `statusReason.resolution`: `complete_tasks` means complete the current tasks from their current details; `wait` means continue monitoring; `contact_support` means contact support with the current `code` and `message`; `none` means no resolution action is specified, so do not invent one.
- **`rejected` and `canceled`:** Stop the current lifecycle.

Every `pending`, `restricted`, `rejected`, or `canceled` capability response requires `statusReason`; `ready` omits it. Requesting a canceled capability with a new idempotency key starts a fresh lifecycle after current eligibility and routing checks pass.

- **Application lifecycle:** Only `ready` means the application is usable. Continue following current resources for `requested`, `in_review`, and `action_required`. `rejected`, `disabled`, and `canceled` stop the current application lifecycle. Do not classify `canceled` or `disabled` as waiting or action states.
- **Application `statusReason`:** `statusReason` is a required field whose value is nullable. When non-null, it contains `code`, `message`, `actor`, and `retryable`; `actor` is `customer`, `developer`, `provider`, `network`, or `swipelux`. An `in_review` application always has a stored or synthesized reason, while self-explanatory statuses may return `null`.
- **Task lifecycle:** Act only on the current `action_required` detail, treat `in_review` as the current review state, and stop acting on that task when its current status is `satisfied`, `rejected`, or `canceled`.

These fields describe the current response. Do not assume the next status or an undocumented transition.
