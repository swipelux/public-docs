---
title: "Onboard businesses"
description: "Create a business customer, manage related parties, and request eligible capabilities."
---

Business onboarding uses the same customer and capability resources as individual onboarding. The business shape and related-party resources carry the additional entity, ownership, voting, and control facts required by current tasks.

## Create the business customer

Create the customer with [`POST /v3/customers`](/api-reference/customers/post-v3-customers). This operation declares `Idempotency-Key`; scope the key to this intended customer creation and preserve the body when replaying the same request after transport uncertainty.

The minimal business body requires `type` and `business.legalName`:

```json
{
  "type": "business",
  "business": {
    "legalName": "Acme Payments SAS"
  }
}
```

Store `data.id` from the response as the customer id. Read the current customer with [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id) before using its business or embedded active-related-party data.

## Create and maintain related parties

Create a related party with [`POST /v3/customers/{customerId}/related-parties`](/api-reference/customers/post-v3-customers-by-customer-id-related-parties). This operation declares `Idempotency-Key` and returns a stable `rp_` id.

`partyType` selects `person` or `entity`. Each request carries `roles` plus the matching `person` or `entity` object. Supply at least one role or one ownership, voting, or control fact. An entity party also requires `entity.legalName`.

```json
{
  "partyType": "person",
  "roles": [
    "director"
  ],
  "title": "Chief executive officer",
  "person": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
```

Use [`GET /v3/customers/{customerId}/related-parties`](/api-reference/customers/get-v3-customers-by-customer-id-related-parties) to list active summaries. Read the current related-party resource before you update it. Fetch it with [`GET /v3/customers/{customerId}/related-parties/{relatedPartyId}`](/api-reference/customers/get-v3-customers-by-customer-id-related-parties-by-related-party-id).

Update supplied fields with [`PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}`](/api-reference/customers/patch-v3-customers-by-customer-id-related-parties-by-related-party-id). This operation declares `Idempotency-Key`. Omitted fields stay unchanged, explicit `null` clears optional fields, and arrays are replaced whole. The related-party id, customer id, and `partyType` are immutable.

Archive a related party with [`DELETE /v3/customers/{customerId}/related-parties/{relatedPartyId}`](/api-reference/customers/delete-v3-customers-by-customer-id-related-parties-by-related-party-id). This operation declares `Idempotency-Key` and has no request body. Reuse the same `Idempotency-Key` only to replay the same archive request after transport uncertainty; use a new key for a different intended archival.

Archives the related party: the id is never reused, normal reads return 404 afterwards, and an idempotent replay returns the same 204. Deletion is blocked with 409 related_party_in_review while an active review depends on the party.

After archival, the read and update operations treat the archived id as not found and return 404 `related_party_not_found`.

Related-party requirements are conditional. A task can request a related-party resource reference with specific roles, so use the current task rather than assuming every business needs the same party set.

## Discover and request a capability

Read [`GET /v3/customers/{customerId}/capabilities/supported`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-supported). The response lists known variants, including `disabled` variants and variants for which the customer is ineligible.

Select a variant only when `availability` is `available` or `beta` and `eligibility.eligible` is `true`. A known ineligible variant fails when requested.

For bank-backed capabilities, omitted or empty `institutions` lists select registry defaults. A non-empty list explicitly overrides defaults; use only public institution ids returned by this response.

The optional task preview is [`GET /v3/customers/{customerId}/capabilities/{capabilityId}/tasks-preview`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-by-capability-id-tasks-preview). It returns descriptor-only tasks from a pinned, side-effect-free evaluation snapshot. The preview does not replace an actual current task created by the capability lifecycle.

Request the capability with [`POST /v3/customers/{customerId}/capabilities/{capabilityId}`](/api-reference/capabilities/post-v3-customers-by-customer-id-capabilities-by-capability-id). This operation declares `Idempotency-Key`. The body can be empty to use defaults or contain a non-empty `institutions` override.

```json
{}
```

Known ineligible variants fail instead of falling back. Read the current result with [`GET /v3/customers/{customerId}/capabilities/{capabilityId}`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-by-capability-id), then follow its `openTaskIds` and application data through [Tasks and submissions](/integration/onboarding/tasks-and-submissions).

Keep `X-API-Key` in your backend. Do not expose it to a browser or client while collecting business or related-party information.
