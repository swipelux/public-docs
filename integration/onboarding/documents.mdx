---
title: "Customer documents"
description: "Upload customer-scoped documents and reference their metadata in current task submissions."
---

Upload a document only when the current task requires one. The task's document requirement can narrow accepted document types, counts, and formats beyond the upload endpoint's file boundary.

## Upload raw file bytes

Use [`POST /v3/customers/{customerId}/documents`](/api-reference/documents/post-v3-customers-by-customer-id-documents). This operation declares `Idempotency-Key` and accepts one file up to 25 MB as `multipart/form-data`.

The accepted file formats are PDF, JPEG, PNG, WebP, and HEIF/HEIC. Send raw binary bytes in the required `file` part; base64 JSON is not accepted. The API multipart schema also permits an optional `type` field. The example intentionally omits the API `type` field. In curl, `;type=application/pdf` sets the MIME type of the `file` part; it does not send the API `type` field. The contract names accepted file formats but does not publish a closed MIME-type enum.

Run uploads from your backend so `X-API-Key` remains server-side:

```bash
export API_BASE='https://platform.swipelux.com'
export CUSTOMER_ID='cus_example123'
export SWIPELUX_API_KEY='YOUR_API_KEY'
export RUN_ID="${RUN_ID:-run-${PPID}-$$-${RANDOM}}"
export IDEMPOTENCY_KEY="customer-document-${RUN_ID}"

curl --request POST \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}/documents" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: ${IDEMPOTENCY_KEY}" \
  --form "file=@./document.pdf;type=application/pdf"
```

Create the key once for one intended upload. In the same shell, keep the same `RUN_ID` when you replay that upload; rerunning the block derives the same `Idempotency-Key`. Change `RUN_ID` before a different intended upload, and the block rotates to a new key even if `IDEMPOTENCY_KEY` was already set. If transport uncertainty leaves the result unknown, retry the same intended upload with the same `Idempotency-Key` and the same multipart body, including the same file bytes and `;type=application/pdf` file-part MIME suffix.

Do not expose `X-API-Key` to a browser or client. Capture `data.id` from the upload response and place that id in the task answer's `documentIds` array. A document answer uses `type: document`; the current task determines how many documents and which document types satisfy the requirement.

## Read current metadata

Use [`GET /v3/customers/{customerId}/documents`](/api-reference/documents/get-v3-customers-by-customer-id-documents) to list customer document metadata. Use [`GET /v3/customers/{customerId}/documents/{documentId}`](/api-reference/documents/get-v3-customers-by-customer-id-documents-by-document-id) to read one current metadata record.

Both reads return metadata rather than a download or file bytes. The metadata includes `id`, `type`, `fileName`, `contentType`, `sizeBytes`, `status`, `archivedAt`, `createdAt`, and `updatedAt`. Ordinary document reads and lists return `Document`; its `archivedAt` is always `null` because archived documents are excluded.

- **Document status:** `uploaded`

## Archive a document

Archive current document metadata with [`DELETE /v3/customers/{customerId}/documents/{documentId}`](/api-reference/documents/delete-v3-customers-by-customer-id-documents-by-document-id). This operation declares `Idempotency-Key` and has no request body. Reuse the same `Idempotency-Key` only to replay the exact same archive request after transport uncertainty; use a new `Idempotency-Key` for a different intended archival.

Archives one customer document. Archived documents are retained for compliance but excluded from subsequent reads, lists, and task submissions.

The DELETE response uses `ArchivedDocument`: `status` is `archived`, and `archivedAt` is set exactly once.

- **Archived document status:** `archived`

Re-read the current task before submitting document ids. Do not reuse a document answer from another task or revision, and do not assume an uploaded document satisfies every document requirement.
