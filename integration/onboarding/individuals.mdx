---
title: "Onboard individuals"
description: "Create an individual customer, discover eligible capabilities, and follow current onboarding tasks."
---

Individual onboarding starts with the customer union and then follows the capabilities and tasks returned for that customer. Keep your API key in your backend and derive each next action from the current resource.

## Create the customer

Create the customer with [`POST /v3/customers`](/api-reference/customers/post-v3-customers). This operation declares `Idempotency-Key`; use one key for this intended customer creation and keep the same body if you replay that request after transport uncertainty.

The contract's minimal individual body requires only `type`:

```json
{
  "type": "individual"
}
```

You can also send fields from the `individual`, `financialProfile`, `externalId`, and `metadata` shapes. Those fields are progressive, not a universal onboarding payload. Store `data.id` from the response as the customer id.

Read the current customer with [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id) before making later decisions from customer data.

## Discover a requestable capability

Read [`GET /v3/customers/{customerId}/capabilities/supported`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-supported). The response lists known variants, including `disabled` variants and variants for which the customer is ineligible.

Select a variant only when `availability` is `available` or `beta` and `eligibility.eligible` is `true`. A known ineligible variant fails when requested.

For bank-backed capabilities, omitted or empty `institutions` lists select registry defaults. A non-empty list explicitly overrides defaults; use only public institution ids returned by the supported-capability response.

## Preview possible work when useful

The optional task preview is [`GET /v3/customers/{customerId}/capabilities/{capabilityId}/tasks-preview`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-by-capability-id-tasks-preview). It returns descriptor-only tasks from a pinned, side-effect-free evaluation snapshot.

A preview does not create or replace an actual current task. Use it for planning, then rely on resources returned after the capability request.

## Request and read the capability

Request the selected capability with [`POST /v3/customers/{customerId}/capabilities/{capabilityId}`](/api-reference/capabilities/post-v3-customers-by-customer-id-capabilities-by-capability-id). This operation declares `Idempotency-Key`. The JSON body is required, but it has no universally required property; an empty object uses applicable registry defaults.

```json
{}
```

Known ineligible variants fail instead of falling back. A successful request can still return work in `openTaskIds` before the capability is usable.

Read the current capability with [`GET /v3/customers/{customerId}/capabilities/{capabilityId}`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-by-capability-id). If it reports open tasks, continue with [Tasks and submissions](/integration/onboarding/tasks-and-submissions). Upload files only when a current task asks for them; see [Documents](/integration/onboarding/documents).

The next action is conditional on the current customer, capability, application, and task resources. Do not copy a payload or assume readiness from an earlier response.
