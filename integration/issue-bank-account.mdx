## Before you start

You need a customer ID, a ready bank capability for the intended method and currency, and a ready issued wallet owned by the same customer. With `allowPending`, you can save the request while the selected bank still reviews the customer. Complete open work through [Capabilities and tasks](/integration/onboarding/capabilities-and-requirements).

## 1. Create or select the settlement wallet

Create an issued wallet through [Accounts and wallets](/integration/accounts#create-the-account), then read it again. Continue only when its current status permits settlement.

Store its response-derived `data.id` as `SETTLEMENT_WALLET_ID`. Do not use an external wallet for `settlement.accountId`.

## 2. Create the issued bank account

Use [`POST /v3/customers/{customerId}/accounts`](/api-reference/accounts/post-v3-customers-by-customer-id-accounts) with these headers:

```http Request headers
X-API-Key: ${SWIPELUX_API_KEY}
Idempotency-Key: issued-bank-account-001
Content-Type: application/json
```

Send this request body:

```json Request body
{
  "origin": "issued",
  "type": "bank",
  "method": "ach",
  "country": "US",
  "currency": "USD",
  "settlement": {
    "accountId": "${SETTLEMENT_WALLET_ID}"
  },
  "label": "USD account"
}
```

Store the returned `data.id` as `BANK_ACCOUNT_ID`. Also retain `data.status`, `data.openTaskIds`, `data.details`, and the settlement relationship.

Optional request fields:

| Field | Applies to | Behavior |
| --- | --- | --- |
| `institution` | Issued `ach`, `wire`, and `swift` | Selects exactly this bank. Swipelux does not fall back to another bank. Use an institution ID returned by the supported-capability response. For a non-USD SWIFT account, send the `institution` listed for that currency. See [Choose the currency and bank](#choose-the-currency-and-bank). |
| `allowPending` | Issued `ach`, `wire`, and `swift` | Set to `true` to save the request while the selected bank's application waits for approval. Requires `institution`. |
| `settlement.currency` | Issued bank accounts | `USDC` or `USDT`. Sets the stablecoin delivered to the settlement wallet. |

### Choose the bank

Send `institution` when the customer needs bank details from a specific bank. Swipelux reserves one issued account per customer, method, currency, and institution. A request without `institution` returns `409 conflict` if the customer already has an issued account for that method and currency at any bank. A request with `institution` returns `409 conflict` only if an account for that bank already exists.

Account reads return the selected bank as `institution` with `id`, `name`, and `bic`. `bic` can be `null`.

Idempotency applies to the selected bank. Replaying the same request returns the original account. Changing `institution` under the same `Idempotency-Key` returns `409 idempotency_conflict`.

### Choose the currency and bank

Each issued account receives one currency. Issued ACH and wire accounts receive USD only. Issued SWIFT accounts receive USD, and some banks also issue SWIFT accounts in other currencies.

To find the currencies a bank issues, read `institutions[].currencies` in the [supported-capability response](/integration/onboarding/capabilities-and-requirements#discover-supported-capabilities). Each entry pairs a currency `code` with the `institution` to send when you open the account. That `institution` can differ from the bank that holds the customer's capability.

For example, Lead Bank (`lead_bank`) issues SWIFT accounts in USD only. When multi-currency SWIFT is enabled for your merchant account, the `swift_named` entry for `lead_bank` also lists AUD, CAD, CHF, CZK, DKK, EUR, GBP, HKD, HUF, JPY, MXN, NOK, NZD, PLN, SEK, SGD, and ZAR with `institution: "bmo"`. BMO Bank N.A. (`bmo`, BIC `HATRUS44`) is the bank reported on those accounts. They use the customer's `swift_named` capability at `lead_bank`, so you don't request a separate capability for `bmo`.

To open a non-USD SWIFT account, send the listed `institution` with the currency:

```json Request body for a EUR SWIFT account
{
  "origin": "issued",
  "type": "bank",
  "method": "swift",
  "country": "US",
  "currency": "EUR",
  "institution": "bmo",
  "settlement": {
    "accountId": "${SETTLEMENT_WALLET_ID}"
  },
  "label": "EUR SWIFT account"
}
```

Account reads return `institution.id: "bmo"` and `institution.bic: "HATRUS44"` for these accounts. Each currency is a separate account, so open one request per currency.

These requests return `400 validation_error`:

- An ACH or wire request in a currency other than USD.
- A SWIFT request with `institution: "lead_bank"` and a currency other than USD. The error message names `bmo` as the institution to send.
- A request with `institution: "bmo"` and USD, or with a method other than `swift`.
- A SWIFT request in a currency that no bank issues for your merchant account.

When the customer's ready banks can't issue the requested currency, the request returns `409 capability_not_ready` with `reason: "no_issuable_route"`. This also applies in the sandbox. Waiting does not change the result, so choose a currency and institution from the supported-capability response instead of retrying.

### Save the request before bank approval

By default, Swipelux accepts an issued bank account request only after the bank capability is ready. To collect the customer's account setup earlier, send `allowPending: true` with `institution`:

```json Request body with allowPending
{
  "origin": "issued",
  "type": "bank",
  "method": "wire",
  "country": "US",
  "currency": "USD",
  "institution": "${INSTITUTION_ID}",
  "allowPending": true,
  "settlement": {
    "accountId": "${SETTLEMENT_WALLET_ID}"
  },
  "label": "USD wire account"
}
```

While the bank's application is under review, the account returns `status: "in_review"` with `statusReason.code` set to `waiting_for_approval`. The response also includes `applicationId` and the application's `openTaskIds`. Complete those tasks through [Capabilities and tasks](/integration/onboarding/capabilities-and-requirements).

The saved request keeps its account ID, settlement wallet, and account slot. After the application and capability are ready, Swipelux provisions bank details under the same `BANK_ACCOUNT_ID`. Keep reading that ID. Do not create another request.

While the saved request waits, it holds the account slot. Another `allowPending` request for the same slot under a different `Idempotency-Key` returns `409 conflict`. The problem's `holder.accountId` names the waiting account. Read that account instead of retrying.

If the application is rejected, canceled, or archived first, the account becomes `rejected`. It no longer holds the account slot.

### Choose the settlement currency

By default, deposits settle in the settlement wallet's currency. Set `settlement.currency` to `USDC` or `USDT` to choose the delivered asset independently of the wallet's currency:

```json Request body with settlement currency
{
  "settlement": {
    "accountId": "${SETTLEMENT_WALLET_ID}",
    "currency": "USDT"
  }
}
```

`USDT` requires a `USD` account and a settlement wallet on a network that supports USDT delivery. Otherwise the request returns `400 invalid_settlement_target`. Account reads return the saved choice, including while the account is provisioning.

The bank account ID and wallet ID have different roles. Read provisioning and bank details through the bank account ID. Use the settlement wallet ID to identify where deposits are credited.

## 3. Monitor provisioning

Read [`GET /v3/customers/{customerId}/accounts/{accountId}`](/api-reference/accounts/get-v3-customers-by-customer-id-accounts-by-account-id) after creation and after each relevant webhook.

Keep the customer interface pending while `details` is absent. If `openTaskIds` is not empty, complete the latest tasks and refetch the account. Do not infer readiness from elapsed time.

If the account was saved with `allowPending: true`, it stays `in_review` with `statusReason.code` set to `waiting_for_approval` until the bank approves the application.

If the latest `statusReason.code` is `awaiting_assignment`, create the first pay-in for the same customer, capability, and settlement wallet through [Receive funds](/integration/receive-funds), then read the bank account again. Follow this branch only when the current account requests it.

## 4. Present bank details safely

Display only the complete details returned by the latest account read. When `details.referenceRequired` is true, show the exact `details.reference` and make it copyable. When it is false, do not invent a reference.

For issued `swift` accounts, display `details.bankName`, `details.swiftCode` (the receiving bank's BIC), `details.accountNumber`, `details.accountHolderName`, and `details.accountHolderAddress` when returned. Senders must copy the beneficiary address exactly into the international wire. Also show `details.bankAddress` and any intermediary bank fields that the account returns.

These bank details are reusable. Do not replace them with funding coordinates from a quoted pay-in, which belong only to that transfer.

Next, add [Webhooks](/integration/webhooks) so provisioning updates reach your application without keeping the customer on a polling screen.
