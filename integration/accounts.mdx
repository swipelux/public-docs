Use accounts for endpoints the customer owns. Choose the account family from the movement you are building, create one representative resource, and wait for its current state to permit the next operation.

## Choose an account

| Account | Use it when |
| --- | --- |
| Issued wallet | You need a custodial stablecoin balance, a transfer source or destination, or the settlement wallet for an issued bank account. |
| Issued bank | You need reusable bank details that settle incoming fiat into an issued wallet after provisioning. |
| External wallet | You need to record a customer-owned blockchain address as a movement destination. |
| External bank | You need a customer-owned bank account as a first-party payout destination. |

The available currencies, networks, methods, and account families depend on the customer's current capabilities. Do not infer support from another customer or an earlier response.

## Create the account

Send the selected body to [`POST /v3/customers/{customerId}/accounts`](/api-reference/accounts/post-v3-customers-by-customer-id-accounts). These examples cover the four account families without reproducing every API Reference variant.

For an issued bank account, set `settlement.accountId` from the issued wallet's response-derived `data.id`. That wallet must be ready for the settlement role before you create the bank account.

## Use the current state

Store `data.id`, `data.status`, and `data.openTaskIds` from each create response. Then read the resource with [`GET /v3/customers/{customerId}/accounts/{accountId}`](/api-reference/accounts/get-v3-customers-by-customer-id-accounts-by-account-id) before you quote a movement, show bank details, or update the account.

Use an account only when its current `data.status` is `ready`, unless the next operation explicitly allows another state. Treat `statusReason` as an action signal: use its current `message` and `retryable` value to decide whether to wait, change data, or complete a task. Keep following current task IDs through [Capabilities and requirements](/integration/onboarding/capabilities-and-requirements#complete-requirements); do not build a local reason-code catalog.

An issued bank account's `data.details` may be `null` while it is provisioning. Present details only after a current read returns them. If `details.referenceRequired` is `true`, show the exact `details.reference` with the bank coordinates.

## Change an account only when needed

The developer fee rule affects later pay-ins. Read the current rule with [`GET /v3/customers/{customerId}/accounts/{accountId}/fees`](/api-reference/accounts/get-v3-customers-by-customer-id-accounts-by-account-id-fees), then replace it with [`PUT /v3/customers/{customerId}/accounts/{accountId}/fees`](/api-reference/accounts/put-v3-customers-by-customer-id-accounts-by-account-id-fees):

```json
{
  "breakdown": {
    "developer": {
      "fixed": "1.00",
      "bips": 50
    }
  }
}
```

Use [`PATCH /v3/customers/{customerId}/accounts/{accountId}`](/api-reference/accounts/patch-v3-customers-by-customer-id-accounts-by-account-id) only to change supported metadata, the default issued wallet, or an issued bank account's settlement wallet. Refetch after the update. Use [`DELETE /v3/customers/{customerId}/accounts/{accountId}`](/api-reference/accounts/delete-v3-customers-by-customer-id-accounts-by-account-id) to archive an unused account; finish in-flight transfers first.

Apply one idempotency key per intended write by following [API reliability](/integration/api-reliability).
