---
title: "Errors"
description: "Handle the shared Problem response, field errors, retry guidance, and correlation ids."
---

API failures use a shared `Problem` shape. Every Problem requires:

- `type`: documentation URI for the stable problem code
- `title`: short human-readable title
- `status`: HTTP status code
- `code`: stable machine-readable code
- `detail`: actionable detail
- `correlationId`: request correlation id

`correlationId` mirrors `X-Request-Id`. Keep it when you investigate a request or contact support.

## Optional diagnostic fields

- `errors` contains field-level entries with `pointer`, `code`, and `message`.
- `retryable` may indicate whether retrying the same request may succeed.
- `statusReason` may describe a state conflict when an operation depends on the resource's current status.

Use HTTP `status`, stable `code`, and `retryable` together. Do not decide from the human-readable message alone.

## Example shape

The values below are placeholders; the field structure follows the shared contract.

```json
{
  "type": "https://example.com/problems/example_problem",
  "title": "Example problem",
  "status": 400,
  "code": "example_problem",
  "detail": "Replace this text with the returned detail.",
  "correlationId": "req_example123",
  "retryable": false,
  "errors": [
    {
      "pointer": "/exampleField",
      "code": "example_field_error",
      "message": "Replace this text with the returned field message."
    }
  ]
}
```

Log `correlationId`, `status`, `code`, and the operation name. Do not log API keys, secrets, full request bodies, or PII.
