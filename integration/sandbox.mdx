---
title: "Sandbox"
description: "Use the six documented sandbox helpers to simulate supported states without moving real funds."
---

Sandbox and production use the same API host, `https://platform.swipelux.com`. The API key selects the environment. No real funds move.

Call sandbox helpers from your backend with `X-API-Key`. Do not expose `X-API-Key` to a browser or client. Do not assume automatic sequencing or production equivalence; call only the helper needed for the state you are testing and read the returned resource.

## Sandbox operations

- [`POST /v3/sandbox/accounts/{accountId}/topup`](/api-reference/sandbox/post-v3-sandbox-accounts-by-account-id-topup) credits an issued sandbox wallet account. The request requires `amount` and `currency`. The response returns a transfer with `data.type` set to `wallet_to_wallet` and `data.state` set to `completed`.
- [`POST /v3/sandbox/transfers/{transferId}/state`](/api-reference/sandbox/post-v3-sandbox-transfers-by-transfer-id-state) requires `state`. The optional `stateDetail` requires `code` and may include `message`; it applies only when forcing a payin transfer to `failed` and is ignored for completed states and payout transfers. The response returns the current transfer.
- [`POST /v3/sandbox/tasks`](/api-reference/sandbox/post-v3-sandbox-tasks) requires `scope` and at least one `items` entry. Each item requires `type` and `request`. A customer scope requires `type` and `customerId`; a capability scope requires `type`, `customerId`, and `capabilityId`; a transfer scope requires `type`, `customerId`, and `transferId`. If supplied, `subject` requires `type`, `name`, and `relatedPartyId`, which may be null. If supplied, `deadline` requires `type` and `outcome`. The response returns the created task.
- [`POST /v3/sandbox/tasks/{taskId}/review`](/api-reference/sandbox/post-v3-sandbox-tasks-by-task-id-review) requires `outcome`. Optional `items` entries require `key` and `verdict`; a supplied `rejection` requires `code` and `message`. The response returns the reviewed task.
- [`POST /v3/sandbox/customers/{customerId}/verification`](/api-reference/sandbox/post-v3-sandbox-customers-by-customer-id-verification) requires `status` and accepts an optional `reason`. The response `data` contains `customerId`, `customerType`, `status`, `previousStatus`, and `reason`.
- [`POST /v3/sandbox/customers/{customerId}/capabilities/{capabilityId}/status`](/api-reference/sandbox/post-v3-sandbox-customers-by-customer-id-capabilities-by-capability-id-status) requires `status`. The response returns the current capability.

## Request vocabularies

- **Transfer target states:** `completed`, `failed`
- **Task scope types:** `customer`, `capability`, `transfer`
- **Task categories:** `intake`, `information_request`, `correction_required`, `verification`, `terms_of_service`, `periodic_review`, `transaction_rfi`, `issue_resolution`, `other`
- **Task subject types:** `person`, `entity`
- **Task item types:** `document`, `profile`, `questionnaire`, `explanation`, `attestation`
- **Deadline types:** `reminder`, `final_notice`, `auto_reject`, `provider_sla`
- **Deadline outcomes:** `auto_rejected`, `none`
- **Review outcomes:** `accepted`, `rejected`
- **Review item verdicts:** `accepted`, `rejected`
- **Verification decisions:** `approved`, `rejected`
- **Capability target statuses:** `ready`, `rejected`, `restricted`

## Request safety

None of these six operations declare `Idempotency-Key`. None of their responses document `Idempotency-Replayed`. Do not add either behavior to sandbox requests unless the generated operation page changes.

Use [Environments](/integration/environments) for environment selection and [Request safety](/integration/request-safety) for operation-specific header rules.
