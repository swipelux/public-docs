---
title: "Clienti"
description: "Crea il cliente Swipelux individuale o business che possiede capability, wallet, conti e transfer e collega il profilo di onboarding KYC o KYB corretto."
---

Crea il cliente prima di costruire un pay-in, un payout o un conto bancario emesso. Capability, conti e transfer hanno come scope quel cliente. Usa `externalId` come mapping stabile verso il record corrispondente nel tuo sistema.

```bash
export API_BASE='https://platform.swipelux.com'
export SWIPELUX_API_KEY='replace-with-your-api-key'
```

## Clienti individuali {#individual-customers}

Un individuo richiede solo `type`. Includi i campi del profilo che gia' conosci e aggiungine altri solo quando la capability o il task corrente ne ha bisogno.

Crea il cliente con [`POST /v3/customers`](/api-reference/customers/post-v3-customers):

```bash
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-user-123" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "individual",
  "externalId": "user_123",
  "individual": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Salva il `data.id` restituito come `CUSTOMER_ID`. Consulta [Onboarding individuale](/it/knowledge-base/individual-onboarding/overview) per il contesto di policy.

## Clienti business {#business-customers}

Un business richiede `business.legalName`. Crea il business con la stessa operazione:

```bash
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-company-456" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "business",
  "externalId": "company_456",
  "business": {
    "legalName": "Acme Payments SAS"
  }
}
JSON
```

Salva il `data.id` restituito come `CUSTOMER_ID`. Consulta [Onboarding business](/it/knowledge-base/business-onboarding/overview) per il contesto di policy e documenti.

## Aggiungi related party del business

Aggiungi director, owner e altri partecipanti aziendali quando sono noti o richiesti. Questo esempio crea un director con [`POST /v3/customers/{customerId}/related-parties`](/api-reference/customers/post-v3-customers-by-customer-id-related-parties):

```bash
curl --request POST \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}/related-parties" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: related-party-director-001" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "partyType": "person",
  "roles": ["director"],
  "title": "Chief executive officer",
  "person": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Salva il `data.id` restituito come `RELATED_PARTY_ID`.

Se devi esportare un cliente, usa [`POST /v3/customers/{customerId}/export`](/api-reference/customers/post-v3-customers-by-customer-id-export) e segui lo schema della richiesta.

## Leggi la readiness dalle capability

Un cliente non ha uno stato di verifica o di readiness nell'API. Leggi il cliente con [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id) per ottenere i dati di profilo correnti, quindi usa le capability e i loro `openTaskIds` per decidere cosa il cliente puo' fare successivamente.

```bash
curl --request GET \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

Successivamente, prosegui su [Capability e task](/it/integration/onboarding/capabilities-and-requirements) per scoprire e attivare il risultato di prodotto di cui hai bisogno.
