## अपने production space को सक्रिय करें {#activate-your-production-space}

1. Swipelux Dashboard में sign in करें और **Create a production space** चुनें।
2. KYB tab खोलें या [Business verification](https://www.swipelux.app/kyb) पर जाएँ।
3. प्रत्येक अनुरोधित field पूरा करें और आवश्यक documents upload करें।
4. Verification के लिए अपना integrating business submit करें और approval की प्रतीक्षा करें।

केवल आपके integrating business का KYB approve होने के बाद ही आप production API customers और transactions बना सकते हैं।

KYB की आवश्यकता वाले live space में, Swipelux approval तक business verification और webhook management के बाहर के हर write request के लिए `422` [`merchant_kyb_not_approved`](/integration/errors#merchant-kyb-not-approved) लौटाता है। इसमें customers, capabilities, accounts, recipients, rules, quotes और transfers शामिल हैं।

Approval की प्रतीक्षा करते समय, आप अब भी ये कर सकते हैं:

- `GET` और `HEAD` requests भेजें।
- अपना business verification पूरा करें (आपके business के KYB customer के लिए profile, related parties, documents और task submissions)।
- API के माध्यम से webhook endpoints manage करें, और Dashboard में secret keys, spaces और rail fees manage करें।

Approval तक settings पर limits लागू रहती हैं:

- आप KYB की आवश्यकता वाले अपने live spaces के सभी endpoints में कुल मिलाकर प्रति घंटे 20 webhook URL बदलाव कर सकते हैं। Sandbox spaces में किए गए बदलाव नहीं गिने जाते। Webhook URL limit पार करने पर `POST /v3/webhooks` या `PATCH /v3/webhooks/{webhookId}` से `422 merchant_kyb_not_approved` लौटाया जाता है।
- Dashboard में, KYB की आवश्यकता वाले प्रति live space आपके पास अधिकतम 10 active API keys हो सकती हैं।
- Dashboard में, जब आपके पास कम से कम एक live space हो, आपके सभी live spaces को KYB की आवश्यकता हो और कोई भी approve न हुआ हो, तब आपके पास प्रति merchant अधिकतम 5 spaces हो सकते हैं। इसमें sandbox और live दोनों spaces गिने जाते हैं। यदि किसी live space को KYB की आवश्यकता नहीं है, तो यह space limit लागू नहीं होती।

Dashboard key या space limit पार करने वाले requests को `merchant_kyb_not_approved` code के बिना, एक सामान्य `422` response के साथ अस्वीकार करता है। किसी endpoint के केवल events बदलना, या उसका मौजूदा URL save करना, URL बदलाव नहीं माना जाता। Revoked API keys key limit में नहीं गिनी जातीं।

Sandbox spaces write block, webhook URL limit और key limit से मुक्त हैं, इसलिए आप वहाँ build और test करना जारी रख सकते हैं। फिर भी वे merchant की space limit में गिने जाते हैं।

## Production को स्वतंत्र रखें

Production resources को स्पष्ट रूप से बनाएँ। API key बदलने से sandbox state migrate नहीं होती।

- Production credentials को एक अलग secret-manager entry में संग्रहीत करें।
- Production-only deployment configuration और resource IDs का उपयोग करें।
- एक अलग production webhook endpoint और signing secret register करें।
- Production में आवश्यक customers, capabilities, accounts, recipients, और destinations फिर से बनाएँ।
- Production पहुँच को उन services और operators तक सीमित करें जिन्हें इसकी आवश्यकता है।

Sandbox और production `https://platform.swipelux.com` का उपयोग करते हैं; API key environment का चयन करती है।

## Launch checklist पूरी करें

- [ ] Sandbox में happy path और expected failure paths का परीक्षण करें।
- [ ] प्रत्येक write के साथ एक `Idempotency-Key` भेजें जिसे इसकी आवश्यकता है और सुरक्षित retries के लिए इसे बनाए रखें।
- [ ] Parsing से पहले webhook signatures verify करें, event IDs को durably persist करें, और replay का परीक्षण करें।
- [ ] अनुपलब्ध capabilities, open tasks, और बदले हुए task revisions को संभालें।
- [ ] दस्तावेज़ीकृत [API errors और retries](/integration/errors) को संभालें, जिसमें मूल key के साथ idempotent retries शामिल हैं।
- [ ] अपने operators को transfer failures और actionable instructions दिखाएँ।
- [ ] पुष्टि करें कि logs `X-Request-Id` या `correlationId` को secrets या संवेदनशील वित्तीय data को उजागर किए बिना बनाए रखते हैं।

## एक नियंत्रित live flow चलाएँ

एक ज्ञात customer और एक low-value transaction से शुरू करें। रिकॉर्ड करें:

| Control | Test से पहले परिभाषित करें |
| --- | --- |
| Scope | Customer, capability, account या destination, amount, और method। |
| Expected result | API state, balance या instructions, और वह webhook event जिसे आप observe करने की उम्मीद करते हैं। |
| Owner | पूर्ण flow देखने के लिए ज़िम्मेदार व्यक्ति। |
| Stop condition | कोई भी अप्रत्याशित state, अनुपस्थित webhook, गलत amount, या अनसुलझा task। |

वर्तमान API resource और authenticated webhook delivery दोनों को verify करें। यदि कोई भी अपेक्षित परिणाम से अलग है, तो अधिक traffic भेजने से पहले रुकें और जाँच करें।

पूर्ण flow के सफल होने के बाद, capability, account, destination, और transfer states की निगरानी करते हुए volume को धीरे-धीरे बढ़ाएँ।

Product journey के लिए [Common flows](/hi/integration/common-flows) पर लौटें, failure handling के लिए [Errors और retries](/integration/errors) की समीक्षा करें, या सटीक contracts के लिए [API Reference](/hi/api-reference/introduction) का उपयोग करें।
