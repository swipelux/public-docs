## KYB workflow

KYB workflow वर्तमान customer, related-party, capability, task, submission, और document resources को business और उसके ownership की नीति समीक्षा के साथ जोड़ता है।

<Warning>
  KYB outcomes और timelines नीति अनुमान हैं। वे API transitions, approval, या availability
  की गारंटी नहीं देते।
</Warning>

## वर्तमान workflow sequence

### 1. Business customer बनाएँ

Business customer को [`POST /v3/customers`](/api-reference/customers/post-v3-customers) के साथ बनाएँ। वर्तमान customer को [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id) के साथ पढ़ें।

### 2. Related parties बनाए रखें

वर्तमान parties की समीक्षा के लिए [`GET /v3/customers/{customerId}/related-parties`](/api-reference/customers/get-v3-customers-by-customer-id-related-parties), एक बनाने के लिए [`POST /v3/customers/{customerId}/related-parties`](/api-reference/customers/post-v3-customers-by-customer-id-related-parties), और आपूर्ति किए गए facts को update करने के लिए [`PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}`](/api-reference/customers/patch-v3-customers-by-customer-id-related-parties-by-related-party-id) का उपयोग करें।

वर्तमान tasks द्वारा अनुरोधित direct owners, parent entities, UBOs, control persons, directors, officers, और signers को बनाए रखें। उनकी roles अलग हैं।

### 3. Eligible capability खोजें और अनुरोध करें

[`GET /v3/customers/{customerId}/capabilities/supported`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-supported) पढ़ें। [`POST /v3/customers/{customerId}/capabilities/{capabilityId}`](/api-reference/capabilities/post-v3-customers-by-customer-id-capabilities-by-capability-id) का उपयोग करके केवल तब available या beta capability का अनुरोध करें जब customer eligible हो।

### 4. वर्तमान tasks पढ़ें

वर्तमान work को [`GET /v3/customers/{customerId}/tasks`](/api-reference/tasks/list-customer-tasks) के साथ सूचीबद्ध करें। प्रत्येक actionable task को [`GET /v3/customers/{customerId}/tasks/{taskId}`](/api-reference/tasks/get-customer-task) के माध्यम से प्राप्त करें, फिर इसकी वर्तमान revision, requirements, और sessions से अगली action निकालें।

### 5. वर्तमान task द्वारा अनुरोधित documents upload करें

एक अनुरोधित file को [`POST /v3/customers/{customerId}/documents`](/api-reference/documents/post-v3-customers-by-customer-id-documents) के साथ upload करें। वर्तमान task निर्धारित करता है कि क्या एक document आवश्यक है और इसके स्वीकृत type, count, या format को narrow कर सकता है।

### 6. पूर्ण task answers submit करें

वर्तमान task revision के लिए एक पूर्ण answer set [`POST /v3/customers/{customerId}/tasks/{taskId}/submissions`](/api-reference/task-submissions/create-customer-task-submission) के साथ submit करें। वर्तमान requirement ids का उपयोग करें और uploaded document ids को केवल वहीं संदर्भित करें जहाँ task पूछता है।

### 7. वर्तमान resources की निगरानी करें

प्रत्येक action या event के बाद, customer को [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id), capability को [`GET /v3/customers/{customerId}/capabilities/{capabilityId}`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-by-capability-id), उसके applications को [`GET /v3/customers/{customerId}/capabilities/{capabilityId}/applications`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-by-capability-id-applications), और किसी भी वर्तमान tasks को पुन: प्राप्त करें।

पूर्ण mechanics के लिए, [business onboarding](/hi/integration/onboarding/customers#business-customers), [Capabilities और tasks](/hi/integration/onboarding/capabilities-and-requirements#complete-current-tasks), और [Integration Documents guide](/hi/integration/onboarding/capabilities-and-requirements#upload-documents) देखें।

## Enhanced due diligence (EDD) triggers

निम्न के लिए EDD आवश्यक हो सकता है:

- High-risk jurisdictions
- High-risk verticals, जिसमें gaming, trading, और crypto exchanges शामिल हैं
- जटिल ownership structures
- लागू thresholds से अधिक अपेक्षित मासिक volume
- Sanctioned देशों से जुड़े Operations

## नीति समीक्षा outcomes

**Outcome:** KYB approval, caps के साथ conditional approval, या rejection।

ये नीति समीक्षा outcomes हैं, वर्तमान API status values नहीं। एक conditional नीति निर्णय "conditional approval" नामक status बनाए बिना वर्तमान resources के माध्यम से प्रतिबिंबित हो सकता है।

## Verification timeline

| Stage | विशिष्ट अवधि |
| --- | --- |
| Document upload | तत्काल |
| Initial review | 1-2 business days |
| Standard KYB | 2-5 business days |
| EDD, यदि triggered | 5-10 business days |

ये अवधि विशिष्ट नीति अनुमान हैं, गारंटीकृत API व्यवहार नहीं।

## सामान्य rejection कारण

| कारण | समाधान |
| --- | --- |
| अनुपस्थित documents | वर्तमान task द्वारा अनुरोधित प्रत्येक document type प्रदान करें |
| अस्पष्ट या धुंधले documents | उच्च गुणवत्ता वाले scans या images प्रदान करें |
| मेल न खाती जानकारी | सुनिश्चित करें कि entity नाम submitted evidence में मेल खाता है |
| अपूर्ण ownership structure | Evidence प्रदान करें जो 100% ownership का हिसाब दे |
| Expired documents | वर्तमान, वैध documents प्रदान करें |

## नीति terms और API states

नीति निर्णयों को वर्तमान resource vocabularies से अलग रखें:

- **Capability status:** `pending`, `ready`, `restricted`, `rejected`, `canceled`
- **Application status:** `requested`, `in_review`, `action_required`, `ready`, `rejected`, `disabled`, `canceled`
- **Task status:** `action_required`, `in_review`, `satisfied`, `rejected`, `canceled`
- **Submission outcome:** `in_review`, `accepted`, `changes_requested`, `rejected`

एक नीति outcome को API value में अनुवादित करने के बजाय नवीनतम resource पढ़ें।
