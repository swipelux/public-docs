---

Luo asiakas ennen kuin rakennat maksun vastaanottoa, maksua ulos tai luotua pankkitiliä. Kyvyt, tilit ja siirrot on rajattu tähän asiakkaaseen. Käytä `externalId`-kenttää vakaana yhdistämisenä järjestelmäsi vastaavaan tietueeseen.

```bash Environment variables
export API_BASE='https://platform.swipelux.com'
export SWIPELUX_API_KEY='replace-with-your-api-key'
```

## Yksityisasiakkaat {#individual-customers}

Yksityishenkilö vaatii vain `type`-kentän. Sisällytä jo tiedossa olevat profiilikentät ja lisää lisää vain, kun nykyinen kyky tai tehtävä niitä tarvitsee.

Luo asiakas [`POST /v3/customers`](/api-reference/customers/post-v3-customers) -toiminnolla:

```bash Create individual customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-user-123" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "individual",
  "externalId": "user_123",
  "individual": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Tallenna palautettu `data.id` muuttujaan `CUSTOMER_ID`. Katso [Yksityishenkilön käyttöönotto](/fi/knowledge-base/individual-onboarding/overview) käytäntökontekstia varten.

## Yritysasiakkaat {#business-customers}

Yritys vaatii `business.legalName`-kentän. Luo yritys samalla toiminnolla:

```bash Create business customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-company-456" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "business",
  "externalId": "company_456",
  "business": {
    "legalName": "Acme Payments SAS"
  }
}
JSON
```

Tallenna palautettu `data.id` muuttujaan `CUSTOMER_ID`. Katso [Yrityksen käyttöönotto](/fi/knowledge-base/business-onboarding/overview) käytäntö- ja dokumenttikontekstia varten.

## Lisää yritykseen liittyvät osapuolet {#add-business-related-parties}

Lisää johtajat, omistajat ja muut yrityksen osallistujat, kun ne ovat tiedossa tai pyydettyjä. Tämä esimerkki luo johtajan [`POST /v3/customers/{customerId}/related-parties`](/api-reference/customers/post-v3-customers-by-customer-id-related-parties) -toiminnolla:

```bash Add related party
curl --request POST \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}/related-parties" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: related-party-director-001" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "partyType": "person",
  "roles": ["director"],
  "title": "Chief executive officer",
  "person": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Tallenna palautettu `data.id` muuttujaan `RELATED_PARTY_ID`.

Jos sinun täytyy viedä asiakkaan tiedot, käytä toimintoa [`POST /v3/customers/{customerId}/export`](/api-reference/customers/post-v3-customers-by-customer-id-export) ja noudata sen pyyntöskeemaa. `json_basic_data`-muoto palauttaa nykyisen julkisen v3-asiakasresurssin JSON-liitteenä; jokainen kutsu laskee nykyiset tiedot uudelleen eikä sisällä asiakirjoja tai asiakirjojen metatietoja.

Siirrettävyystunnusmuotoa varten lähetä vastaanottavan KYC-projektin asiakas-ID kentässä `forClientId`, ei Swipeluxin `customerId`-arvoa. Käytä palautettua `data.token`-arvoa ennen `data.expiresAt`-ajankohtaa. Saman `Idempotency-Key`-avaimen ja rungon uudelleenkäyttö toistaa kyseisen tunnustuloksen; käytä uutta avainta uuden tunnuksen myöntämiseen.

## Tarkista ohitetut kentät päivityksissä {#check-ignored-fields-on-updates}

[`PATCH /v3/customers/{customerId}`](/api-reference/customers/patch-v3-customers-by-customer-id) ja `PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}` ohittavat rungon kentät, joita ne eivät tunnista. Kun ne ohittavat kentän, onnistunut vastaus sisältää otsakkeen `Swipelux-Ignored-Fields`. Otsake listaa ohitettujen kenttien JSON Pointerit pilkuilla erotettuina ja lajiteltuina. Luontipyynnöt eivät palauta tätä otsaketta.

Tarkista tämä otsake jokaisen päivityksen jälkeen. Muuten väärin nimetty tai väärään kohtaan sijoitettu kenttä hylätään ilman virhettä. Jos esimerkiksi lähetät `individual.dateOfBirth` kentän `individual.birthDate` sijaan, syntymäaika jää asettamatta.

```http Ignored fields response header
Swipelux-Ignored-Fields: /individual/dateOfBirth,/nickname
```

- Otsake listaa enintään 20 osoitinta ja 4096 merkkiä, ja se päättyy `...`, kun Swipelux lyhentää luetteloa. Osoittimien osat ovat prosenttikoodattuja.
- `metadata`-kentän sisäiset kentät ovat vapaamuotoisia, eikä niitä koskaan ilmoiteta.
- Idempotentit toistot jättävät otsakkeen pois, joten lue se ensimmäisestä vastauksesta.
- Tuntemattomat kentät saatetaan tulevassa versiossa hylätä virheellä `400`.

## Lue valmius kyvyistä

Asiakkaalla ei ole vahvistus- tai valmiustilaa API:ssa. Lue asiakas [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id) -toiminnolla nykyisten profiilitietojen saamiseksi, käytä sitten kykyjä ja niiden `openTaskIds`-kenttiä päättämään, mitä asiakas voi tehdä seuraavaksi.

```bash Get customer
curl --request GET \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

### Suodata asiakkaita kykyjen valmiuden mukaan {#filter-customers-by-capability-readiness}

Löydät tietyssä käyttöönottovaiheessa olevat asiakkaat suodattamalla [`GET /v3/customers`](/api-reference/customers/get-v3-customers) näillä kyselyparametreilla:

- `pooledCapabilityStatus`: asiakkaalla on yhteinen kyky tässä tilassa.
- `namedCapabilityStatus`: asiakkaalla on nimetty kyky tässä tilassa.
- `hasReadyNamedAccount`: `true` palauttaa asiakkaat, joilla on `ready`-tilassa oleva nimetty tili. `false` palauttaa asiakkaat, joilla sitä ei ole.

Tilasuodattimet hyväksyvät arvot `pending`, `ready`, `restricted`, `rejected` ja `canceled`. Swipelux lukee tilat samalla tavalla kuin `include=capabilities`. Katso [Jaetut ja nimelliset tilityypit](/fi/integration/onboarding/capabilities-and-requirements#pooled-vs-named-account-types).

Jos haluat jättää pois kyvyt, jotka vain odottavat, lisää `namedCapabilityExcludeWait=true` tai `pooledCapabilityExcludeWait=true`; se poistaa osumat, joiden `statusReason.resolution` on `wait`. `namedCapabilityIncludeWait=true` tai `pooledCapabilityIncludeWait=true` sisällyttää myös `restricted`-kyvyt, joilla on tämä ratkaisu. Kukin lippu toimii vain oman tilasuodattimensa kanssa, ja `ExcludeWait` voittaa, kun molemmat on asetettu.

Suodattimia voi yhdistää keskenään ja muiden luettelosuodattimien kanssa. Swipelux soveltaa niitä ennen sivutusta, joten jokainen sivu sisältää vain vastaavia asiakkaita. API-avaimet tarvitsevat niiden käyttöön oikeuden `accounts:read` tai `rails:read`. Virheellinen arvo palauttaa `400 validation_error`.

Esimerkiksi löytääksesi asiakkaat, jotka pankki on hyväksynyt nimettyyn kykyyn mutta joilla ei vielä ole valmista nimettyä tiliä:

```bash Filter customers awaiting a named account
curl --request GET \
  --get "${API_BASE}/v3/customers" \
  --data-urlencode "namedCapabilityStatus=ready" \
  --data-urlencode "hasReadyNamedAccount=false" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

### Etsi asiakkaat, joilta puuttuu asiakirjoja

Selvittääksesi, mitkä sivun asiakkaat ovat vielä velkaa pakollisia asiakirjoja, välitä `include=documentRequirements` kohteelle [`GET /v3/customers`](/api-reference/customers/get-v3-customers). Voit yhdistää sen kykyjen yhteenvetoihin muodossa `include=capabilities,documentRequirements`. API-avaimet tarvitsevat `accounts:read`-oikeuden `documentRequirements`-laajennukseen.

Jokainen asiakasyhteenveto sisältää tällöin `documentRequirements`-objektin:

```json Document requirement summary
{
  "documentRequirements": {
    "required": true,
    "count": 2
  }
}
```

- `count` on niiden pakollisten asiakirjavaatimusten määrä, jotka ovat tilassa `action_required` tehtävissä, jotka ovat myös tilassa `action_required`. Se kattaa kaikki tehtävien laajuudet, myös koko tilin tehtävät, eikä se riipu kykyjen valmiudesta.
- `required` on `true`, kun `count` on suurempi kuin `0`.
- Vaihtoehtojen joukko lasketaan kerran, ja vain silloin, kun jokainen vaihtoehto vaatii asiakirjan.

Yhteenveto on varovainen. Se jättää pois valinnaiset asiakirjat, ehdollisesti pakolliset asiakirjat sekä vaihtoehdot, joissa yhdistyvät asiakirjareitit ja muut reitit. Se jättää pois myös vaatimukset, jotka asiakas voi täyttää isännöidyn vahvistuksen kautta. Siksi `required: false` ei todista, ettei mikään asiakirjatehtävä koske asiakasta. Käytä sitä asiakkaiden priorisointiin ja lue sitten heidän tehtävänsä saadaksesi määräävän luettelon kerättävistä tiedoista. Ilman laajennusta vastaus jättää `documentRequirements`-kentän pois.

## Lue asiakkaan siirtovolyymi {#read-customer-transfer-volume}

Näyttääksesi, kuinka paljon rahaa asiakas on siirtänyt, kutsu `GET /v3/customers/{customerId}/transfer-totals`. API-avaimet tarvitsevat oikeuden `customers:read`. Tuntematon asiakas palauttaa `404 customer_not_found`.

```json Transfer totals
{
  "data": {
    "customerId": "cus_...",
    "received": { "amount": "1000.00", "currency": "USD" },
    "sent": { "amount": "25.00", "currency": "USD" }
  }
}
```

- Vain valmiit siirrot lasketaan. Odottavat ja epäonnistuneet siirrot jätetään pois.
- `received` laskee yhteen pay-in-maksut ja muilta asiakkailta saapuvat lompakkosiirrot. `sent` laskee yhteen payout-maksut ja lähtevät lompakkosiirrot.
- USD, USDC ja USDT lasketaan 1:1 USD:nä. Muiden valuuttojen summat jätetään pois.
- Siirrot asiakkaan omien lompakoiden välillä jätetään pois.
- Jokainen `amount` on desimaalimerkkijono kahdella desimaalilla, ja se on `"0.00"`, kun yksikään siirto ei täytä ehtoja.

Summat ovat siirtovolyymia, eivät nykyinen saldo.
