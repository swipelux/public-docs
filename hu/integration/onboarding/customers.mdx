Hozza létre az ügyfelet, mielőtt pénzbefizetést, kifizetést vagy kibocsátott bankszámlát épít. A képességek, számlák és átutalások az adott ügyfélhez tartoznak. Az `externalId` használatával stabil hozzárendelést tehet a rendszerében lévő rekordhoz.

```bash Environment variables
export API_BASE='https://platform.swipelux.com'
export SWIPELUX_API_KEY='replace-with-your-api-key'
```

## Magánszemély ügyfelek {#individual-customers}

Egy magánszemélyhez csak a `type` szükséges. Adja hozzá a már ismert profilmezőket, és csak akkor tegyen hozzá többet, ha az aktuális képességnek vagy feladatnak szüksége van rájuk.

Hozza létre az ügyfelet a [`POST /v3/customers`](/api-reference/customers/post-v3-customers) művelettel:

```bash Create individual customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-user-123" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "individual",
  "externalId": "user_123",
  "individual": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Tárolja a visszakapott `data.id` értéket `CUSTOMER_ID`-ként. A szabályzati kontextushoz lásd a [Magánszemély onboarding](/hu/knowledge-base/individual-onboarding/overview) oldalt.

## Üzleti ügyfelek {#business-customers}

Az üzleti ügyfélhez a `business.legalName` szükséges. Hozza létre a vállalkozást ugyanazzal a művelettel:

```bash Create business customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-company-456" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "business",
  "externalId": "company_456",
  "business": {
    "legalName": "Acme Payments SAS"
  }
}
JSON
```

Tárolja a visszakapott `data.id` értéket `CUSTOMER_ID`-ként. A szabályzati és dokumentum-kontextushoz lásd az [Üzleti onboarding](/hu/knowledge-base/business-onboarding/overview) oldalt.

## Üzleti kapcsolt felek hozzáadása {#add-business-related-parties}

Adja hozzá az igazgatókat, tulajdonosokat és egyéb üzleti résztvevőket, ha ismertek vagy kértek. Ez a példa egy igazgatót hoz létre a [`POST /v3/customers/{customerId}/related-parties`](/api-reference/customers/post-v3-customers-by-customer-id-related-parties) művelettel:

```bash Add related party
curl --request POST \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}/related-parties" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: related-party-director-001" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "partyType": "person",
  "roles": ["director"],
  "title": "Chief executive officer",
  "person": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Tárolja a visszakapott `data.id` értéket `RELATED_PARTY_ID`-ként.

Ha ügyfelet kell exportálnia, használja a [`POST /v3/customers/{customerId}/export`](/api-reference/customers/post-v3-customers-by-customer-id-export) műveletet, és kövesse a kérési sémáját. A `json_basic_data` formátum az aktuális nyilvános v3 ügyfél-erőforrást adja vissza JSON-mellékletként; minden hívás újraszámítja az aktuális adatokat, és kizárja a dokumentumokat és a dokumentum-metaadatokat.

Hordozhatósági token formátumhoz a fogadó KYC-projekt kliensazonosítóját küldje el `forClientId` értékként, ne a Swipelux `customerId` értékét. A visszakapott `data.token` értéket a `data.expiresAt` időpont előtt használja fel. Ugyanazon `Idempotency-Key` és törzs újbóli használata ugyanazt a tokeneredményt játssza vissza; új token kibocsátásához használjon új kulcsot.

## Figyelmen kívül hagyott mezők ellenőrzése frissítéskor {#check-ignored-fields-on-updates}

A [`PATCH /v3/customers/{customerId}`](/api-reference/customers/patch-v3-customers-by-customer-id) és a `PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}` figyelmen kívül hagyja azokat a törzsmezőket, amelyeket nem ismer fel. Ha figyelmen kívül hagy egy mezőt, a sikeres válasz tartalmazza a `Swipelux-Ignored-Fields` fejlécet. A fejléc vesszővel elválasztva és rendezve sorolja fel a figyelmen kívül hagyott mezők JSON Pointereit. A létrehozások nem adják vissza ezt a fejlécet.

Minden frissítés után ellenőrizze ezt a fejlécet. Ellenkező esetben a hibás nevű vagy rossz helyre tett mező hiba nélkül elvész. Ha például `individual.birthDate` helyett `individual.dateOfBirth` értéket küld, a születési dátum beállítatlan marad.

```http Ignored fields response header
Swipelux-Ignored-Fields: /individual/dateOfBirth,/nickname
```

- A fejléc legfeljebb 20 mutatót és 4096 karaktert sorol fel, és `...` jellel végződik, ha a Swipelux csonkítja a listát. A mutatószegmensek százalékos kódolásúak.
- A `metadata` belüli mezők szabad formátumúak, és soha nem kerülnek jelentésre.
- Az idempotens ismétlések kihagyják a fejlécet, ezért az első válaszból olvassa ki.
- Egy későbbi verzióban az ismeretlen mezőket `400` válasszal elutasíthatják.

## Készenlét olvasása képességekből

Az ügyfélnek nincs ellenőrzési vagy készenléti státusza az API-ban. Olvassa be az ügyfelet a [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id) művelettel az aktuális profiladatokért, majd használja a képességeket és azok `openTaskIds` értékeit annak eldöntéséhez, hogy az ügyfél mit tehet legközelebb.

```bash Get customer
curl --request GET \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

### Ügyfelek szűrése a képességek készenléte szerint {#filter-customers-by-capability-readiness}

Egy adott bevezetési szakaszban lévő ügyfelek megtalálásához szűrje a [`GET /v3/customers`](/api-reference/customers/get-v3-customers) kérést ezekkel a lekérdezési paraméterekkel:

- `pooledCapabilityStatus`: az ügyfélnek van ilyen állapotú közös képessége.
- `namedCapabilityStatus`: az ügyfélnek van ilyen állapotú nevesített képessége.
- `hasReadyNamedAccount`: a `true` azokat az ügyfeleket adja vissza, akiknek van `ready` állapotú nevesített számlájuk. A `false` azokat, akiknek nincs.

Az állapotszűrők a `pending`, `ready`, `restricted`, `rejected` vagy `canceled` értéket fogadják el. A Swipelux ugyanúgy olvassa az állapotokat, mint az `include=capabilities`. Lásd: [Közös és dedikált számlatípusok](/hu/integration/onboarding/capabilities-and-requirements#pooled-vs-named-account-types).

A csak várakozó képességek kihagyásához adja hozzá a `namedCapabilityExcludeWait=true` vagy `pooledCapabilityExcludeWait=true` paramétert; ez kiszűri azokat a találatokat, amelyek `statusReason.resolution` értéke `wait`. A `namedCapabilityIncludeWait=true` vagy `pooledCapabilityIncludeWait=true` az ilyen megoldású `restricted` képességeket is beleveszi. Minden jelző csak a saját állapotszűrőjével működik, és ha mindkettő be van állítva, az `ExcludeWait` érvényesül.

A szűrők egymással és a többi listaszűrővel kombinálhatók. A Swipelux a lapozás előtt alkalmazza őket, így minden oldal csak egyező ügyfeleket tartalmaz. A használatukhoz az API-kulcsoknak `accounts:read` vagy `rails:read` jogosultság kell. Az érvénytelen érték `400 validation_error` választ ad.

Például azoknak az ügyfeleknek a megtalálásához, akiket egy bank jóváhagyott egy nevesített képességre, de még nincs kész nevesített számlájuk:

```bash Filter customers awaiting a named account
curl --request GET \
  --get "${API_BASE}/v3/customers" \
  --data-urlencode "namedCapabilityStatus=ready" \
  --data-urlencode "hasReadyNamedAccount=false" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

### Hiányzó dokumentumokkal rendelkező ügyfelek keresése

Ha meg szeretné tudni, mely ügyfeleknek kell még kötelező dokumentumokat benyújtaniuk egy oldalon, adja át az `include=documentRequirements` paramétert a [`GET /v3/customers`](/api-reference/customers/get-v3-customers) végpontnak. Kombinálhatja a képesség-összefoglalókkal `include=capabilities,documentRequirements` formában. Az API-kulcsoknak `accounts:read` jogosultságra van szükségük a `documentRequirements` bővítéshez.

Ekkor minden ügyfél-összefoglaló tartalmaz egy `documentRequirements` objektumot:

```json Document requirement summary
{
  "documentRequirements": {
    "required": true,
    "count": 2
  }
}
```

- A `count` azoknak a kötelező dokumentumkövetelményeknek a száma, amelyek `action_required` állapotban vannak olyan feladatokon, amelyek szintén `action_required` állapotúak. Minden feladathatókört lefed, beleértve a teljes számlára vonatkozó feladatokat is, és nem függ a képességek készenlététől.
- A `required` értéke `true`, ha a `count` nagyobb, mint `0`.
- Egy alternatívakészlet egyszer számít, és csak akkor, ha minden alternatíva dokumentumot igényel.

Az összefoglaló óvatos. Kizárja az opcionális dokumentumokat, a feltételesen kötelező dokumentumokat, valamint azokat az alternatívákat, amelyek dokumentumos és nem dokumentumos utakat kevernek. Kizárja azokat a követelményeket is, amelyeket az ügyfél hosztolt ellenőrzéssel teljesíthet. Ezért a `required: false` nem bizonyítja, hogy nem vonatkozik rá dokumentumfeladat. Használja az ügyfelek rangsorolására, majd olvassa be a feladataikat a begyűjtendők hiteles listájáért. A bővítés nélkül a válasz nem tartalmazza a `documentRequirements` mezőt.

## Ügyfél átutalási forgalmának lekérdezése {#read-customer-transfer-volume}

Ha meg szeretné mutatni, mennyi pénzt mozgatott egy ügyfél, hívja meg a `GET /v3/customers/{customerId}/transfer-totals` végpontot. Az API-kulcsokhoz `customers:read` szükséges. Ismeretlen ügyfél esetén a válasz `404 customer_not_found`.

```json Transfer totals
{
  "data": {
    "customerId": "cus_...",
    "received": { "amount": "1000.00", "currency": "USD" },
    "sent": { "amount": "25.00", "currency": "USD" }
  }
}
```

- Csak a teljesített átutalások számítanak. A függőben lévő és sikertelen átutalások nem számítanak bele.
- A `received` összesíti a pay-ineket és a más ügyfelektől érkező bejövő wallet-átutalásokat. A `sent` összesíti a payoutokat és a kimenő wallet-átutalásokat.
- Az USD, USDC és USDT 1:1 arányban USD-ként számít. Más pénznemekben lévő összegek nem számítanak bele.
- Az ügyfél saját walletjai közötti átutalások nem számítanak bele.
- Minden `amount` két tizedesjegyű decimális karakterlánc, és `"0.00"`, ha egyetlen átutalás sem felel meg.

Az összegek mozgási forgalmat jelentenek, nem aktuális egyenleget.

Ezután folytassa a [Képességek és feladatok](/hu/integration/onboarding/capabilities-and-requirements) oldalon a szükséges termékeredmény felfedezéséhez és aktiválásához.
