title: "Pruebas en sandbox"

---

El sandbox utiliza el mismo host de la API que producción. Una clave de API de sandbox selecciona el entorno de pruebas, donde los helpers simulan resultados sin mover fondos reales.

Mantén la clave en tu backend. Los helpers de sandbox no sustituyen al cumplimiento normativo ni al onboarding de producción.

Utiliza [Errores y reintentos](/integration/errors) para probar cómo gestiona tu integración los fallos de validación, de estado y de plataforma reintenables devueltos por las operaciones del sandbox.

```bash Environment variables
export API_BASE='https://platform.swipelux.com'
export SWIPELUX_SANDBOX_API_KEY='replace-with-your-sandbox-key'
```

## Prueba la disponibilidad de una capacidad {#test-capability-readiness}

En el sandbox, las capacidades ACH, Wire y SWIFT, tanto con nombre como agrupadas, solo se ofrecen en JPMorgan Chase (`jpmorgan`). Omite `institutions` al solicitar una de estas capacidades y Swipelux selecciona `jpmorgan`. Indicar cualquier otro banco devuelve `422 capability_institutions_unsupported`. La lista de capacidades admitidas en el sandbox solo muestra `jpmorgan` para estos métodos. El enrutamiento de producción y otros métodos, como RTP, Pix y SPEI, no cambian.

```bash Request a sandbox bank capability
curl --request POST \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}/capabilities/${CAPABILITY_ID}" \
  --header "X-API-Key: ${SWIPELUX_SANDBOX_API_KEY}" \
  --header "Idempotency-Key: sandbox-capability-001" \
  --header "Content-Type: application/json" \
  --data '{"institutions":["jpmorgan"]}'
```

Después de solicitar una capacidad, establece su estado de sandbox con [`POST /v3/sandbox/customers/{customerId}/capabilities/{capabilityId}/status`](/api-reference/sandbox/post-v3-sandbox-customers-by-customer-id-capabilities-by-capability-id-status):

```bash Set capability status
curl --request POST \
  "${API_BASE}/v3/sandbox/customers/${CUSTOMER_ID}/capabilities/${CAPABILITY_ID}/status" \
  --header "X-API-Key: ${SWIPELUX_SANDBOX_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{"status":"ready"}'
```

Vuelve a consultar la capacidad después de usar el helper. Considera su `status` y `openTaskIds` actuales como el resultado que tu producto debe gestionar. Una respuesta `200` aún puede mostrar trabajo pendiente, como tareas del cliente o una revisión `pending`.

El helper devuelve `409 capability_status_blocked` cuando la capacidad no puede alcanzar el estado solicitado por un motivo que no puedes resolver en el sandbox, como `approval_scope_review_required`, una retención operativa o un estado terminal. El `statusReason` del problema incluye el código y el mensaje del motivo de la capacidad, con `retryable: false`. Lee la capacidad para obtener la `resolution` del motivo.

Forzar una capacidad con nombre a `rejected` por segunda vez devuelve la misma capacidad sin cambios. Forzar una capacidad rechazada a `restricted` o `ready` devuelve `422 invalid_capability`. En su lugar, crea un cliente de sandbox nuevo para probar esos estados.

## Prueba una tarea abierta

Crea una tarea de sandbox con [`POST /v3/sandbox/tasks`](/api-reference/sandbox/post-v3-sandbox-tasks). Asígnala al recurso cuyo flujo de trabajo estés probando y usa `items` para describir lo que el cliente debe enviar. Esta guía muestra flujos de capacidad y transferencia; la Referencia de la API define el ámbito de cliente y el esquema completo de la solicitud.

Usa un elemento `explanation` para una respuesta de texto y un elemento `document` para una carga. Los nuevos elementos `profile` también requieren `profilePointer`, un puntero JSON que identifica el campo del cliente. Consulta [Crear tarea de sandbox](/api-reference/sandbox/post-v3-sandbox-tasks) para ver los demás tipos de elementos y campos.

Para el ejemplo de transferencia, crea primero una transferencia de sandbox mediante un flujo de [entrada de fondos](/es/integration/receive-funds) o [pago](/es/integration/send-funds) y luego exporta el `data.id` devuelto:

```bash Transfer ID
export TRANSFER_ID='tr_replace_with_your_transfer_id'
```

```bash
curl --request POST \
  "${API_BASE}/v3/sandbox/tasks" \
  --header "X-API-Key: ${SWIPELUX_SANDBOX_API_KEY}" \
  --header "Content-Type: application/json" \
  --data @- <<JSON
{
  "scope": {
    "type": "capability",

  "items": [
    {
      "type": "explanation",
      "request": "Explain the source of funds."
    }
  ]
}
JSON
```

  <Tab title="RFI de transferencia + documento">

Aplica el ámbito de la tarea a la transferencia bajo revisión y solicita un documento con `constraints` que acoten los tipos, formatos y antigüedad aceptados.

```bash Create document task
curl --request POST \
  "${API_BASE}/v3/sandbox/tasks" \
  --header "X-API-Key: ${SWIPELUX_SANDBOX_API_KEY}" \
  --header "Content-Type: application/json" \
  --data @- <<JSON
{
  "scope": {
    "type": "transfer",
    "customerId": "${CUSTOMER_ID}",
    "transferId": "${TRANSFER_ID}"
  },
  "category": "transaction_rfi",
  "items": [
    {
      "type": "document",
      "request": "Upload a bank statement showing the source of funds for this transfer.",
      "constraints": {
        "acceptedDocumentTypes": ["bank_statement"],
        "acceptedFormats": ["pdf", "jpeg"],
        "maxAgeDays": 90
      }
    }
  ]
}
JSON
```

El ejemplo limita el tipo, el formato y la antigüedad aceptados del documento. Consulta [Crear tarea de sandbox](/api-reference/sandbox/post-v3-sandbox-tasks) para ver todas las restricciones de documento compatibles.

    {
      "requirementId": "${REQUIREMENT_ID}",

Luego acepta o rechaza el envío actual con [`POST /v3/sandbox/tasks/{taskId}/review`](/api-reference/sandbox/post-v3-sandbox-tasks-by-task-id-review):

```bash Review submission
curl --request POST \
  "${API_BASE}/v3/sandbox/tasks/${TASK_ID}/review" \
  --header "X-API-Key: ${SWIPELUX_SANDBOX_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{"outcome":"accepted"}'
```

Puedes revisar las tareas creadas con `POST /v3/sandbox/tasks` y las tareas de admisión de capacidades que Swipelux recopila. Revisar una tarea que pertenece a Operaciones o a otro flujo de trabajo devuelve `409 task_not_sandbox_reviewable`. Esa tarea sigue siendo legible a través de los endpoints de tareas y espera a que su propietario la revise. `404 task_not_found` significa que el ID de la tarea es desconocido o pertenece a otro comercio.

Utiliza [Capacidades y tareas](/es/integration/onboarding/capabilities-and-requirements) para el patrón de finalización de tareas en producción.

## Financia una cartera de sandbox

Acredita una cartera emitida con [`POST /v3/sandbox/accounts/{accountId}/topup`](/api-reference/sandbox/post-v3-sandbox-accounts-by-account-id-topup):

```bash Top up issued wallet
curl --request POST \
  "${API_BASE}/v3/sandbox/accounts/${ACCOUNT_ID}/topup" \
  --header "X-API-Key: ${SWIPELUX_SANDBOX_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{"amount":"250.00","currency":"USDC"}'
```

Guarda el `data.id` devuelto como `TRANSFER_ID` cuando quieras inspeccionar la transferencia de financiación simulada.

El id del topup es un id de transferencia. Recupéralo mediante [`GET /v3/transfers/{transferId}`](/api-reference/money-movement/get-v3-transfers-by-transfer-id) o lístalo mediante [`GET /v3/transfers`](/api-reference/money-movement/get-v3-transfers) para ejercitar tu ruta de código de depósito entrante contra los topups del sandbox. La proyección de la transferencia es un depósito entrante de stablecoin completado con `origin: "inbound_deposit"`, `method: "stablecoin_transfers"` y `direction: "stablecoin_move"`, y se devuelve con los filtros de listado correspondientes de `accountId`, `origin`, `method` y `direction`.

## Completa o falla una transferencia

Establece el resultado con [`POST /v3/sandbox/transfers/{transferId}/state`](/api-reference/sandbox/post-v3-sandbox-transfers-by-transfer-id-state):

<Tabs>
  <Tab title="Completar">

```bash
curl --request POST \
  "${API_BASE}/v3/sandbox/transfers/${TRANSFER_ID}/state" \
  --header "X-API-Key: ${SWIPELUX_SANDBOX_API_KEY}" \
  --header "Content-Type: application/json" \
  --data '{"state":"completed"}'
```

  </Tab>
  <Tab title="Fallar">

```bash
curl --request POST \
  "${API_BASE}/v3/sandbox/transfers/${TRANSFER_ID}/state" \
  --header "X-API-Key: ${SWIPELUX_SANDBOX_API_KEY}" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "state": "failed",
  "stateDetail": {
    "code": "sandbox_review",
    "message": "Sandbox transfer failed."
  }
}
JSON
```

  </Tab>
</Tabs>

A continuación, ejecuta un flujo de [cobro](/es/integration/receive-funds), [pago](/es/integration/send-funds) o [cuenta bancaria emitida](/es/integration/issue-bank-account) en sandbox.
