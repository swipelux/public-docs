本頁列出 Swipelux API 依日期排序的變更。每則條目會註明受影響的版本、變更類型，以及整合方需採取的任何行動。

<Update label="2026-11-16" description="v3" tags={["新增","變更","修正"]}>

### 新增
- `GET /v3/customers` 接受 `pooledCapabilityIncludeWait`、`pooledCapabilityExcludeWait`、`namedCapabilityIncludeWait` 與 `namedCapabilityExcludeWait`。請將每個參數搭配對應的 `pooledCapabilityStatus` 或 `namedCapabilityStatus` 篩選條件使用。`IncludeWait` 會加入處理方式為 `wait` 的受限能力，`ExcludeWait` 會移除處理方式為 `wait` 的能力。兩者皆為 `true` 時以 `ExcludeWait` 為準。這些篩選條件需要 `accounts:read` 或 `rails:read`。請參閱[客戶](/zh-Hant/integration/onboarding/customers#filter-customers-by-capability-readiness)。
- 透過 `include=capabilities` 傳回的能力摘要可能附有 `statusReason.resolution`：`wait`、`contact_support` 或 `none`。若原因取決於任務，請讀取該能力。
- 文件要求可能傳回長度為 3 到 50 個字元的 `constraints.idNumber`。當其 `required` 為 `true` 時，請在 `documentMetadata` 中附上證件號碼。當文件需要時，Dashboard 會要求填寫證件號碼與簽發國家。
- `PATCH /v3/customers/{customerId}/accounts/{accountId}` 在非 USD 的外部 SWIFT 帳戶上接受 `bankAddress`（最多 105 個字元）、`bankCity` 與 `bankPostalCode`。外幣 SWIFT 出金需要 `bankAddress` 與 `bankCity`。在 USD 帳戶上變更這些欄位會傳回 `409 conflict`。當待處理的報價或出金正在使用該帳戶時，變更會傳回 `409 account_has_active_transfers`，您可以重試。
- 在 Dashboard 中，KYB 接受 WebP、HEIF 與 HEIC 文件。

### 變更
- 當發行帳戶的 SWIFT 代碼、路由號碼或帳號變更時，Swipelux 會傳送 [`account.details_changed`](/api-reference/webhooks/account-details-changed)。`data.object` 是目前的帳戶，`data.previous` 只包含 `routingVersion`。請參閱[發行銀行帳戶](/zh-Hant/integration/issue-bank-account)。
- 封存作為未封存銀行帳戶結算錢包的錢包帳戶，會傳回 `409 account_has_dependent_accounts`。請使用 `PATCH` 將銀行帳戶的結算移至其他錢包，或先封存該銀行帳戶。
- `PATCH /v3/customers/{customerId}/recipients/{recipientId}` 會以 `400 validation_error` 拒絕另一種收款人類型的欄位，並為每個欄位傳回 `invalid_field` 錯誤：個人上的 `companyName` 與 `businessIndustry`，企業上的 `firstName` 與 `lastName`。
- 當相同的請求仍在執行時，`POST /v3/customers/{customerId}/tasks/{taskId}/withdrawals` 也會傳回附有 `retryable: true` 的 `409 idempotency_request_in_progress`。
- 在 Dashboard 中，遭拒絕的客戶刪除會列出阻擋刪除的資源，收款人國家使用國家選擇器，個人資料文字輸入上限為 256 個字元。從客戶頁面或 Balances 建立出金後，會開啟其詳細資料。

### 修正
- Swipelux 不再於單次更新中為同一能力傳送兩個 `capability.status_changed` 事件，且在狀態最終回到起始狀態時不傳送任何事件。
- 當帳戶在佈建期間遭拒絕時，`account.status_changed` 會回報 `previous.state: "provisioning"`，而非 `"in_review"`。

</Update>

<Update label="2026-11-09" description="v3" tags={["新增","變更","修正"]}>

### 新增
- 當銀行要求為轉給第三方的 USD SWIFT 出金提供證明文件時，Swipelux 會在該轉帳上開啟 `category: "transaction_rfi"` 的任務。該任務會要求一份文件及其參考號。請使用既有的任務提交端點回答，Swipelux 會將回答轉送給銀行。若出金在未獲銀行核准的情況下完成、失敗或遭退款，Swipelux 會取消該任務。請參閱[報價與轉帳](/zh-Hant/integration/quotes-and-transfers#supporting-documents-for-swift-payouts)。
- 所有銀行的發行 SWIFT 帳戶都會在 `details.accountHolderAddress` 中傳回受款人的郵寄地址。先前只有 Lead Bank 與 BMO 的帳戶會傳回。它不同於 `details.bankAddress`，後者是收款銀行的地址。請參閱[發行銀行帳戶](/zh-Hant/integration/issue-bank-account)。
- 以帳戶幣別存入非 USD SWIFT 帳戶的款項會以 USDC 結算至結算錢包。轉帳的 `amounts.in` 顯示以帳戶幣別收到的金額，`amounts.out` 顯示送達的 USDC。先前這些存款會被暫扣審核，且沒有轉帳或 webhook。
- 文件要求可能傳回 `constraints.issuingCountryRequired: true`。為其提交的每份文件都必須在 `documentMetadata` 中包含 `issuingCountry`。

### 變更
- 在第一個相同請求仍在執行時到達的重試，會在能力申請、文件、收款人及其目的地、規則、webhooks、報價、轉帳、轉帳取消與驗證工作階段共用權杖上傳回附有 `retryable: true` 的 `409 idempotency_request_in_progress`。先前這些路由傳回 `idempotency_conflict`。以不同本文重複使用金鑰仍會傳回 `idempotency_conflict`。請參閱[錯誤與重試](/integration/errors#idempotency-request-in-progress)。
- 銀行入金報價現在會傳回具體錯誤，而非一般失敗：`400 quote_amount_out_of_range`、`400 quote_volume_limit_exceeded`、`400 quote_destination_network_unsupported`、`503 quote_temporarily_unavailable`（可重試）或 `502 quote_failed`。
- 當銀行審核中的申請仰賴某份文件時，`DELETE /v3/customers/{customerId}/documents/{documentId}` 會傳回 `409 document_in_use`。請在審核結束或申請取消後再封存。
- 結算錢包為 USDT 的非 USD 銀行帳戶，現在在建立與更新時會傳回 `400 invalid_settlement_target`，即使沒有明確的 `settlement.currency`。請參閱[選擇結算幣別](/zh-Hant/integration/issue-bank-account#choose-the-settlement-currency)。
- 在 Dashboard 中，出金審核會將外幣收款金額標示為估計值。
- 在 Dashboard 與公開追蹤頁面上，遭銀行退回或撤銷的已完成轉帳會顯示提示。其狀態仍為 Completed。

### 修正
- 發行銀行帳戶在變為就緒時會傳送 `account.status_changed`。請參閱[Webhook](/zh-Hant/integration/webhooks)。
- 使用相同的冪等金鑰與檔案重試分段文件上傳，不再傳回 `409`。
- Dashboard 的交易篩選條件會依銀行通道比對銀行出金，並涵蓋所有加密網路。以精確 ID 搜尋可找到小額入金。

</Update>

### 新增
- 擁有就緒的 Lead Bank（`lead_bank`）`swift_named` 能力的客戶可以傳送 AUD、CAD、CHF、CZK、DKK、EUR、GBP、HKD、HUF、JPY、MXN、NOK、NZD、PLN、SEK、SGD 與 ZAR 的 SWIFT 出金。銀行未為該客戶啟用的幣別會傳回 `422 bank_not_supported_for_customer`。請使用精確的 USDC `in.amount` 報價，Swipelux 會從中以 USD 收取費用。報價的 `out.amount` 是以新的 `out.amountEstimated: true` 標示的估計值，傳送 `out.amount` 會傳回 `422 validation_error`，出金完成時轉帳會記錄實際送達金額。EUR、GBP、CHF、CZK、DKK、HUF、NOK、PLN 與 SEK 需要有效的 IBAN。其他幣別接受有效的 IBAN 或本地帳號，MXN 的本地帳號為 18 位數 CLABE。持有人地址需要包含郵遞區號。遭退回的出金會交由 Swipelux 審核，而非自動退款。請參閱[發送資金](/zh-Hant/integration/send-funds#foreign-currency-swift-payouts)。

</Update>

### 變更
- Swipelux 每天都會重新檢查已儲存的 webhook 目的地。若某個端點的主機名稱現在遭到拒絕，或解析至遭拒絕的位址，Swipelux 會暫停該端點並設定 `disabled: true`。僅變更 `url` 時，已暫停的端點仍維持暫停；若要恢復，請傳送可通過檢查的 `url` 並附上 `disabled: false`。請參閱[Webhook](/zh-Hant/integration/webhooks#use-a-public-destination-url)。
- 建立規則時，若目標錢包位於其他網路，或目標為銀行目的地，會以 `400 rule_target_invalid` 拒絕。請參閱[錯誤與重試](/integration/errors#rule-target-invalid)。
- 文件下載回應會附上 `Cache-Control: private, no-store`。
- 透過通行金鑰復原帳戶後，Dashboard 會寄送電子郵件給您，並在 24 小時內暫停出金、提領、密鑰建立、代理程式連線與團隊邀請。

- `include=capabilities` 不再對部分客戶傳回空清單。
- 沙箱帳戶餘額不再顯示浮點數捨入誤差。
- 若銀行出金報價帶有路線無法收取的開發者費用，現在會在報價時以 `400 validation_error` 拒絕，而非在執行時失敗。
- 當第一筆卡片付款仍在處理中而報價到期時，卡片付款連結不再開啟第二個結帳頁面。
- 已完成的卡片入金會保留其法幣來源金額。
- 對於 Lead Bank，Dashboard 的 **Open bank account** 抽屜不再提供該銀行不支援的 USDT 網路，並提供 Solana 上的 USDT。

### 新增
- [`GET /v3/customers/{customerId}/capabilities/supported`](/api-reference/capabilities/get-v3-customers-by-customer-id-capabilities-supported) 的每個項目都包含 `unavailableInstitutions`。它會列出提供該能力變體但不接受此客戶的銀行，每家銀行都帶有 `id`、`name`，以及結構與 `statusReason` 相同的 `reasons`。目前的原因代碼為 `jurisdiction_unsupported`、`legal_form_unsupported` 與 `customer_type_unsupported`。此欄位在共用型與非銀行項目中為 `[]`，且同一家銀行絕不會同時出現在 `institutions` 與 `unavailableInstitutions` 中。在能力申請中指定無法使用的銀行，仍會傳回 `422 capability_institutions_unsupported`。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements#show-why-a-bank-is-unavailable)。

### 新增
- 經過身分驗證的請求會依 API 金鑰、依整合企業以及依用戶端 IP 位址進行速率限制。超出限制的請求會傳回 `429 rate_limited`，並附上 `retryable: true` 與 `Retry-After` 標頭，後者會提供重試前需等待的秒數。尚未獲准的整合企業限制較低。API 參考中每個需身分驗證的操作都列出 `429` 回應。來自同一 IP 位址的重複驗證失敗在超出其限制後也會傳回 `429`，從該位址傳送的有效 API 金鑰在限制恢復之前也可能收到相同的回應，因此請在 `Retry-After` 延遲之後重試。請參閱[錯誤與重試](/integration/errors#rate-limited)。

### 變更
- Swipelux 已停用沒有公開部分的舊版 API 金鑰，例如不含點號的金鑰。使用這些金鑰的請求會傳回 `401 unauthorized`。

</Update>

### 變更
- 在您的整合企業 KYB 獲准之前，Swipelux 會在任意滾動 24 小時內、跨您的所有空間限制建立數量：10 個 API 金鑰、10 個 webhook 端點、10 條規則、250 位客戶、20 次 `sumsub_share_token` 匯出以及 10 次身分驗證匯入。這取代了每個正式環境空間 10 個有效 API 金鑰的限制；撤銷金鑰不會釋出名額。超出限制的建立會傳回 `422 merchant_kyb_not_approved`；Dashboard 會傳回一般的 `422`。失敗的建立與冪等重送不計入。這些限制以及每小時 20 次 webhook URL 變更的限制也適用於沙箱空間，除非您有已獲准或不要求 KYB 的正式環境空間。請參閱[每日建立限制](/zh-Hant/integration/go-live#daily-creation-limits)。

</Update>

<Update label="2026-10-28" description="v3" tags={["新增","變更"]}>

### 新增
- `GET /v3/customers` 接受 `pooledCapabilityStatus` 與 `namedCapabilityStatus` 篩選條件，值可為 `pending`、`ready`、`restricted`、`rejected` 或 `canceled`。它也接受 `hasReadyNamedAccount=true|false`，用來列出擁有或沒有 `ready` 具名帳戶的客戶。這些篩選條件可彼此組合，也可與其他清單篩選條件組合，Swipelux 會在分頁之前套用。API 金鑰需要 `accounts:read` 或 `rails:read` 才能使用。無效的值會傳回 `400 validation_error`。例如，`namedCapabilityStatus=ready&hasReadyNamedAccount=false` 可找出已獲銀行核准但尚無就緒具名帳戶的客戶。請參閱[客戶](/zh-Hant/integration/onboarding/customers#filter-customers-by-capability-readiness)。
- 當 `PATCH /v3/customers/{customerId}` 與 `PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}` 忽略無法辨識的請求本文欄位時，會傳回 `Swipelux-Ignored-Fields` 回應標頭。該標頭以逗號分隔並排序列出被忽略欄位的 JSON Pointer，最多 20 個指標與 4096 個字元，截斷時以 `...` 結尾。`metadata` 內的欄位一律不回報，冪等重送會省略此標頭。請在每次更新後檢查此標頭，以免在不知情的情況下遺失資料，例如以錯誤欄位名稱傳送的出生日期。請參閱[客戶](/zh-Hant/integration/onboarding/customers#check-ignored-fields-on-updates)。
- Webhook 端點包含 `disabled`，在對該端點的派送暫停期間其值為 `true`。在多次派送失敗後，Swipelux 也會暫停端點。在 [`PATCH /v3/webhooks/{webhookId}`](/api-reference/webhooks/patch-v3-webhooks-by-webhook-id) 中傳送 `disabled: true` 可暫停派送，傳送 `disabled: false` 可恢復派送。恢復時會重新檢查目的地 URL，若不再通過檢查則傳回 `400`，端點會維持暫停。
- Swipelux 可以暫停整合企業。暫停期間，使用其任何 API 金鑰發出的每個請求都會傳回附有 `retryable: false` 的 `403 merchant_suspended`，Swipelux 也會暫緩其 webhook 派送、規則執行與向銀行提出的申請。不會刪除或撤銷任何內容，因此在 Swipelux 解除暫停後，API 金鑰、webhook 端點與規則會恢復運作。若要解決暫停問題，請聯絡 Swipelux 支援團隊。請參閱[錯誤與重試](/integration/errors#merchant-suspended)。

### 變更
- 當身分驗證服務提供者拒絕建立共用權杖時（例如針對未知的 `forClientId`），帶有 `format: sumsub_share_token` 的 `POST /v3/customers/{customerId}/export` 會傳回附有 `retryable: false` 的 `422 kyc_provider_rejected`，而非 `502 request_failed`。回應包含固定的 Swipelux 訊息，絕不會重複提供者的錯誤文字，因此請在重試前檢查請求。其他提供者失敗仍會傳回可重試的 `502 request_failed`。
- `GET /v3/webhooks/portal` 的入口網站不再建立、編輯、暫停或刪除端點。使用具有 `webhooks:write` 的 API 金鑰時，它仍會顯示並輪替端點簽章密鑰、重試派送並重播派送。請使用 `POST /v3/webhooks` 建立端點，使用 `PATCH /v3/webhooks/{webhookId}` 變更或暫停端點，並使用 `DELETE /v3/webhooks/{webhookId}` 刪除端點。請參閱[Webhook](/zh-Hant/integration/webhooks)。
- `POST /v3/webhooks` 與 `PATCH /v3/webhooks/{webhookId}` 只接受所有解析位址皆為全域可路由單播位址的目的地。對於 IANA 特殊用途範圍中的位址、多播位址、內含遭拒絕 IPv4 位址的 IPv6 轉換形式、無法解析的主機名稱、`localhost`、單一標籤主機名稱，以及以 `.localhost`、`.local`、`.localdomain`、`.internal` 或 `.home.arpa` 結尾的主機名稱，會傳回 `400 validation_error`。

</Update>

### 新增
- 在商家面板中，擁有者與管理員可以透過 **Settings** > **Customer pages** 上傳公司標誌（PNG、JPG 或 WebP，最大 512 KB），並為每個空間設定 `https://` 返回 URL。在正式環境空間中，該標誌會取代您客戶託管條款頁面上的 Swipelux 文字標誌。當空間設有返回 URL 時，完成後的條款頁面會提供 **Return to the app**。

### 變更
- 託管條款頁面採用了新設計。沙箱流程的每個頁面都會顯示 **Sandbox** 標記。
- 在要求 KYB 的正式環境空間中，商家面板會在您的 KYB 獲准之前鎖定 **Customers**、**Balances** 與 **Transactions**。首頁會顯示上線步驟，客戶的 **Bank accounts** 區段會每家銀行一列並列出其幣別，並在銀行核准後顯示銀行帳戶詳細資料。
- 當服務該能力的銀行皆不提供入金報價時（例如 Lead Bank（`lead_bank`）的 `ach_named` 與 `wire_named`），入金的 `POST /v3/quotes` 會傳回附有 `retryable: false` 的 `422 capability_direction_unsupported`，而非可重試的 `503 rail_temporarily_unavailable`。使用相同 `Idempotency-Key` 的重試會重播該 `422`。

- `GET /v3/webhooks/portal` 傳回的入口網站 URL 會在一小時後到期，並附上 `Cache-Control: no-store`。使用具有 `webhooks:write` 的 API 金鑰時，入口網站會顯示端點簽章密鑰，並可管理端點、重試派送及重播派送。僅具有 `webhooks:read` 時，入口網站只會顯示派送記錄。請參閱[Webhook](/zh-Hant/integration/webhooks)。
- Citi（`citibank`）僅提供給企業客戶。所有企業都保有共用（pooled）Citi，而具名（named）Citi 僅提供給在美國境外註冊的企業。當客戶未獲提供 Citi 時，支援清單會省略它，指定它會傳回 `422 capability_institutions_unsupported`，且僅由 Citi 提供的方法會列為 `disabled`。未包含 `institutions` 的要求會從其餘銀行中選擇。既有的申請與帳戶不變。
- 具名 CFSB（`cfsb`）功能僅提供給美國客戶：在美國註冊的企業，以及居住在美國的個人。對於其他客戶，支援清單會省略具名 CFSB，指定它會傳回 `422 capability_institutions_unsupported`。未包含 `institutions` 的要求會從其餘銀行中選擇。共用 CFSB、國家不明的客戶以及既有的申請均不變。
- Lead Bank（`lead_bank`）的具名 ACH、Wire 與 SWIFT 功能，僅提供給 Lead Bank 依其法律形式與國家能夠完成開戶的客戶。對於其他客戶，支援清單會省略 `lead_bank`，指定它會傳回 `422 capability_institutions_unsupported`。Lead Bank 已完成開戶的客戶，以及其未結要求已指定 `lead_bank` 的功能，會保留它。既有的申請與帳戶不變。
- 在正式模式下，省略 `institutions` 的 `ach_named` 或 `wire_named` 能力申請，現在會在 Lead Bank 接受新客戶且能為該客戶開戶時預設使用 Lead Bank（`lead_bank`）：資料中至少列出一個國家且 Lead Bank 接受其中的每個國家，企業資料中列出的法律形式為 Lead Bank 所接受，且客戶在其他銀行沒有 `ready` 的申請（無論具名或共用）。其他客戶預設使用 JPMorgan Chase（`jpmorgan`），與 `ach_named` 先前的行為相同。`wire_named` 先前沒有預設銀行。客戶既有的目前申請仍然優先。`GET /v3/customers/{customerId}/capabilities/supported` 中的 `isDefault` 會對每位客戶套用 Lead Bank 規則，因此標示的銀行可能因客戶而異，且可能隨時間改變。請參閱[能力與任務](/zh-Hant/integration/onboarding/capabilities-and-requirements#discover-supported-capabilities)。
- 省略 `institutions` 的 `wire_pooled` 申請現在預設使用 JPMorgan Chase（`jpmorgan`），支援清單會以 `isDefault` 標示該銀行。先前這類申請會選擇 CFSB（`cfsb`）。
- RTP 僅提供共用（pooled）方式。沒有任何銀行向新要求提供 `rtp_named`，因此支援清單會將其顯示為 `disabled`。對於未持有 `rtp_named` 的客戶，針對它且指定銀行的功能要求或任務預覽會傳回 `422 capability_institutions_unsupported`，未包含 `institutions` 的則會傳回 `422 capability_variant_unavailable`。共用 RTP（`rtp_pooled`）由 Citi 提供，因此僅企業客戶可以申請。
- 針對個人與最終受益人的新身分文件要求可設定 `constraints.identityMetadataRequired: true`，因此每個檔案都需要在 `documentMetadata` 中提供證件號碼與簽發國家。新的企業地址證明與擁有者居住證明要求可設定 `constraints.maxIssueAgeDays: 90`，因此每個檔案都需要其簽發日期。既有任務會保留其要求，因此請讀取每個任務要求上的限制條件。
- 針對企業註冊要求（其 `profilePointer` 為 `/business/registration`）的任務答案，需要同時提供管轄國家、註冊號碼，以及早於提交日期的成立日期。該要求的 `valueSchema` 會公布此規則，部分答案會傳回 `400 validation_error`。
- 完成託管驗證後，對於結構化值（例如地址或稅務識別碼）的個人資料要求，Swipelux 僅在託管答案通過與直接答案相同的結構描述與限制檢查時才會接受。否則該要求會保持開啟，您需使用 `POST /v3/customers/{customerId}/tasks/{taskId}/submissions` 提交該值。因這一原因被 Swipelux 退回 `action_required` 的要求會帶有 `reviewFeedback.code: hosted_profile_direct_submission_required`。已為 `satisfied` 的任務會維持其狀態。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements#hosted-actions)。
- 遭託管驗證拒絕的任務，若該驗證決定日後被撤銷，可能會離開 `rejected`。此時任務會變為 `satisfied`，或在新的 `revision` 下變為 `action_required`，並重新開啟新決定未回答的要求。這些要求先前的提交仍為 `rejected`，因此請重新提交這些答案。請參閱[遷移至 v3](/zh-Hant/api-reference/versioning/migrate-to-v3#1-4-the-task-loop)。
- 收款人目的地的 `type` 現在是開放式列舉。本參考資料的先前版本將其描述為封閉式，因此請更新任何會拒絕或捨棄未知類型的用戶端。目的地回應與 `destination.status_changed` 事件現在可能帶有 `pix` 與 `pix_safe`，日後也可能新增更多類型。
- 收款人建立與更新要求（包括巢狀的 `address`）會忽略未定義的欄位，而不會傳回 `400 validation_error`。在建立要求中，屬於另一種收款人類型的名稱或產業欄位仍會傳回 `400`，`PATCH /v3/customers/{customerId}/recipients/{recipientId}` 中的 `type` 與 `externalId` 亦同。不含任何可識別欄位的 `PATCH` 會傳回 `400 validation_error`，而非 `200`。
- 對於僅要求文件的合格工作階段，驗證連結現在會開啟由 Swipelux 託管的文件上傳頁面。連結本身不變，其他工作階段仍會開啟託管的驗證流程。
- 個人客戶與關聯方人員的 `employment.occupation` 最多接受 255 個字元。
- 當資料值或任務答案包含 Swipelux 表單連結（例如 RFI、客戶請求或轉帳追蹤連結）時，`POST /v3/customers`, `PATCH /v3/customers/{customerId}`, `POST /v3/customers/{customerId}/related-parties`, `PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}` 與 `POST /v3/customers/{customerId}/tasks/{taskId}/submissions` 會回傳 `400 validation_error`。這不適用於 `externalId` 或 `metadata`。每個被拒絕的值都會出現在 `errors[]` 中，並附上 `code: public_form_link` 及其 JSON Pointer，且回應絕不會重複該連結。請改為直接傳送資訊本身。請參閱[錯誤與重試](/integration/errors#validation-error)。

### 修正
- 省略 `institutions` 的 `ach_pooled` 申請現在會選擇 JPMorgan Chase（`jpmorgan`），也就是支援清單以 `isDefault` 標示的銀行。先前它們可能會選擇 Citi（`citibank`）。既有的申請與帳戶不受影響。

- 審查人員新增文件提交欄位時，RFI 表單會保留現有輸入，因此重新提交時不會遺失先前的回答。
- 商家面板可從可用動作繼續託管的合規工作階段，而不會捨棄有效連結。
- 託管的服務條款連結現在適用於 API 傳回的所有任務範圍。
- 在商家面板中要求 Payment Access 後，面板會開啟該要求傳回的受理任務，而不是較早要求中的任務。
- 商家面板的 KYB 示範現在會要求目前的必填欄位。
- 報價若將來源錢包重複用作 `destinationId`，現在會在開始任何供應商工作前傳回可採取行動的 `422 quote_direction_invalid` 詳細資料。請參閱[報價與轉帳](/zh-Hant/integration/quotes-and-transfers)。
- API 現在會以 `400` 錯誤拒絕格式錯誤的查詢字串編碼，而不是在未提示的情況下正規化要求。請參閱[錯誤與重試](/integration/errors)。
- `POST /v3/customers/{customerId}/documents` 現在會以 `400` 錯誤拒絕空白、非 multipart 或格式錯誤的要求本文。

### 新增
- 在 OpenAPI 規範中發布 v3 Problem Details 目錄，讓整合方可以直接從 schema 對應錯誤回應。請參閱[錯誤](/integration/errors)。
- 為 v3 帳戶 webhook 事件新增 `customerId`，讓您無需後續讀取即可將帳戶活動關聯至擁有的客戶。請參閱 [Webhook](/zh-Hant/integration/webhooks)。
- 商家後台完整支援 V3 個人檔案欄位，讓入駐操作人員可以審核並編輯透過 v3 API 收集的每個 KYC 欄位。請參閱[客戶入駐](/zh-Hant/integration/onboarding/customers)。
- 發布 v3 開發者遷移指南。請參閱[遷移至 v3](/zh-Hant/api-reference/versioning/migrate-to-v3)。

### 變更
- 客戶與帳戶的國家代碼在寫入時現在會驗證為已指派的 ISO 3166-1 alpha-2 值。讀取時容許舊有儲存值，讓現有紀錄仍可繼續解析。請參閱[帳戶與錢包](/zh-Hant/integration/accounts)。
- USDC 的可用性現在依目的地網路限定，因此報價與轉帳只會在目的地實際支援的網路上提供 USDC。
- 所有入駐流程現在都需要 Swipelux 服務條款。既有的工作階段仍可恢復。請參閱[客戶入駐](/zh-Hant/integration/onboarding/customers)。
- `Capability.ready` 仍持續回報權限已獲核准。請使用 `accountProvisioning` 追蹤帳戶核發狀態：`not_applicable`、`not_started`、`in_progress`、`issued` 或 `failed`。請參閱[能力與任務](/zh-Hant/integration/onboarding/capabilities-and-requirements)。
- 現在接受來自 iPhone 的 HEIC 上傳作為身分與地址文件。
- 清除未完成任務仍需要的客戶或關聯方欄位，現在會傳回 `409 field_required_by_open_task`，並附上造成阻擋的 `taskId` 與 `fields`，而不是可重試的衝突。請先完成或取消該任務，再變更這些欄位。請參閱[錯誤與重試](/integration/errors#field-required-by-open-task)。

### 修正
- 重新執行已消耗的報價現在會回傳 `409 quote_execution_consumed`，而非通用錯誤。請參閱[報價與轉帳](/zh-Hant/integration/quotes-and-transfers)。
- 轉帳清單讀取與報價金額讀取在大量歷史結果上不再回傳 `500`。
- 並行的 KYC 重新導向現在會回傳衝突而非 `404`，因此重試能順利解決。託管的重新導向不再中途回滾，且 KYC 連結仍可恢復。
- 個人客戶的關聯方讀取不再回傳 `404`。
- 含無效錢包欄位的 KYB 提交會在送出前被拒絕，且同步失敗不再於商家後台中回報為成功。
- 商家後台中的需求任務現在會將已提交的答覆顯示為完成、獨立追蹤服務條款動作、移除重複的文件文字、讓已開始的 KYC 工作階段在完成前保持待處理，並在不破壞需求視圖的情況下處理過期任務。
- 商家後台中的驗證連結列現在每一列都會顯示 **Open** 動作，且每個任務連結都會在需求視圖中呈現。
