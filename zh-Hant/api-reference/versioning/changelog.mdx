本頁列出 Swipelux API 依日期排序的變更。每則條目會註明受影響的版本、變更類型，以及整合方需採取的任何行動。

若要將既有整合從較早版本升級，請參閱[遷移至 v3](/zh-Hant/api-reference/versioning/migrate-to-v3)。

<Update label="2026-10-08" description="v3" tags={["新增","變更","修正"]}>

### 新增
- 收款人目的地接受 `pix` 與 `pix_safe` 類型，用於巴西的 BRL 出金。Pix 目的地會付款至 Pix 金鑰。Pix Safe 目的地會付款至以持有人的 CPF 或 CNPJ、銀行的 ISPB 代碼、分行及帳號識別的銀行帳戶。兩者都需要客戶已就緒的 Pix 功能（`pix_pooled`），其出金以 USDC 提供資金，且不收取開發者費用。請參閱[收款人](/zh-Hant/integration/recipients)與[發送資金](/zh-Hant/integration/send-funds#pix-payouts)。
- `GET /v3/customers/{customerId}/tasks/{taskId}` 接受帶有文件要求 ID 的 `documentCandidatesFor`，以及用於具備替代方案之要求的 `documentAlternativeKey`。回應隨後會在 `data.documentCandidates` 中列出客戶已上傳且可滿足該要求的檔案，並附上任何 `missingMetadata` 或 `conflictingMetadata`。請提交候選檔案的 `documentId` 並補上缺少的 `documentMetadata`，而不必重新上傳檔案。此查詢需要 `accounts:read` 與 `customers:read`，無效的選擇會傳回 `400 validation_error`。

### 變更
- `GET /v3/webhooks/portal` 傳回的入口網站 URL 會在一小時後到期，並附上 `Cache-Control: no-store`。使用具有 `webhooks:write` 的 API 金鑰時，入口網站會顯示端點簽章密鑰，並可管理端點、重試派送及重播派送。僅具有 `webhooks:read` 時，入口網站只會顯示派送記錄。請參閱[Webhook](/zh-Hant/integration/webhooks)。
- Citi（`citibank`）僅提供給企業客戶。所有企業都保有共用（pooled）Citi，而具名（named）Citi 僅提供給在美國境外註冊的企業。當客戶未獲提供 Citi 時，支援清單會省略它，指定它會傳回 `422 capability_institutions_unsupported`，且僅由 Citi 提供的方法會列為 `disabled`。未包含 `institutions` 的要求會從其餘銀行中選擇。既有的申請與帳戶不變。
- 具名 CFSB（`cfsb`）功能僅提供給美國客戶：在美國註冊的企業，以及居住在美國的個人。對於其他客戶，支援清單會省略具名 CFSB，指定它會傳回 `422 capability_institutions_unsupported`。未包含 `institutions` 的要求會從其餘銀行中選擇。共用 CFSB、國家不明的客戶以及既有的申請均不變。
- Lead Bank（`lead_bank`）的具名 ACH、Wire 與 SWIFT 功能，僅提供給 Lead Bank 依其法律形式與國家能夠完成開戶的客戶。對於其他客戶，支援清單會省略 `lead_bank`，指定它會傳回 `422 capability_institutions_unsupported`。Lead Bank 已完成開戶的客戶，以及其未結要求已指定 `lead_bank` 的功能，會保留它。既有的申請與帳戶不變。
- 針對個人與最終受益人的新身分文件要求可設定 `constraints.identityMetadataRequired: true`，因此每個檔案都需要在 `documentMetadata` 中提供證件號碼與簽發國家。新的企業地址證明與擁有者居住證明要求可設定 `constraints.maxIssueAgeDays: 90`，因此每個檔案都需要其簽發日期。既有任務會保留其要求，因此請讀取每個任務要求上的限制條件。
- 收款人目的地的 `type` 現在是開放式列舉。本參考資料的先前版本將其描述為封閉式，因此請更新任何會拒絕或捨棄未知類型的用戶端。目的地回應與 `destination.status_changed` 事件現在可能帶有 `pix` 與 `pix_safe`，日後也可能新增更多類型。
- 對於僅要求文件的合格工作階段，驗證連結現在會開啟由 Swipelux 託管的文件上傳頁面。連結本身不變，其他工作階段仍會開啟託管的驗證流程。
- 個人客戶與關聯方人員的 `employment.occupation` 最多接受 255 個字元。
- 當資料值或任務答案包含 Swipelux 表單連結（例如 RFI、客戶請求或轉帳追蹤連結）時，`POST /v3/customers`, `PATCH /v3/customers/{customerId}`, `POST /v3/customers/{customerId}/related-parties`, `PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}` 與 `POST /v3/customers/{customerId}/tasks/{taskId}/submissions` 會回傳 `400 validation_error`。這不適用於 `externalId` 或 `metadata`。每個被拒絕的值都會出現在 `errors[]` 中，並附上 `code: public_form_link` 及其 JSON Pointer，且回應絕不會重複該連結。請改為直接傳送資訊本身。請參閱[錯誤與重試](/integration/errors#validation-error)。

### 修正
- 出金報價與轉帳回應會將 USDC 或 USDT 來源金額保留至小數點後六位，例如 `4009.711365` 而非 `4009.71`。法幣金額保留兩位小數。建立或讀取穩定幣來源金額超過兩位小數的出金時，不再傳回 `500`。
- [`POST /v3/customers/{customerId}/capabilities/{capabilityId}/cancel`](/api-reference/capabilities/post-v3-customers-by-customer-id-capabilities-by-capability-id-cancel) 參考資料現在會依實際運作方式說明取消。您可以取消狀態為 `ready` 的功能，`stablecoin_transfers` 功能無法取消，且取消只會終止該功能，其申請仍會保留各自的狀態、任務與核准。

</Update>

<Update label="2026-10-05" description="v3" tags={["新增","變更","修正"]}>

### 新增
- `GET /v3/customers` 接受 `include=documentRequirements`。每筆客戶摘要隨後會回報仍待提交的必要文件數量，與功能就緒狀態無關。可合併使用 `include=capabilities,documentRequirements`。請參閱[客戶](/zh-Hant/integration/onboarding/customers)。
- 商家面板的 Webhooks 頁面在端點選單中新增 **Replay missed events**。它會重新傳送過去 13 天內端點從未收到的事件，且絕不會重複傳送同一事件。請參閱[Webhook](/zh-Hant/integration/webhooks#recover-deliveries)。
- 商家面板的 **Settings** 頁面新增 **Compliance** 區段。擁有者與管理員可以設定合規電子郵件地址，並選擇在 Swipelux 要求提供客戶的更多資訊時是否接收電子郵件。
- 商家可以直接在商家面板的 KYB 頁面回覆自己的 KYB 合規要求。

### 變更
- 銀行受理完成後，客戶與關聯方更新不再傳回 `409 field_conflicts_with_completed_intake`。更新會被儲存，每個新的銀行申請都會依其自身要求檢查最新的客戶檔案。
- 當功能現有的銀行路由無法安全更新時，功能要求會傳回 `409 capability_route_header_conflict`。重試前請聯絡 Swipelux 支援團隊。
- 當 `institutions` 指定了該功能不提供的銀行時，`GET /v3/customers/{customerId}/capabilities/{capabilityId}/tasks-preview` 會傳回 `422 capability_institutions_unsupported`，與功能要求的行為一致。
- 在沙盒中，ACH、Wire 與 SWIFT 功能僅由 JPMorgan Chase 提供。省略 `institutions` 的要求會選擇 `jpmorgan`，指定其他銀行則會傳回 `422 capability_institutions_unsupported`。正式環境的路由不變。請參閱[在沙盒中測試](/zh-Hant/integration/sandbox)。
- 當模擬案例無法達到所要求的狀態時，強制設定沙盒功能狀態會傳回 `409 capability_status_blocked` 並附上 `statusReason`。重複已套用的強制設定會傳回 `200`，且不做任何變更。請參閱[在沙盒中測試](/zh-Hant/integration/sandbox#test-capability-readiness)。
- 對於由營運團隊或其他工作流程擁有的任務,`POST /v3/sandbox/tasks/{taskId}/review` 會回傳 `409 task_not_sandbox_reviewable`。來自 `POST /v3/sandbox/tasks` 的任務以及 Swipelux 收集的能力受理任務仍可審核。請參閱[在沙盒中測試](/zh-Hant/integration/sandbox)。
- 若在帳戶仍於銀行端佈建時變更結算設定，`PATCH /v3/customers/{customerId}/accounts/{accountId}` 會傳回 `409 account_provisioning_unresolved`。請在佈建完成後重試。請參閱[錯誤與重試](/integration/errors#account-provisioning-unresolved)。
- `POST /v3/transfers` 可能會傳回 `409 quote_execution_evidence_conflict`。請建立新的報價並執行。請參閱[錯誤與重試](/integration/errors)。
- 商家面板的 **Pay out** 抽屜會顯示完整的目的地資料、以切換開關遮蔽帳號與錢包地址，並顯示每種付款方式的預估到帳時間。
- 商家面板將銀行帳戶併入客戶的 **Payment access** 分頁，並提供列出每家銀行名稱的任務卡片。**Documents** 分頁已移至 **Profile**。
- 在商家面板中開立具名銀行帳戶現在只需一個步驟，並會列出每家銀行的幣別、方式與入駐時間。請參閱[帳戶](/zh-Hant/integration/accounts)。
- 因審查而被暫停的銀行帳戶會在商家面板中顯示為 **On hold**，並附上帳戶 ID 與 **Contact support** 操作。
- 當 Swipelux 正在準備提交申請且尚未開始審查時，處於 `pending` 的能力現在會回報 `statusReason.code: preparing_submission`，而非 `review_in_progress`。兩個代碼都使用 `resolution: wait`。在兩者之間切換時狀態仍為 `pending`，因此不會傳送 `capability.status_changed` 事件。現有能力會在下一次重新評估時採用新代碼。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements#continue-when-the-capability-is-ready)。
- 商家面板中客戶 **Payment access** 分頁上的 **Shared methods** 表格，對於能力回報 `preparing_submission` 的共用方式，會顯示 **In preparation** 而非 **In review**。
- 能力的 `applications` 列表現在僅顯示其目前的申請，適用於能力讀取（包括 `GET /v3/customers/{customerId}/capabilities/{capabilityId}/applications`）、能力申請回應以及 `capability.status_changed` 事件。被較新申請取代的申請仍會出現在 `GET /v3/customers/{customerId}/applications` 中，其中 `supersededByApplicationId` 指明其後繼申請。被取代申請的未完成任務仍計入能力的 `openTaskIds`。能力的狀態與 `openTaskIds` 不會改變，因此此變更本身不會傳送任何 webhook 事件。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements#list-the-customers-applications)。

### 修正
- 在銀行核准前，針對同一已發行帳戶送出的第二個 `allowPending` 要求，現在會傳回 `409` 並在 `holder.accountId` 中指出等待中的帳戶，而不是傳回 `500`。請參閱[發行銀行帳戶](/zh-Hant/integration/issue-bank-account)。
- 取消功能時，現在會關閉仍在等待銀行核准的已發行帳戶要求，讓之後在同一家銀行的要求重新開始。
- 重新要求所有銀行案件皆遭拒絕的已取消功能時，會從 `canceled` 發布單一 `capability.status_changed` 事件。
- 在銀行先前的申請已封存後重新要求該銀行，現在會提交新的申請。
- 只要對應的功能顯示為 `ready`，即可新增收款人目的地，而不會傳回 `409 rail_not_ready`。請參閱[收款人](/zh-Hant/integration/recipients)。
- 在您首次開啟商家面板的 Webhooks 頁面之前傳送的 Webhook 事件現在會被保留，因此您可以將其重新傳送至新的端點。
- 商家面板中的任務到期日會以您自己的時區顯示，且當沒有任何待處理項目時，銀行審查抽屜會顯示 **All requirements submitted**。

</Update>

<Update label="2026-09-28" description="v3" tags={["新增","變更","修正"]}>

### 新增
- `POST /v3/quotes` 接受選用的 `institutionId`，用於為加密貨幣轉法幣的出金報價選擇已核准的銀行通道。省略此欄位即維持自動路由。若選擇無法用於該出金的銀行，會傳回 `422 bank_not_supported_for_customer`；若在任何其他報價類型上傳送 `institutionId`，則會傳回 `400 validation_error`。請參閱[發送資金](/zh-Hant/integration/send-funds)。
- `POST /v3/customers/{customerId}/accounts` 上的已發行銀行帳戶要求現在接受 `institution`，可將帳戶固定於單一銀行且不進行備援切換；並接受 `allowPending: true`，可在該銀行的申請仍待核准時先儲存要求。`allowPending` 需要搭配 `institution`。已儲存的要求會回報所依據的 `applicationId`。請參閱[發行銀行帳戶](/zh-Hant/integration/issue-bank-account)。
- 商家面板新增原生 **Webhooks** 頁面，用於管理端點。請參閱[Webhook](/zh-Hant/integration/webhooks)。
- 商家面板新增 **Pay in** 抽屜，提供具名銀行帳戶、加密貨幣存款與審核步驟。
- 商家面板的 **Pay out** 流程會在來源選擇器中顯示錢包餘額、新增 **Max** 金額選項，並包含審核步驟。
- 商家面板中的客戶檔案新增 **Recipients & destinations** 分頁。
- 任務要求可以包含簡短的 `title` 標題。要求的 `prompt` 仍承載指引說明。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements)。

### 變更
- 共用（pooled）Wire 通道上的 Wire 入金報價現在至少需要 $20。低於通道最低金額，或金額過小而不足以支付轉帳費用的報價，會傳回 `422 amount_not_deliverable`，而不是一般的報價失敗。請參閱[接收資金](/zh-Hant/integration/receive-funds)。
- Webhook 入口網站現在會依資源將 v3 事件類型分組，並顯示每個事件的 payload schema 與範例。舊版事件類型會顯示在獨立的 **Legacy** 群組中，並標示為已淘汰。已訂閱這些事件類型的端點會繼續收到它們；新訂閱請使用 v3 事件類型。請參閱[Webhook](/zh-Hant/integration/webhooks)。
- 沙盒儲值現在會發出 `transfer.created` 與 `transfer.state_changed` webhook 事件。請參閱[在沙盒中測試](/zh-Hant/integration/sandbox)。
- 當客戶已有使用中的已核發帳戶時，`accountProvisioning` 現在會回報 `issued`。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements)。
- 商家面板中的銀行帳戶詳細資料會在抽屜中開啟，並顯示銀行標誌。請參閱[帳戶](/zh-Hant/integration/accounts)。
- 商家面板將資金移動標示為 **Pay in** 與 **Pay out**，讓您保持登入六小時，並以電子郵件將協助要求傳送給 Swipelux 支援團隊。
- 在接受直接提交的受理任務中，已有客戶檔案或已上傳文件佐證的合格要求會自動進入 `in_review`。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements#reused-profile-evidence)。

### 修正
- 重新要求已取消的功能時，不再因已被取代的申請紀錄或過時的要求而失敗。
- 儲存在已停用 Fedwire ID 下的功能現在會讀取為 `wire`，而不是傳回 `500`。

</Update>

<Update label="2026-09-21" description="v3" tags={["新增","變更","移除","修正"]}>

### 新增
- `GET /v3/customers/{customerId}/applications` 會列出客戶的申請案件，並附上每個案件所要求的功能，以及其核准所涵蓋的功能。一家銀行的一次核准可涵蓋多項功能。保留的歷史案件會透過 `supersededByApplicationId` 指向其後繼案件。此清單支援游標分頁與 `updatedAfter`。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements)。
- 對於以案件為基礎的功能，`POST /v3/customers/{customerId}/capabilities/{capabilityId}` 的回應會包含 `selectedApplicationId`。它會識別該要求重複使用的既有申請案件，或其所開啟的案件。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements)。
- 由 `GET /v3/institutions` 與支援功能清單傳回的機構包含可為 null 的 `logoUrl`。可用時請用它顯示銀行品牌，當其為 `null` 時則改為顯示機構名稱。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements)。
- 現已提供 USD SWIFT 出金。SWIFT 出金至少需要 100 USD。商家面板會為收款人收集 SWIFT 銀行指令。請參閱[發送資金](/zh-Hant/integration/send-funds)。
- 已發行銀行帳戶可透過具名收款資料經由 SWIFT 收款。請參閱[發行銀行帳戶](/zh-Hant/integration/issue-bank-account)。
- USDT 現在可作為 ACH 與 Wire 出金的來源。請參閱[發送資金](/zh-Hant/integration/send-funds)。
- 已發行銀行帳戶現在接受值為 `USDC` 或 `USDT` 的 `settlement.currency`，用於選擇交付至結算錢包的穩定幣，且與錢包帳戶的幣別無關。省略此欄位則繼續以錢包的幣別結算。請參閱[發行銀行帳戶](/zh-Hant/integration/issue-bank-account)。
- SWIFT 銀行帳戶與收款人目的地接受 `bankCity`、`bankState`、`bankPostalCode` 與 `bankAddressLine2`，以及選用的 `beneficiaryTaxId`、`beneficiaryPhoneNumber`、`ifscBranchCode`、`paymentCode` 與中介銀行資料。請參閱[發送資金](/zh-Hant/integration/send-funds)。
- 當銀行提供分開的 ACH 與 Wire 路由號碼時，已發行銀行帳戶的詳細資料會包含 `achRoutingNumber` 與 `wireRoutingNumber`，並包含收款銀行的 `bankLogoUrl`。請參閱[發行銀行帳戶](/zh-Hant/integration/issue-bank-account)。
- `capability.created` webhook 事件包含 `applicationId`，以及值為 `requested` 或 `approval` 的 `origin`，讓您能區分自己要求的功能與由核准所涵蓋的功能。請參閱[Webhook](/zh-Hant/integration/webhooks)。
- 要求可以宣告用於驗證的 `constraints.format`，例如 `http_url`、`us_ssn`、`us_ein` 或 `bank_industry_classification`。請參閱[功能與要求](/zh-Hant/integration/onboarding/capabilities-and-requirements)。

### 變更

- 清除未完成任務仍需要的客戶或關聯方欄位，現在會傳回 `409 field_required_by_open_task`，並附上造成阻擋的 `taskId` 與 `fields`，而不是可重試的衝突。請先完成或取消該任務，再變更這些欄位。請參閱[錯誤與重試](/integration/errors#field-required-by-open-task)。

### 修正
- 重新執行已消耗的報價現在會回傳 `409 quote_execution_consumed`，而非通用錯誤。請參閱[報價與轉帳](/zh-Hant/integration/quotes-and-transfers)。
- 轉帳清單讀取與報價金額讀取在大量歷史結果上不再回傳 `500`。
- 並行的 KYC 重新導向現在會回傳衝突而非 `404`，因此重試能順利解決。託管的重新導向不再中途回滾，且 KYC 連結仍可恢復。
- 個人客戶的關聯方讀取不再回傳 `404`。
- 含無效錢包欄位的 KYB 提交會在送出前被拒絕，且同步失敗不再於商家後台中回報為成功。
- 商家後台中的需求任務現在會將已提交的答覆顯示為完成、獨立追蹤服務條款動作、移除重複的文件文字、讓已開始的 KYC 工作階段在完成前保持待處理，並在不破壞需求視圖的情況下處理過期任務。
- 商家後台中的驗證連結列現在每一列都會顯示 **Open** 動作，且每個任務連結都會在需求視圖中呈現。
