入金、支払い、または発行済み銀行口座を構築する前に顧客を作成します。ケイパビリティ、口座、送金はその顧客にスコープされます。`externalId` を、システム内の対応するレコードへの安定したマッピングとして使用してください。

```bash Environment variables
export API_BASE='https://platform.swipelux.com'
export SWIPELUX_API_KEY='replace-with-your-api-key'
```

## 個人顧客 {#individual-customers}

個人顧客は `type` のみが必須です。既知のプロファイル項目を含め、現在のケイパビリティやタスクが必要とする場合にのみ、他の項目を追加してください。

[`POST /v3/customers`](/api-reference/customers/post-v3-customers) で顧客を作成します。

```bash Create individual customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-user-123" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "individual",
  "externalId": "user_123",
  "individual": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

返された `data.id` を `CUSTOMER_ID` として保存します。ポリシー文脈については [個人オンボーディング](/jp/knowledge-base/individual-onboarding/overview) をご覧ください。

## ビジネス顧客 {#business-customers}

ビジネスには `business.legalName` が必須です。同じ操作でビジネスを作成します。

```bash Create business customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-company-456" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "business",
  "externalId": "company_456",
  "business": {
    "legalName": "Acme Payments SAS"
  }
}
JSON
```

返された `data.id` を `CUSTOMER_ID` として保存します。ポリシーおよびドキュメントの文脈については [ビジネスオンボーディング](/jp/knowledge-base/business-onboarding/overview) をご覧ください。

## ビジネスの関連当事者を追加する {#add-business-related-parties}

取締役、所有者、その他のビジネス参加者が判明したり要求された時点で追加してください。この例では、[`POST /v3/customers/{customerId}/related-parties`](/api-reference/customers/post-v3-customers-by-customer-id-related-parties) で取締役を作成します。

```bash Add related party
curl --request POST \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}/related-parties" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: related-party-director-001" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "partyType": "person",
  "roles": ["director"],
  "title": "Chief executive officer",
  "person": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

返された `data.id` を `RELATED_PARTY_ID` として保存します。

顧客をエクスポートする必要がある場合は、[`POST /v3/customers/{customerId}/export`](/api-reference/customers/post-v3-customers-by-customer-id-export) を使用し、リクエストスキーマに従ってください。`json_basic_data` 形式は、現在の公開 v3 顧客リソースを JSON 添付ファイルとして返します。各呼び出しは現在のデータを再計算し、ドキュメントおよびドキュメントのメタデータは含まれません。

ポータビリティトークン形式の場合は、Swipelux の `customerId` ではなく、受け取り側の KYC プロジェクトのクライアント ID を `forClientId` として送信してください。返された `data.token` は `data.expiresAt` より前に使用してください。同じ `Idempotency-Key` とボディを再利用すると、そのトークンの結果が再生されます。別のトークンを発行するには新しいキーを使用してください。

## 更新時に無視されたフィールドを確認する {#check-ignored-fields-on-updates}

[`PATCH /v3/customers/{customerId}`](/api-reference/customers/patch-v3-customers-by-customer-id) と `PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}` は、認識できない本文フィールドを無視します。フィールドを無視した場合、成功レスポンスに `Swipelux-Ignored-Fields` ヘッダーが含まれます。このヘッダーには、無視されたフィールドの JSON Pointer がカンマ区切りで並べ替えて記載されます。作成リクエストではこのヘッダーは返されません。

更新のたびにこのヘッダーを確認してください。確認しないと、名前や位置を誤ったフィールドがエラーなしで破棄されます。たとえば、`individual.birthDate` の代わりに `individual.dateOfBirth` を送信すると、生年月日は設定されないままになります。

```http Ignored fields response header
Swipelux-Ignored-Fields: /individual/dateOfBirth,/nickname
```

- ヘッダーには最大 20 個のポインターと 4096 文字までが記載され、Swipelux が一覧を切り詰めた場合は末尾が `...` になります。ポインターのセグメントはパーセントエンコードされます。
- `metadata` 内のフィールドは自由形式で、報告されることはありません。
- 冪等な再送ではヘッダーが省略されるため、最初のレスポンスから読み取ってください。
- 将来のバージョンでは、不明なフィールドが `400` で拒否される場合があります。

## ケイパビリティから ready 状態を読み取る

顧客自体には、API における検証や ready 状態はありません。現在のプロファイルデータを取得するには [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id) で顧客を読み取り、ケイパビリティとその `openTaskIds` を使って、顧客が次に何をできるかを判断してください。

```bash Get customer
curl --request GET \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

### ケイパビリティの準備状況で顧客を絞り込む {#filter-customers-by-capability-readiness}

特定のオンボーディング段階にある顧客を見つけるには、次のクエリパラメーターで [`GET /v3/customers`](/api-reference/customers/get-v3-customers) を絞り込みます。

- `pooledCapabilityStatus`: 顧客がこのステータスのプール型ケイパビリティを持っています。
- `namedCapabilityStatus`: 顧客がこのステータスの名義型ケイパビリティを持っています。
- `hasReadyNamedAccount`: `true` は `ready` の名義型口座を持つ顧客を返します。`false` は持たない顧客を返します。

ステータスフィルターには `pending`、`ready`、`restricted`、`rejected`、`canceled` を指定できます。Swipelux は `include=capabilities` と同じ方法でステータスを読み取ります。[プール型と名義型の口座タイプ](/jp/integration/onboarding/capabilities-and-requirements#pooled-vs-named-account-types) を参照してください。

待機中のみのケイパビリティを除外するには、`namedCapabilityExcludeWait=true` または `pooledCapabilityExcludeWait=true` を追加します。これにより、`statusReason.resolution` が `wait` の一致が除外されます。`namedCapabilityIncludeWait=true` または `pooledCapabilityIncludeWait=true` は、その解決方法を持つ `restricted` のケイパビリティにも一致します。各フラグは対応するステータスフィルターとのみ機能し、両方を指定した場合は `ExcludeWait` が優先されます。

フィルターは互いに、またほかの一覧フィルターと組み合わせることができます。Swipelux はページングの前に適用するため、各ページには一致する顧客のみが含まれます。使用するには、API キーに `accounts:read` または `rails:read` が必要です。無効な値は `400 validation_error` を返します。

たとえば、銀行が名義型ケイパビリティを承認したものの、まだ ready の名義型口座を持っていない顧客を見つけるには、次のようにします。

```bash Filter customers awaiting a named account
curl --request GET \
  --get "${API_BASE}/v3/customers" \
  --data-urlencode "namedCapabilityStatus=ready" \
  --data-urlencode "hasReadyNamedAccount=false" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

### 未提出の書類がある顧客を見つける

ページ内のどの顧客に必須書類がまだ残っているかを確認するには、[`GET /v3/customers`](/api-reference/customers/get-v3-customers) に `include=documentRequirements` を渡します。`include=capabilities,documentRequirements` のように、ケイパビリティのサマリーと組み合わせることもできます。`documentRequirements` 展開には、API キーに `accounts:read` が必要です。

各顧客サマリーには、`documentRequirements` オブジェクトが含まれます。

```json Document requirement summary
{
  "documentRequirements": {
    "required": true,
    "count": 2
  }
}
```

- `count` は、同じく `action_required` であるタスク上の、`action_required` 状態の必須書類要件の数です。口座全体のタスクを含むすべてのタスクスコープを対象とし、ケイパビリティの ready 状態には依存しません。
- `count` が `0` より大きい場合、`required` は `true` になります。
- 代替手段のセットは 1 回だけカウントされ、すべての代替手段が書類を必要とする場合にのみカウントされます。

このサマリーは保守的です。任意の書類、条件付きで必須となる書類、および書類による手段と書類以外の手段が混在する代替手段は除外されます。顧客がホスト型検証で完了できる要件も除外されます。そのため、`required: false` は書類タスクが適用されないことの証明にはなりません。顧客の優先順位付けに使用し、収集すべき内容の正式なリストについては顧客のタスクを読み取ってください。展開を指定しない場合、レスポンスには `documentRequirements` が含まれません。

## 顧客の送金ボリュームを読み取る {#read-customer-transfer-volume}

顧客がどれだけの資金を動かしたかを表示するには、`GET /v3/customers/{customerId}/transfer-totals` を呼び出します。API キーには `customers:read` が必要です。不明な顧客の場合は `404 customer_not_found` が返されます。

```json Transfer totals
{
  "data": {
    "customerId": "cus_...",
    "received": { "amount": "1000.00", "currency": "USD" },
    "sent": { "amount": "25.00", "currency": "USD" }
  }
}
```

- 完了した送金のみが計上されます。保留中および失敗した送金は除外されます。
- `received` は、入金と他の顧客からのインバウンドのウォレット送金を合計します。`sent` は、出金とアウトバウンドのウォレット送金を合計します。
- USD、USDC、USDT は 1:1 で USD として計上されます。その他の通貨の金額は除外されます。
- 顧客自身のウォレット間の送金は除外されます。
- 各 `amount` は小数点以下 2 桁の 10 進数文字列で、対象となる送金がない場合は `"0.00"` になります。

合計は資金移動のボリュームであり、現在の残高ではありません。
