このページには、Swipelux API に対する日付付きの変更が一覧表示されます。各エントリには、影響を受けるバージョン、変更の種類、およびインテグレーターに求められる対応が記載されています。

既存のインテグレーションを以前のバージョンからアップグレードする場合は、[v3 への移行](/jp/api-reference/versioning/migrate-to-v3) を参照してください。

<Update label="2026-10-08" description="v3" tags={["追加","変更","修正"]}>

### 追加
- 受取人の送金先で、ブラジルでの BRL 支払い向けに `pix` タイプと `pix_safe` タイプを使用できるようになりました。Pix 送金先は Pix キーに支払います。Pix Safe 送金先は、名義人の CPF または CNPJ、銀行の ISPB コード、支店、口座番号で特定される銀行口座に支払います。どちらも顧客の ready 状態の Pix ケイパビリティ（`pix_pooled`）が必要で、その支払いは USDC で資金拠出され、開発者手数料はかかりません。[受取人](/jp/integration/recipients)と[資金を送る](/jp/integration/send-funds#pix-payouts)を参照してください。
- `GET /v3/customers/{customerId}/tasks/{taskId}` は、書類要件 ID を指定する `documentCandidatesFor` と、代替を持つ要件向けの `documentAlternativeKey` を受け付けるようになりました。指定すると、レスポンスの `data.documentCandidates` に、顧客がすでにアップロードした書類のうちその要件に回答できるものが、`missingMetadata` や `conflictingMetadata` とともに一覧表示されます。ファイルを再度アップロードする代わりに、候補の `documentId` を不足している `documentMetadata` とともに送信してください。このクエリには `accounts:read` と `customers:read` が必要で、無効な選択では `400 validation_error` が返されます。

### 変更
- `GET /v3/webhooks/portal` は、1 時間で有効期限が切れるポータル URL を `Cache-Control: no-store` とともに返します。`webhooks:write` を持つ API キーを使用すると、ポータルにはエンドポイントの署名シークレットが表示され、エンドポイントの管理、配信の再試行、リプレイが可能です。`webhooks:read` のみの場合、ポータルには配信のみが表示されます。[Webhook](/jp/integration/webhooks)を参照してください。
- Citi（`citibank`）は法人顧客にのみ提供されます。すべての法人はプール型 Citi を引き続き利用でき、名義型 Citi は米国外で登録された法人にのみ提供されます。顧客に Citi が提供されない場合、サポート対象リストから Citi が除外され、Citi を指定すると `422 capability_institutions_unsupported` が返され、Citi のみが提供する方法は `disabled` として表示されます。`institutions` を指定しないリクエストでは、残りの銀行から選択されます。既存の申請と口座は変更されません。
- 名義型 CFSB（`cfsb`）のケイパビリティは、米国の顧客、つまり米国で登録された法人と米国に居住する個人にのみ提供されます。その他の顧客の場合、サポート対象リストから名義型 CFSB が除外され、指定すると `422 capability_institutions_unsupported` が返されます。`institutions` を指定しないリクエストでは、残りの銀行から選択されます。プール型 CFSB、国が不明な顧客、既存の申請は変更されません。
- Lead Bank（`lead_bank`）の名義型 ACH、Wire、SWIFT ケイパビリティは、法的形態と国に基づいて Lead Bank がオンボーディングできる顧客にのみ提供されます。その他の顧客の場合、サポート対象リストから `lead_bank` が除外され、指定すると `422 capability_institutions_unsupported` が返されます。Lead Bank がすでにオンボーディングした顧客と、未完了のリクエストですでに `lead_bank` を指定しているケイパビリティは、引き続き利用できます。既存の申請と口座は変更されません。
- 個人および実質的支配者に対する新しい本人確認書類のリクエストでは `constraints.identityMetadataRequired: true` を設定できるようになり、各ファイルの `documentMetadata` に ID 番号と発行国が必要になります。法人の住所証明書類と所有者の居住証明書類に対する新しいリクエストでは `constraints.maxIssueAgeDays: 90` を設定できるようになり、各ファイルに発行日が必要になります。既存のタスクは要件を維持するため、各タスクのリクエストで制約を確認してください。
- 受取人の送金先の `type` はオープンな列挙型になりました。このリファレンスの以前のバージョンではクローズドとして記載されていたため、未知のタイプを拒否または破棄するクライアントは更新してください。送金先のレスポンスと `destination.status_changed` イベントには `pix` と `pix_safe` が含まれる可能性があり、今後さらにタイプが追加されることがあります。
- 書類のみを求める対象セッションの確認リンクは、Swipelux がホストする書類アップロードページを開くようになりました。リンク自体は変更されず、その他のセッションでは引き続きホスト型の確認フローが開きます。
- 個人顧客と関係者である個人の `employment.occupation` は、最大 255 文字まで受け付けます。

### 修正
- 支払いの見積もりと送金のレスポンスでは、USDC または USDT の送金元金額が小数点以下 6 桁で保持されます（例: `4009.71` ではなく `4009.711365`）。フィアットの金額は小数点以下 2 桁のままです。ステーブルコインの送金元金額が小数点以下 2 桁を超える支払いを作成または読み取っても、`500` が返されなくなりました。
- [`POST /v3/customers/{customerId}/capabilities/{capabilityId}/cancel`](/api-reference/capabilities/post-v3-customers-by-customer-id-capabilities-by-capability-id-cancel) のリファレンスが、実際の動作どおりにキャンセルを説明するようになりました。`ready` 状態のケイパビリティはキャンセルでき、`stablecoin_transfers` ケイパビリティはキャンセルできません。また、キャンセルで終了するのはそのケイパビリティのみで、その申請のステータス、タスク、承認は維持されます。

</Update>

<Update label="2026-10-05" description="v3" tags={["追加","変更","修正"]}>

### 追加
- `GET /v3/customers` は `include=documentRequirements` を受け付けるようになりました。指定すると、各顧客のサマリーに、ケイパビリティの準備状況とは関係なく、未提出の必須書類の件数が示されます。`include=capabilities,documentRequirements` のように組み合わせて指定できます。[顧客](/jp/integration/onboarding/customers)を参照してください。
- マーチャントパネルの Webhooks ページで、エンドポイントのメニューに **Replay missed events** が追加されました。エンドポイントが受信しなかった過去 13 日間のイベントを再送信し、同じイベントを 2 回送信することはありません。[Webhook](/jp/integration/webhooks#recover-deliveries)を参照してください。
- マーチャントパネルの **Settings** ページに **Compliance** セクションが追加されました。オーナーと管理者は、コンプライアンス用のメールアドレスを設定し、Swipelux が顧客に関する追加情報を求めた際にメールを受け取るかどうかを選択できます。
- マーチャントは、マーチャントパネルの KYB ページで、自社の KYB コンプライアンス依頼にその場で回答できるようになりました。

### 変更
- 銀行の受付が完了した後も、顧客および関係者の更新は `409 field_conflicts_with_completed_intake` を返さなくなりました。更新は保存され、新しい銀行申請はそれぞれ独自の要件に照らして最新のプロファイルを確認します。
- ケイパビリティの既存の銀行ルーティングを安全に更新できない場合、ケイパビリティのリクエストは `409 capability_route_header_conflict` を返します。再試行する前に Swipelux サポートにお問い合わせください。
- `institutions` にケイパビリティが提供していない銀行が指定された場合、`GET /v3/customers/{customerId}/capabilities/{capabilityId}/tasks-preview` はケイパビリティのリクエストと同様に `422 capability_institutions_unsupported` を返します。
- サンドボックスでは、ACH、Wire、SWIFT のケイパビリティは JPMorgan Chase でのみ提供されます。`institutions` を省略したリクエストでは `jpmorgan` が選択され、他の銀行を指定すると `422 capability_institutions_unsupported` が返されます。本番環境のルーティングは変更されません。[サンドボックスでテストする](/jp/integration/sandbox)を参照してください。
- サンドボックスのケイパビリティのステータスを強制変更する際、シミュレートされたケースが要求されたステータスに到達できない場合は、`statusReason` 付きで `409 capability_status_blocked` が返されます。すでに適用済みの強制変更を繰り返すと、変更なしで `200` が返されます。[サンドボックスでテストする](/jp/integration/sandbox#test-capability-readiness)を参照してください。
- `POST /v3/sandbox/tasks/{taskId}/review` は、Operations または別のワークフローが所有するタスクに対して `409 task_not_sandbox_reviewable` を返します。`POST /v3/sandbox/tasks` のタスクと、Swipelux が収集するケイパビリティの受付タスクは引き続きレビューできます。[サンドボックスでテストする](/jp/integration/sandbox)を参照してください。
- 銀行で口座のプロビジョニングがまだ進行中の間に決済設定を変更すると、`PATCH /v3/customers/{customerId}/accounts/{accountId}` は `409 account_provisioning_unresolved` を返します。プロビジョニングが確定した後に再試行してください。[エラーと再試行](/integration/errors#account-provisioning-unresolved)を参照してください。
- `POST /v3/transfers` が `409 quote_execution_evidence_conflict` を返す場合があります。新しい見積もりを作成して実行してください。[エラーと再試行](/integration/errors)を参照してください。
- マーチャントパネルの **Pay out** ドロワーでは、送金先の詳細がすべて表示され、口座番号とウォレットアドレスはトグルでマスクされ、支払い方法ごとに到着予定時間が表示されます。
- マーチャントパネルでは、銀行口座が顧客の **Payment access** タブに統合され、各銀行名を示すタスクカードが表示されます。**Documents** タブは **Profile** に移動しました。
- マーチャントパネルでの名前付き銀行口座の開設は 1 ステップになり、各銀行の通貨、方法、オンボーディング期間が一覧表示されます。[口座](/jp/integration/accounts)を参照してください。
- 審査のために保留されている銀行口座は、マーチャントパネルで **On hold** と表示され、口座 ID と **Contact support** アクションが表示されます。
- Swipelux が申請の提出を準備中で審査が行われていない間、`pending` のケイパビリティは `review_in_progress` ではなく `statusReason.code: preparing_submission` を報告するようになりました。どちらのコードも `resolution: wait` を使用します。両者の間で切り替わってもステータスは `pending` のままなので、`capability.status_changed` イベントは送信されません。既存のケイパビリティは、次回の再評価時に新しいコードを取得します。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements#continue-when-the-capability-is-ready)を参照してください。
- マーチャントパネルの顧客の **Payment access** タブにある **Shared methods** テーブルは、ケイパビリティが `preparing_submission` を報告する共有メソッドについて、**In review** ではなく **In preparation** と表示します。
- ケイパビリティの `applications` リストには、ケイパビリティの読み取り（`GET /v3/customers/{customerId}/capabilities/{capabilityId}/applications` を含む）、ケイパビリティリクエストのレスポンス、`capability.status_changed` イベントで、現在の申請のみが表示されるようになりました。新しい申請に置き換えられた申請は引き続き `GET /v3/customers/{customerId}/applications` に表示され、`supersededByApplicationId` が後継の申請を示します。置き換えられた申請の未完了タスクは、引き続きケイパビリティの `openTaskIds` に含まれます。ケイパビリティのステータスと `openTaskIds` は変わらないため、この変更自体では webhook イベントは送信されません。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements#list-the-customers-applications)を参照してください。

### 修正
- 銀行の承認前に同じ発行済み口座に対して送信された 2 回目の `allowPending` リクエストは、`500` ではなく、`holder.accountId` で待機中の口座を示す `409` を返すようになりました。[銀行口座を発行する](/jp/integration/issue-bank-account)を参照してください。
- ケイパビリティをキャンセルすると、まだ銀行の承認待ちだった発行済み口座のリクエストが閉じられるようになったため、同じ銀行での後続のリクエストは新規に開始されます。
- 銀行ケースがすべて却下されたキャンセル済みケイパビリティを再リクエストすると、`canceled` からの `capability.status_changed` イベントが 1 件だけ発行されます。
- 以前の申請がアーカイブされた後に銀行を再リクエストすると、新しい申請が送信されるようになりました。
- 受取人の送金先は、対応するケイパビリティが `ready` になった時点で、`409 rail_not_ready` を返さずに追加できるようになりました。[受取人](/jp/integration/recipients)を参照してください。
- マーチャントパネルの Webhooks ページを初めて開く前に送信された Webhook イベントが保持されるようになったため、それらを新しいエンドポイントにリプレイできます。
- マーチャントパネルのタスクの期日はご自身のタイムゾーンで表示され、銀行の審査ドロワーでは未対応の項目がなくなると **All requirements submitted** が表示されます。

<Update label="2026-09-28" description="v3" tags={["追加","変更","修正"]}>

### 追加
- `POST /v3/quotes` は、暗号資産から法定通貨への支払い見積もりで承認済みの銀行ルートを選択するための任意の `institutionId` を受け付けるようになりました。自動ルーティングを維持する場合は省略してください。支払いに利用できない銀行を指定すると `422 bank_not_supported_for_customer` が返され、他の種類の見積もりで `institutionId` を送信すると `400 validation_error` が返されます。[資金を送る](/jp/integration/send-funds)を参照してください。
- `POST /v3/customers/{customerId}/accounts` での発行済み銀行口座のリクエストは、フォールバックなしで口座を 1 つの銀行に固定する `institution` と、その銀行での申請がまだ承認待ちの間もリクエストを保存する `allowPending: true` を受け付けます。`allowPending` には `institution` が必要です。保存されたリクエストは、対応する `applicationId` を返します。[銀行口座を発行する](/jp/integration/issue-bank-account)を参照してください。
- マーチャントパネルに、エンドポイントを管理するためのネイティブな **Webhooks** ページが追加されました。[Webhook](/jp/integration/webhooks)を参照してください。
- マーチャントパネルに、名前付き銀行口座、暗号資産入金、確認ステップを備えた **Pay in** ドロワーが追加されました。
- マーチャントパネルの **Pay out** フローでは、送金元の選択時にウォレット残高が表示され、**Max** 金額オプションが追加され、確認ステップが含まれるようになりました。
- マーチャントパネルの顧客プロファイルに **Recipients & destinations** タブが追加されました。
- タスク要件に短い `title` 見出しを含められるようになりました。ガイダンスは引き続きリクエストの `prompt` に含まれます。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements)を参照してください。

### 変更
- 共有（プール型）の Wire ルートでの Wire による pay-in の見積もりには、$20 以上が必要になりました。ルートの最小額を下回る見積もり、または送金手数料を賄えないほど少額の見積もりは、汎用的な見積もりエラーではなく `422 amount_not_deliverable` を返すようになりました。[資金を受け取る](/jp/integration/receive-funds)を参照してください。
- Webhook ポータルで、v3 のイベントタイプがリソースごとにグループ化され、各イベントのペイロードスキーマと例が表示されるようになりました。レガシーのイベントタイプは別の **Legacy** グループに表示され、非推奨としてマークされます。すでにそれらをサブスクライブしているエンドポイントは引き続き受信します。新しいサブスクリプションには v3 のイベントタイプを使用してください。[Webhook](/jp/integration/webhooks)を参照してください。
- サンドボックスでのトップアップで、`transfer.created` および `transfer.state_changed` の Webhook イベントが発行されるようになりました。[サンドボックスでテストする](/jp/integration/sandbox)を参照してください。
- 顧客がすでにアクティブな発行済み口座を持っている場合、`accountProvisioning` は `issued` を返すようになりました。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements)を参照してください。
- マーチャントパネルの銀行口座の詳細は、銀行ロゴ付きのドロワーで開きます。[口座](/jp/integration/accounts)を参照してください。
- マーチャントパネルでは、資金移動のラベルが **Pay in** と **Pay out** になり、ログイン状態が 6 時間維持され、ヘルプリクエストはメールで Swipelux サポートに送信されるようになりました。
- 直接送信を受け付ける受付タスクでは、顧客プロファイルまたはアップロード済みの書類によってすでに裏付けられている対象要件が、自動的に `in_review` に移行するようになりました。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements#reused-profile-evidence)を参照してください。

### 修正
- キャンセルされたケイパビリティの再リクエストが、置き換えられた申請レコードや古くなった要件が原因で失敗しなくなりました。
- 廃止された Fedwire ID で保存されたケイパビリティが、`500` を返さずに `wire` として読み取られるようになりました。

<Update label="2026-09-21" description="v3" tags={["追加","変更","削除","修正"]}>

### 追加
- `GET /v3/customers/{customerId}/applications` は、顧客の申請ケースを一覧表示し、各ケースに対してリクエストされたケイパビリティと、その承認が対象とするケイパビリティを示します。1 つの銀行での 1 件の承認で複数のケイパビリティを対象にできます。保持されている過去のケースは、`supersededByApplicationId` によって後続のケースを指します。この一覧はカーソルページネーションと `updatedAfter` をサポートします。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements)を参照してください。
- `POST /v3/customers/{customerId}/capabilities/{capabilityId}` のレスポンスには、ケースに基づくケイパビリティの場合に `selectedApplicationId` が含まれます。これは、リクエストが再利用した既存の申請ケース、またはリクエストによって開かれたケースを識別します。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements)を参照してください。
- `GET /v3/institutions` およびサポートされるケイパビリティの一覧で返される金融機関には、null 許容の `logoUrl` が含まれます。利用可能な場合は銀行のブランディングの表示に使用し、`null` の場合は金融機関名を代わりに表示してください。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements)を参照してください。
- USD の SWIFT 支払いが利用可能になりました。SWIFT 支払いには 100 USD 以上が必要です。マーチャントパネルで受取人の SWIFT 銀行指示を収集します。[資金を送る](/jp/integration/send-funds)を参照してください。
- 発行済み銀行口座は、名義付きの受取情報を使用して SWIFT で受け取れるようになりました。[銀行口座を発行する](/jp/integration/issue-bank-account)を参照してください。
- USDT が ACH および Wire の支払いの送金元としてサポートされるようになりました。[資金を送る](/jp/integration/send-funds)を参照してください。

- 見積もりと送金は、資金が移動する前にケイパビリティがサポートする方向を確認するようになりました。サポートされていない方向でケイパビリティを使用すると `422 capability_direction_unsupported` が返され、ウォレット間の移動には `stablecoin_transfers` ケイパビリティが必要です。[エラーと再試行](/integration/errors#capability-direction-unsupported)を参照してください。

### 削除
- マーチャントパネルでは新しい UAEFTS 口座の設定を提供しなくなりました。既存の UAEFTS 口座は引き続き取得できます。[口座](/jp/integration/accounts)を参照してください。

### 修正
- レビュー担当者が新しい書類提出欄を追加しても、RFI フォームの既存入力が保持され、再送信時に以前の回答が失われなくなりました。
- マーチャントパネルは、有効なリンクを破棄せず、利用可能なアクションからホスト型コンプライアンスセッションを再開します。

- マーチャントパネルで Payment Access をリクエストすると、以前のリクエストのタスクではなく、そのリクエストから返された受付タスクが開くようになりました。
- マーチャントパネルの KYB デモで、現在必要なフィールドが求められるようになりました。
- ソースウォレットを `destinationId` として再利用する見積もりは、プロバイダー処理を開始する前に、対処可能な `422 quote_direction_invalid` の詳細を返すようになりました。[見積もりと送金](/jp/integration/quotes-and-transfers)を参照してください。
- API は不正なクエリ文字列エンコーディングを暗黙に正規化せず、`400` エラーで拒否するようになりました。[エラーと再試行](/integration/errors)を参照してください。
- `POST /v3/customers/{customerId}/documents` は、空、multipart 以外、または不正な形式のリクエストボディを `400` エラーで拒否するようになりました。

### 追加
- OpenAPI 仕様に v3 Problem Details カタログを公開しました。これにより、インテグレーターはスキーマから直接エラー応答をマッピングできます。[エラー](/integration/errors)を参照してください。
- v3 の口座 webhook イベントに `customerId` を追加し、追加の読み取りなしに口座アクティビティを所有者の顧客に関連付けられるようにしました。[Webhook](/jp/integration/webhooks) を参照してください。
- マーチャントパネルで V3 個人プロファイルフィールドを全面的にカバーし、オンボーディング担当者が v3 API 経由で収集されたすべての KYC フィールドを確認・編集できるようになりました。[顧客のオンボーディング](/jp/integration/onboarding/customers) を参照してください。
- v3 の開発者向け移行ガイドを公開しました。[v3 への移行](/jp/api-reference/versioning/migrate-to-v3) を参照してください。

### 変更
- 顧客および口座の国コードは、書き込み時に割り当て済みの ISO 3166-1 alpha-2 値として検証されるようになりました。読み取りはレガシーの保存値を許容するため、既存のレコードは引き続き解決されます。[口座とウォレット](/jp/integration/accounts) を参照してください。
- USDC の提供は宛先ネットワークによってスコープが限定されるようになりました。これにより、見積もりと送金は宛先が実際にサポートするネットワーク上でのみ USDC を提供します。
- すべてのオンボーディングフローで Swipelux の利用規約が必須になりました。既存のセッションは引き続き再開できます。[顧客のオンボーディング](/jp/integration/onboarding/customers)を参照してください。
- `Capability.ready` は引き続き利用権限の承認を示します。口座発行の追跡には `accountProvisioning` を使用し、`not_applicable`、`not_started`、`in_progress`、`issued`、`failed` として追跡してください。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements)を参照してください。
- iPhone からの HEIC アップロードが本人確認および住所確認書類として受け入れられるようになりました。
- 未完了のタスクがまだ必要としている顧客または関係者のフィールドをクリアすると、再試行可能な競合ではなく、ブロックしている `taskId` と `fields` を含む `409 field_required_by_open_task` が返されるようになりました。これらのフィールドを変更する前に、タスクを完了またはキャンセルしてください。[エラーと再試行](/integration/errors#field-required-by-open-task)を参照してください。

### 修正
- 使用済みの見積もりを再実行すると、汎用エラーではなく `409 quote_execution_consumed` を返すようになりました。[見積もりと送金](/jp/integration/quotes-and-transfers) を参照してください。
- 大量の履歴結果に対する送金一覧の読み取りおよび見積もり金額の読み取りが `500` を返さなくなりました。
- 同時実行された KYC リダイレクトは `404` ではなくコンフリクトを返すようになり、再試行が正常に解決されるようになりました。ホスト型リダイレクトが途中でロールバックすることはなくなり、KYC リンクは引き続き再開できます。
- 個人顧客の関係者読み取りが `404` を返さなくなりました。
- 無効なウォレットフィールドを含む KYB 送信は提出前に拒否されるようになり、同期の失敗がマーチャントパネルで成功として報告されなくなりました。
- マーチャントパネルの要件タスクは、送信済みの回答を完了として表示し、利用規約アクションを個別に追跡し、重複するドキュメントテキストを削除し、開始済みの KYC セッションを完了まで保留状態に保ち、要件ビューを壊すことなく古いタスクを処理するようになりました。
- マーチャントパネルの検証リンク行に、すべての行で **Open** アクションが表示されるようになり、すべてのタスクリンクが要件ビューにレンダリングされるようになりました。
