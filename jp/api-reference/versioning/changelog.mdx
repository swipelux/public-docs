このページには、Swipelux API に対する日付付きの変更が一覧表示されます。各エントリには、影響を受けるバージョン、変更の種類、およびインテグレーターに求められる対応が記載されています。

既存のインテグレーションを以前のバージョンからアップグレードする場合は、[v3 への移行](/jp/api-reference/versioning/migrate-to-v3) を参照してください。

<Update label="2026-10-30" description="v3" tags={["追加","変更"]}>

### 追加 {#added}
- 認証済みリクエストには、API キーごと、統合事業者ごと、クライアント IP アドレスごとにレート制限が適用されます。制限を超えたリクエストは、`retryable: true` と、再試行までに待つ秒数を示す `Retry-After` ヘッダーを伴う `429 rate_limited` を返します。まだ承認されていない統合事業者には、より低い制限が適用されます。API リファレンスの認証済みの各操作には `429` レスポンスが記載されています。1 つの IP アドレスから認証の失敗が繰り返された場合も、制限を超えると `429` が返されます。そのアドレスから送信された有効な API キーも、制限が回復するまで同じレスポンスを受け取る場合があるため、`Retry-After` の待機時間の後に再試行してください。[エラーと再試行](/integration/errors#rate-limited) を参照してください。

### 変更 {#changed}
- Swipelux は、ドットのないキーなど、公開部分を持たない従来の API キーを無効化しました。これらのキーを使ったリクエストは `401 unauthorized` を返します。

</Update>

<Update label="2026-10-26" description="v3" tags={["追加","変更","修正"]}>

### 追加 {#added}
- マーチャントパネルの **Settings** > **Customer pages** で、オーナーと管理者が会社のロゴ（PNG、JPG、WebP、最大 512 KB）をアップロードし、スペースごとに `https://` の戻り先 URL を設定できるようになりました。ライブスペースでは、このロゴが顧客のホスト型利用規約ページの Swipelux ワードマークに置き換わります。スペースに戻り先 URL がある場合、完了した利用規約ページに **Return to the app** が表示されます。

### 変更 {#changed}
- ホスト型利用規約ページのデザインが新しくなりました。サンドボックスのジャーニーのすべてのページに **Sandbox** バッジが表示されます。
- KYB が必要なライブスペースでは、KYB が承認されるまでマーチャントパネルの **Customers**、**Balances**、**Transactions** がロックされます。ホームには本番稼働までの手順が表示され、顧客の **Bank accounts** セクションには銀行ごとに 1 行ずつ通貨とともに表示され、銀行が承認すると銀行口座の詳細が表示されます。
- ケイパビリティを提供する銀行がいずれも入金の見積もりを提供していない場合（Lead Bank（`lead_bank`）の `ach_named` と `wire_named` など）、入金の `POST /v3/quotes` は再試行可能な `503 rail_temporarily_unavailable` ではなく、`retryable: false` を伴う `422 capability_direction_unsupported` を返します。同じ `Idempotency-Key` で再試行すると、`422` が再生されます。
- `DELETE /v3/customers/{customerId}` は、お客様の事業者の KYB 顧客に対して、`retryable: false` を伴う `409 merchant_kyb_subject_archive_refused` を返します。まず Swipelux サポートに、KYB を別の顧客に移すよう依頼してください。

### 修正 {#fixed}
- ホスト型の確認が審査に入り、それがタスクの最後のオープン項目だった場合、ケイパビリティは `statusReason.code: information_in_review` を伴う `pending` になり、`action_required` だった申請は `in_review` になります。Swipelux はこれらの変更について `capability.status_changed` と `application.status_changed` を送信します。以前は、どちらも以前のステータスのままで、Swipelux は webhook を送信していませんでした。
- タスクの送信で、住所、商業登記、所有構造などのオブジェクト型の回答は、保存済みの値とマージされるのではなく置き換えられるため、新しい回答に含まれないフィールド（`state` や `streetLine2` など）は削除されます。顧客と関係者に対する `PATCH` リクエストは引き続きマージされます。
- 最初の webhook エンドポイント、ポータルセッション、またはイベントが存在する前でも、`GET /v3/webhooks` は `502 request_failed` ではなく、空の `data` 配列とともに `200` を返します。
- 保存済みのエラーレスポンスを再生する、同じ `Idempotency-Key` での再試行に、再試行自体のリクエスト ID が設定された `X-Request-Id` が含まれるようになりました。本文には最初のリクエストの `correlationId` が保持されます。
- `card` ケイパビリティをキャンセルした後に再度リクエストすると、`500` ではなく `retryable: false` を伴う `409 capability_not_reopenable` が返されます。

</Update>

<Update label="2026-10-19" description="v3" tags={["追加","変更","修正"]}>

### 追加 {#added}
- Swipelux が銀行に転送する書類リクエストには、銀行のファイルごとの上限が `request.constraints.maxSizeBytes` に含まれる場合があります。マーチャントパネルとホスト型情報リクエストページは、JPEG、PNG、WebP の写真を上限内に収まるよう縮小し、それでも上限を超えるファイルを拒否します。[ドキュメントをアップロードする](/jp/integration/onboarding/capabilities-and-requirements#upload-documents) を参照してください。
- KYB が必要なライブスペースで、Swipelux がお客様の事業者確認（KYB）に関するオープン中のリクエストを持っている場合、マーチャントパネルはブラウザタブで初めて読み込んだときに KYB ページを開きます。ヘッダーの **Action needed** ボタンからも移動できます。

### 変更 {#changed}
- キャンセルされた銀行ケイパビリティを再度リクエストすると、リクエストが新しい申請を開いた場合は `201`、顧客がすでに持つ申請に参加した場合は `200` を返します。[ケイパビリティとタスク](/jp/integration/onboarding/capabilities-and-requirements#shared-applications-per-bank) を参照してください。
- `/financialProfile/accountPurposes` を求める新しいプール型 intake タスクは、`/financialProfile/accountPurposeDescription` も求めます。説明が必要なのは目的に `other` が含まれる場合のみで、説明がない場合、送信はそのポインターに対して `400 validation_error` を返します。マーチャントパネルは、**Something else** が選択されている間のみ説明フィールドを表示します。
- 個人顧客向けの名義型 JPMorgan Chase（`jpmorgan`）ケイパビリティには `employment.occupation` が必要です。職業のない雇用に関する回答は `400 validation_error` を返します。まだ銀行に送信されていない申請にはこの要件が適用されます。オープン中の intake タスクには要件が追加され、完了済みの intake にはフォローアップタスクが作成されます。プール型ケイパビリティと他の銀行は変更されません。
- `GET /v3/customers` は、居住地住所に国がない場合、個人の居住国を `country` として返します。`country` フィルターは同じ値に一致します。[顧客](/jp/integration/onboarding/customers) を参照してください。
- `POST /v3/sandbox/tasks/{taskId}/review` は、オープン中のすべての送信ラウンドと、審査待ちの再利用された証拠にわたって、タスク上の未決定の回答をすべて判定します。[サンドボックステスト](/jp/integration/sandbox#test-an-open-task) を参照してください。
- ホスト型情報リクエストページには、ステータスの概要が 1 つだけ表示され、リクエストされた各修正は対応する項目の横に表示されます。
- マーチャントパネルは、宣言を **Terms of Service** の下ではなくリクエストされた項目とともに一覧表示し、支払いの銀行送金先を **Destination Account** と表示し、保留中の支払いを **Processing** として表示します。

### 修正 {#fixed}
- 残りのタスク回答がすべて承認済みまたは審査中であるケイパビリティ（Swipelux が顧客の既存のプロファイルと書類から入力した回答を含む）は、`tasks_due` を伴う `restricted` のままではなく、`statusReason.code: information_in_review` を伴う `pending` を返すようになりました。[ケイパビリティとタスク](/jp/integration/onboarding/capabilities-and-requirements#continue-when-the-capability-is-ready) を参照してください。
- 承認済みの申請がケイパビリティをカバーしているもののリクエストはしていない銀行での `allowPending` 口座リクエストは、`500` ではなく `reason: no_ready_route` を伴う `409 capability_not_ready` を返します。ケイパビリティが `ready` になると、同じリクエストは成功します。[銀行口座を発行する](/jp/integration/issue-bank-account#save-the-request-before-bank-approval) を参照してください。
- 銀行が却下した Lead Bank（`lead_bank`）の申請は、`in_review` のままではなく `rejected` になります。
- Swipelux は、最初の intake タスクの後にリクエストされた資金源の書類など、フォローアップ intake タスクの回答を審査するようになりました。これにより、その申請は `requested` のままではなく銀行に送信されます。
- 利用規約セッションがまだ開いている間に Swipelux が intake タスクのすべての回答を承認した場合、またはお客様が `POST /v3/sandbox/tasks/{taskId}/review` で承認した場合でも、審査が `409 kyc_process_conflict` で失敗しなくなりました。顧客が利用規約に同意すると、タスクは `satisfied`、ケイパビリティは `ready` になります。このような審査の後にキャンセルされた `ach_named` または `wire_named` ケイパビリティを再度リクエストしても成功します。
- タスクの送信で、`documentMetadata[].issuedOn` は送信の UTC 日付の 1 日後までの日付を受け付けるため、UTC より進んだタイムゾーンで本日発行された書類が受け付けられます。`maxIssueAgeDays` は引き続き UTC 日付から数えます。
- マーチャントパネルで新しい受取人を追加するとき、口座フォームには ready 状態の支払い方法のみが表示されます。
- マーチャントパネルは、フォームの残りを送信している間も送信済みのフォームセクションのステータスを保持し、顧客のタイムゾーンでの本日を書類の発行日として受け付け、KYB の回答を送信した後に空のリクエストが一瞬表示されることがなくなり、ウェブサイトと書類の回答を切り替えてもアップロード済みのファイルを保持します。
- マーチャントパネルの取引詳細パネルが切れた状態で開かなくなりました。

</Update>

<Update label="2026-10-12" description="v3" tags={["追加","変更","修正"]}>

### 追加 {#added}
- `POST /v3/customers/{customerId}/tasks/{taskId}/submissions` は、省略可能な `allowPartial: true` を受け付けます。この場合、Swipelux は有効な回答を保存し、`refusedAnswers` とともに `201` を返します。各エントリには `requirementId`、`code`、`pointer`、`message` が含まれます。`code` は `invalid`、`absence_conflicts_with_profile`、`invalid_document_reference`、`depends_on_refused_answer` のいずれかで、今後コードが追加される場合があります。保持できる回答がない場合、レスポンスは `400 validation_error` となり、何も保存されません。`allowPartial` は、送信で回答が必要な要件を変更せず、指定しない場合の動作も変わりません。[`allowPartial` で有効な回答を保持する](/jp/integration/onboarding/capabilities-and-requirements#keep-valid-answers-with-allowpartial) を参照してください。
- `POST /v3/customers/{customerId}/tasks/{taskId}/withdrawals` は、審査待ちの送信を取り下げ、顧客が修正できるようにします。`Idempotency-Key` が必要です。送信の回答は `action_required` に戻り、次の送信で新しい `remediationRound` が始まります。審査待ちの送信がちょうど 1 件ではない場合、またはタスクの期限が過ぎている場合、取り下げは `409 task_not_in_review` を返します。銀行がタスクを直接審査する場合、または Swipelux がすでに送信を審査に回している場合は `409 submission_already_forwarded` を返します。[審査待ちの送信を取り下げる](/jp/integration/onboarding/capabilities-and-requirements#withdraw-a-submission-awaiting-review) を参照してください。
- ドキュメントリソースに `contentSha256` が含まれるようになりました。これは保存されたファイルの SHA-256 ダイジェストで、`sha256:` の後に小文字の 16 進ダイジェストが続く形式です。ダイジェストの記録開始前に保存されたドキュメントでは `null` になります。ファイルのダイジェストと比較することで、すでに保存されているファイルの再アップロードを検出できます。[ドキュメントをアップロードする](/jp/integration/onboarding/capabilities-and-requirements#upload-documents) を参照してください。
- マーチャントパネルの受取人フォームでは、顧客の対応するアクセスが ready になると SPEI（メキシコ、MXN）、Pix、Pix Safe の口座を追加でき、**Pay out** ドロワーから SPEI 口座に支払えるようになりました。[受取人と送金先](/jp/integration/recipients) を参照してください。
- 公開タスクフォームで、審査中の人物に **Edit details** が表示されるようになりました。これにより人物を審査から戻し、再追加するのではなく詳細を修正できます。その人物の回答と書類は再入力する必要があります。

### 変更 {#changed}
- 送信の `outcome` に、審査の判定前に顧客が取り下げた送信を表す `withdrawn` が追加されました。不明な結果を拒否するクライアントを更新してください。
- 承認済みまたは審査中の書類が、別の銀行の申請にある一致する書類リクエストにも回答するようになりました。銀行ごとにリクエストの表現が異なる場合も同様です。顧客が同じファイルをアップロードする回数が減ります。90 日を超える住所証明など、リクエストの `maxIssueAgeDays` より古いファイルは再利用されません。
- 法定通貨の受取人送金先には、その方法の `ready` 状態のケイパビリティが必要になりました。ケイパビリティ導入前に銀行アクセスが設定された顧客も対象です。それ以外の場合、`POST /v3/customers/{customerId}/recipients/{recipientId}/destinations` は `409 rail_not_ready` を返します。ウォレットの送金先は変更されません。[受取人と送金先](/jp/integration/recipients) を参照してください。
- 顧客がケイパビリティを持たない方法で銀行口座を発行すると `409 capability_not_ready` が返されます。リクエストで `institution` を省略した場合の理由は `route_selection_required`、銀行を指定した場合は `no_ready_route` です。どちらも、口座を発行できるケイパビリティを `capabilities` に一覧表示します。`ambiguous_route_scope` と `rail_not_ready` の理由は返されなくなりました。[銀行口座を発行する](/jp/integration/issue-bank-account) を参照してください。
- 以前のルートを続行できなくなった `Idempotency-Key` で再試行された見積もりまたは口座のリクエストは、`retryable: true` を伴う `409 capability_not_ready` を返します。新しい `Idempotency-Key` で再送してください。
- 公開タスクフォームは、一部の回答が拒否された場合も有効な回答を保持し、拒否された各回答の横に理由を表示します。審査中の人物はステータスとともに一覧に残ります。
- 公開タスクフォームでは、個人の本人確認をフォーム内で実行します。マーチャントパネルでは、ホスト型の確認を提供する個人のタスクはその確認のみにリンクし、**Documents** セクションでは個人顧客向けのアップロードが表示されなくなりました。
- マーチャントパネルの顧客の **Profile** タブはセクションごとに保存され、フィールドをクリアすると実際にクリアされるようになりました。

### 修正 {#fixed}
- 銀行が拒否した Lead Bank の支払い見積もりは `500` ではなく `400 quote_failed` を返し、銀行が応答できない見積もりは再試行可能な `503 quote_temporarily_unavailable` を返します。[見積もりと送金](/jp/integration/quotes-and-transfers) を参照してください。
- 別の銀行が同じ住所を審査している間でも、Lead Bank の所有者タスクの送信が `500` を返さなくなりました。
- 個人の場合、本人確認の完了後にリクエストされた書類では、新しいホスト型の確認セッションが開きます。
- ブラウザがページを翻訳してもマーチャントパネルのフォームが動作し続け、Swipelux のリリース後に顧客タブが復旧するようになりました。
- KYB フォームのフィールドは、フィールドから離れた後にのみエラーを表示します。

</Update>

<Update label="2026-10-08" description="v3" tags={["追加","変更","修正"]}>

### 追加
- 受取人の送金先で、ブラジルでの BRL 支払い向けに `pix` タイプと `pix_safe` タイプを使用できるようになりました。Pix 送金先は Pix キーに支払います。Pix Safe 送金先は、名義人の CPF または CNPJ、銀行の ISPB コード、支店、口座番号で特定される銀行口座に支払います。どちらも顧客の ready 状態の Pix ケイパビリティ（`pix_pooled`）が必要で、その支払いは USDC で資金拠出され、開発者手数料はかかりません。[受取人](/jp/integration/recipients)と[資金を送る](/jp/integration/send-funds#pix-payouts)を参照してください。
- `GET /v3/customers/{customerId}/tasks/{taskId}` は、書類要件 ID を指定する `documentCandidatesFor` と、代替を持つ要件向けの `documentAlternativeKey` を受け付けるようになりました。指定すると、レスポンスの `data.documentCandidates` に、顧客がすでにアップロードした書類のうちその要件に回答できるものが、`missingMetadata` や `conflictingMetadata` とともに一覧表示されます。ファイルを再度アップロードする代わりに、候補の `documentId` を不足している `documentMetadata` とともに送信してください。このクエリには `accounts:read` と `customers:read` が必要で、無効な選択では `400 validation_error` が返されます。

### 変更
- `GET /v3/webhooks/portal` は、1 時間で有効期限が切れるポータル URL を `Cache-Control: no-store` とともに返します。`webhooks:write` を持つ API キーを使用すると、ポータルにはエンドポイントの署名シークレットが表示され、エンドポイントの管理、配信の再試行、リプレイが可能です。`webhooks:read` のみの場合、ポータルには配信のみが表示されます。[Webhook](/jp/integration/webhooks)を参照してください。
- Citi（`citibank`）は法人顧客にのみ提供されます。すべての法人はプール型 Citi を引き続き利用でき、名義型 Citi は米国外で登録された法人にのみ提供されます。顧客に Citi が提供されない場合、サポート対象リストから Citi が除外され、Citi を指定すると `422 capability_institutions_unsupported` が返され、Citi のみが提供する方法は `disabled` として表示されます。`institutions` を指定しないリクエストでは、残りの銀行から選択されます。既存の申請と口座は変更されません。
- 名義型 CFSB（`cfsb`）のケイパビリティは、米国の顧客、つまり米国で登録された法人と米国に居住する個人にのみ提供されます。その他の顧客の場合、サポート対象リストから名義型 CFSB が除外され、指定すると `422 capability_institutions_unsupported` が返されます。`institutions` を指定しないリクエストでは、残りの銀行から選択されます。プール型 CFSB、国が不明な顧客、既存の申請は変更されません。
- Lead Bank（`lead_bank`）の名義型 ACH、Wire、SWIFT ケイパビリティは、法的形態と国に基づいて Lead Bank がオンボーディングできる顧客にのみ提供されます。その他の顧客の場合、サポート対象リストから `lead_bank` が除外され、指定すると `422 capability_institutions_unsupported` が返されます。Lead Bank がすでにオンボーディングした顧客と、未完了のリクエストですでに `lead_bank` を指定しているケイパビリティは、引き続き利用できます。既存の申請と口座は変更されません。
- ライブモードでは、`institutions` を省略した `ach_named` または `wire_named` のケイパビリティリクエストは、Lead Bank が新規顧客を受け付けていて、その顧客をオンボーディングできる場合、デフォルトで Lead Bank（`lead_bank`）を使用するようになりました。条件は、プロファイルに少なくとも 1 つの国が記載されていて Lead Bank がそのすべての国を受け付けること、法人のプロファイルに Lead Bank が受け付ける法人形態が記載されていること、そして顧客が他の銀行で名義型・プール型を問わず `ready` 状態の申請を持っていないことです。その他の顧客は、`ach_named` でこれまでどおり、デフォルトで JPMorgan Chase（`jpmorgan`）を使用します。`wire_named` には以前はデフォルトの銀行がありませんでした。顧客がすでに持っている現在の申請は引き続き優先されます。`GET /v3/customers/{customerId}/capabilities/supported` の `isDefault` は顧客ごとに Lead Bank のルールを適用するため、マークされる銀行は顧客によって異なり、時間とともに変わる場合があります。[ケイパビリティとタスク](/jp/integration/onboarding/capabilities-and-requirements#discover-supported-capabilities) を参照してください。
- `institutions` を省略した `wire_pooled` リクエストは、デフォルトで JPMorgan Chase（`jpmorgan`）を使用するようになりました。サポート対象リストはこの銀行を `isDefault` でマークします。以前は CFSB（`cfsb`）が選択されていました。
- RTP はプール型のみになりました。新しいリクエストに `rtp_named` を提供する銀行はないため、サポート対象リストでは `disabled` として表示されます。`rtp_named` を保有していない顧客の場合、銀行を指定したケイパビリティリクエストまたはタスクのプレビューでは `422 capability_institutions_unsupported` が返され、`institutions` を指定しないものでは `422 capability_variant_unavailable` が返されます。プール型 RTP（`rtp_pooled`）は Citi で提供されるため、リクエストできるのは法人顧客のみです。
- 個人および実質的支配者に対する新しい本人確認書類のリクエストでは `constraints.identityMetadataRequired: true` を設定できるようになり、各ファイルの `documentMetadata` に ID 番号と発行国が必要になります。法人の住所証明書類と所有者の居住証明書類に対する新しいリクエストでは `constraints.maxIssueAgeDays: 90` を設定できるようになり、各ファイルに発行日が必要になります。既存のタスクは要件を維持するため、各タスクのリクエストで制約を確認してください。
- `profilePointer` が `/business/registration` である法人登記リクエストへのタスクの回答には、管轄国、登記番号、提出日より前の設立日をすべてそろえて含める必要があります。このルールはリクエストの `valueSchema` で公開されており、一部のみの回答では `400 validation_error` が返されます。
- ホスト型の確認の後、住所や納税者番号などの構造化された値を求めるプロファイル要件へのホスト型の回答は、直接の回答と同じスキーマおよび制約のチェックに合格した場合にのみ Swipelux に受け付けられます。合格しない場合、その要件は未完了のままとなるため、その値を `POST /v3/customers/{customerId}/tasks/{taskId}/submissions` で送信してください。この理由で Swipelux が `action_required` に戻した要件には、`reviewFeedback.code: hosted_profile_direct_submission_required` が含まれます。すでに `satisfied` であるタスクは、そのステータスを維持します。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements#hosted-actions)を参照してください。
- ホスト型の確認によって却下されたタスクは、その確認の判定が後から覆された場合に `rejected` から移行することがあります。その場合、タスクは `satisfied` になるか、新しい `revision` で `action_required` になり、新しい判定で回答されない要件が再び未完了になります。それらの要件に対する以前の送信は `rejected` のままなので、それらの回答を再度送信してください。[v3 への移行](/jp/api-reference/versioning/migrate-to-v3#1-4-the-task-loop)を参照してください。
- 受取人の送金先の `type` はオープンな列挙型になりました。このリファレンスの以前のバージョンではクローズドとして記載されていたため、未知のタイプを拒否または破棄するクライアントは更新してください。送金先のレスポンスと `destination.status_changed` イベントには `pix` と `pix_safe` が含まれる可能性があり、今後さらにタイプが追加されることがあります。
- 受取人の作成リクエストと更新リクエストは、ネストされた `address` を含め、定義されていないフィールドを `400 validation_error` を返さずに無視するようになりました。作成リクエストで、もう一方の受取人タイプの名前フィールドまたは業種フィールドを指定した場合は引き続き `400` が返され、`PATCH /v3/customers/{customerId}/recipients/{recipientId}` での `type` と `externalId` も同様です。認識できるフィールドを 1 つも含まない `PATCH` では、`200` ではなく `400 validation_error` が返されます。
- 書類のみを求める対象セッションの確認リンクは、Swipelux がホストする書類アップロードページを開くようになりました。リンク自体は変更されず、その他のセッションでは引き続きホスト型の確認フローが開きます。
- 個人顧客と関係者である個人の `employment.occupation` は、最大 255 文字まで受け付けます。
- プロフィールの値またはタスクの回答に、RFI、顧客リクエスト、送金追跡リンクなどの Swipelux フォームリンクが含まれている場合、`POST /v3/customers`, `PATCH /v3/customers/{customerId}`, `POST /v3/customers/{customerId}/related-parties`, `PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}`、`POST /v3/customers/{customerId}/tasks/{taskId}/submissions` は `400 validation_error` を返します。これは `externalId` と `metadata` には適用されません。拒否された各値は `code: public_form_link` とその JSON Pointer とともに `errors[]` に表示され、レスポンスがリンクを繰り返すことはありません。代わりに情報そのものを送信してください。[エラーと再試行](/integration/errors#validation-error)を参照してください。

### 追加
- 顧客スコープのホスト型本人確認および利用規約セッションに、信頼すべき `action` オブジェクトが追加されました。`available` または `unavailable` の種類に従ってください。利用可能なアクションでは、トップレベルの `url` と `expiresAt` は互換性のためのミラーとして残ります。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements)を参照してください。

### 変更
- カードおよび Apple Pay 向けのマーチャントパネルの **First pay-in** ガイドで、顧客に Polygon ウォレットが必要になりました。ガイドを開始する前にウォレットを作成してください。[口座](/jp/integration/accounts)を参照してください。

- Faster Payments の新しいケイパビリティ、発行口座、見積もりリクエストは利用できません。既存の口座、見積もり、送金は引き続き取得できます。[口座](/jp/integration/accounts)を参照してください。
- KYB の最初のページでは代表者の生年月日を収集しなくなりました。株主の生年月日は引き続き別の要件です。[KYB ワークフロー](/jp/knowledge-base/business-onboarding/kyb-workflow)を参照してください。

### 変更
- 顧客および口座の国コードは、書き込み時に割り当て済みの ISO 3166-1 alpha-2 値として検証されるようになりました。読み取りはレガシーの保存値を許容するため、既存のレコードは引き続き解決されます。[口座とウォレット](/jp/integration/accounts) を参照してください。
- USDC の提供は宛先ネットワークによってスコープが限定されるようになりました。これにより、見積もりと送金は宛先が実際にサポートするネットワーク上でのみ USDC を提供します。
- すべてのオンボーディングフローで Swipelux の利用規約が必須になりました。既存のセッションは引き続き再開できます。[顧客のオンボーディング](/jp/integration/onboarding/customers)を参照してください。
- `Capability.ready` は引き続き利用権限の承認を示します。口座発行の追跡には `accountProvisioning` を使用し、`not_applicable`、`not_started`、`in_progress`、`issued`、`failed` として追跡してください。[ケイパビリティと要件](/jp/integration/onboarding/capabilities-and-requirements)を参照してください。
- iPhone からの HEIC アップロードが本人確認および住所確認書類として受け入れられるようになりました。
- 未完了のタスクがまだ必要としている顧客または関係者のフィールドをクリアすると、再試行可能な競合ではなく、ブロックしている `taskId` と `fields` を含む `409 field_required_by_open_task` が返されるようになりました。これらのフィールドを変更する前に、タスクを完了またはキャンセルしてください。[エラーと再試行](/integration/errors#field-required-by-open-task)を参照してください。

### 修正
- 使用済みの見積もりを再実行すると、汎用エラーではなく `409 quote_execution_consumed` を返すようになりました。[見積もりと送金](/jp/integration/quotes-and-transfers) を参照してください。
- 大量の履歴結果に対する送金一覧の読み取りおよび見積もり金額の読み取りが `500` を返さなくなりました。
- 同時実行された KYC リダイレクトは `404` ではなくコンフリクトを返すようになり、再試行が正常に解決されるようになりました。ホスト型リダイレクトが途中でロールバックすることはなくなり、KYC リンクは引き続き再開できます。
- 個人顧客の関係者読み取りが `404` を返さなくなりました。
- 無効なウォレットフィールドを含む KYB 送信は提出前に拒否されるようになり、同期の失敗がマーチャントパネルで成功として報告されなくなりました。

- マーチャントパネルの検証リンク行に、すべての行で **Open** アクションが表示されるようになり、すべてのタスクリンクが要件ビューにレンダリングされるようになりました。
