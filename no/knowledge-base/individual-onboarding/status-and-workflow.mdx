## Verifiseringsstatus og workflow

Den policyvendte KYC-reisen beveger seg fra informasjonsinnsamling gjennom gjennomgang til en godkjennings- eller avvisningsbeslutning. Gjeldende API-ressurser eksponerer separate livssykluser for capability, application, oppgave og innsending.

<Warning>
  Merkelapper for policygjennomgang og tidsestimater definerer ikke API-atferd. Ikke
  implementer en tilstandsmaskin fra merkelappene nedenfor.
</Warning>

## Policyvendte gjennomgangskonsepter

Disse policyvendte gjennomgangskonseptene beskriver onboarding-reisen. De er ikke gjeldende API-enums, webhook-verdier eller garanterte overganger.

| Policy-merkelapp | Betydning |
| --- | --- |
| `not_started` | Kunden finnes, men KYC-arbeidet har ikke startet |
| `incomplete` | KYC-arbeidet er startet, men nødvendig informasjon mangler |
| `pending_verification` | Gjennomgangen venter på kundens fullføring |
| `under_review` | Innsendt informasjon eller dokumenter gjennomgås |
| `approved` | Policygjennomgangen godkjente kunden for gjeldende flyter |
| `rejected` | Policygjennomgangen avviste kunden |

Bruk disse merkelappene kun når du diskuterer policyreisen. Ikke send dem som gjeldende statusverdier med mindre et gjeldende generert skjema eksplisitt ber om samme verdi i sin egen kontekst.

## Standard KYC-gjennomgangsflyt

1. Opprett individkunden.
2. Oppdag og be om en kvalifisert capability.
3. Les detaljene i den gjeldende oppgaven.
4. Send kunden til en førsteparts hosted verifiseringssesjon eller send inn de komplette oppgavesvarene som oppgaven ber om.
5. La gjennomgangen kjøre mens gjeldende ressurser rapporterer sine egne gjennomgangstilstander.
6. Hent gjeldende ressurser på nytt for å avgjøre om mer handling kreves eller capability-en er ready, restricted, rejected eller canceled.

Policyreisen kan beskrive dette som not started, pending verification, under review og deretter approved eller rejected. Disse begrepene definerer ikke API-overgangssekvensen.

## Enhanced KYC-gjennomgangsflyt

1. Fullfør det forespurte standard identitets- og liveness-arbeidet.
2. Les den siste oppgaven når enhanced-gjennomgangen ber om ytterligere informasjon.
3. Oppgi forespurt bostedsbevis, bevis for midler eller annet bevis via den gjeldende hosted sesjonen eller oppgaveinnsendingen.
4. Last opp dokumenter kun når den gjeldende oppgaven ber om dem.
5. Fortsett å overvåke gjeldende ressurser under manuell gjennomgang.
6. Stopp eller fortsett basert på gjeldende capability-, application-, oppgave- og innsendingstilstander.

Compliance-teamet kan også koordinere en enhanced-gjennomgang gjennom kundens registrerte e-postadresse.

## Vanlige avvisningsgrunner

| Grunn | Løsning |
| --- | --- |
| Dokument ikke lesbart | Oppgi et klart bilde med høy oppløsning |
| Dokument utløpt | Oppgi et gyldig, ikke-utløpt identitetsdokument |
| Ansikt matcher ikke | Sørg for at selfien tydelig matcher bildet på identitetsdokumentet |
| Ufullstendig informasjon | Oppgi hvert element forespurt av gjeldende oppgave |
| Mistenkelig aktivitet | Kontakt support for manuell gjennomgang |

## Verifiseringstidslinje

| Stadium | Typisk varighet |
| --- | --- |
| Dokumentopplasting | Umiddelbart |
| Automatiserte kontroller | 1-3 minutter |
| Standard-gjennomgang | 1-24 timer |
| Enhanced-gjennomgang | 1-3 virkedager |

Disse varighetene er typiske policy-estimater, ikke garantert API-atferd.

## Gjeldende API-tilstandsordforråd

De gjeldende ressursene bruker separate lukkede ordforråd:

- **Capability-status:** `pending`, `ready`, `restricted`, `rejected`, `canceled`
- **Application-status:** `requested`, `in_review`, `action_required`, `ready`, `rejected`, `disabled`, `canceled`
- **Oppgavestatus:** `action_required`, `in_review`, `satisfied`, `rejected`, `canceled`
- **Innsendingsutfall:** `in_review`, `accepted`, `changes_requested`, `rejected`

Ikke slå disse ordforrådene sammen til én verifiseringsstatus.

## Hendelser og gjeldende tilstand

Bruk gjeldende dokumenterte [Webhooks](/no/integration/webhooks) som endringsvarslinger, og hent så de gjeldende kunde-, capability-, application- og oppgaveressursene på nytt. Hendelser erstatter ikke autoritative ressursavlesninger, og ingen policyvendt merkelapp innebærer en bestemt hendelse.

Se [Capabilities og oppgaver](/no/integration/onboarding/capabilities-and-requirements#complete-current-tasks) for den gjeldende handlingsløkken.
