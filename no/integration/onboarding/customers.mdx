---
title: "Kunder"
description: "Opprett individ- eller virksomhetskunden i Swipelux som eier capabilities, wallets, bankkontoer og overføringer, og knytt til riktig onboardingprofil."
---

Opprett kunden før du bygger en pay-in, payout eller utstedt bankkonto. Capabilities, kontoer og overføringer er avgrenset til denne kunden. Bruk `externalId` som stabil kobling til den tilhørende oppføringen i ditt system.

```bash Environment variables
export API_BASE='https://platform.swipelux.com'
export SWIPELUX_API_KEY='replace-with-your-api-key'
```

## Individkunder {#individual-customers}

En individkunde krever kun `type`. Inkluder profilfelter du allerede kjenner, og legg til flere kun når gjeldende capability eller oppgave trenger dem.

Opprett kunden med [`POST /v3/customers`](/api-reference/customers/post-v3-customers):

```bash Create individual customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-user-123" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "individual",
  "externalId": "user_123",
  "individual": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Lagre den returnerte `data.id` som `CUSTOMER_ID`. Se [Individonboarding](/no/knowledge-base/individual-onboarding/overview) for policykontekst.

## Virksomhetskunder {#business-customers}

En virksomhet krever `business.legalName`. Opprett virksomheten med samme operasjon:

```bash Create business customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-company-456" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "business",
  "externalId": "company_456",
  "business": {
    "legalName": "Acme Payments SAS"
  }
}
JSON
```

Lagre den returnerte `data.id` som `CUSTOMER_ID`. Se [Virksomhetsonboarding](/no/knowledge-base/business-onboarding/overview) for policy- og dokumentkontekst.

## Legg til nærstående parter for virksomheten {#add-business-related-parties}

Legg til styremedlemmer, eiere og andre deltakere i virksomheten når de er kjent eller etterspurt. Dette eksempelet oppretter et styremedlem med [`POST /v3/customers/{customerId}/related-parties`](/api-reference/customers/post-v3-customers-by-customer-id-related-parties):

```bash Add related party
curl --request POST \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}/related-parties" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: related-party-director-001" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "partyType": "person",
  "roles": ["director"],
  "title": "Chief executive officer",
  "person": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Lagre den returnerte `data.id` som `RELATED_PARTY_ID`.

Hvis du må eksportere en kunde, bruker du [`POST /v3/customers/{customerId}/export`](/api-reference/customers/post-v3-customers-by-customer-id-export) og følger request-skjemaet. Formatet `json_basic_data` returnerer gjeldende offentlige v3-kunderessurs som et JSON-vedlegg; hvert kall beregner gjeldende data på nytt og utelater dokumenter og dokumentmetadata.

For et portabilitets-token-format sender du klient-ID-en til det mottakende KYC-prosjektet som `forClientId`, ikke Swipelux `customerId`. Bruk den returnerte `data.token` før `data.expiresAt`. Gjenbruk av samme `Idempotency-Key` og body spiller av det token-resultatet på nytt; bruk en ny nøkkel for å utstede et nytt token.

## Les klarhet fra capabilities

En kunde har ikke en verifiserings- eller klarhetsstatus i API-et. Les kunden med [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id) for gjeldende profildata, og bruk deretter capabilities og deres `openTaskIds` for å avgjøre hva kunden kan gjøre videre.

```bash Get customer
curl --request GET \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

### Finn kunder med utestående dokumenter

For å finne ut hvilke kunder på en side som fortsatt mangler obligatoriske dokumenter, sender du `include=documentRequirements` til [`GET /v3/customers`](/api-reference/customers/get-v3-customers). Du kan kombinere det med capability-sammendrag som `include=capabilities,documentRequirements`. API-nøkler trenger `accounts:read` for `documentRequirements`-utvidelsen.

Hvert kundesammendrag inneholder da et `documentRequirements`-objekt:

```json Document requirement summary
{
  "documentRequirements": {
    "required": true,
    "count": 2
  }
}
```

- `count` er antallet obligatoriske dokumentkrav i `action_required` på oppgaver som også er i `action_required`. Det dekker alle oppgaveomfang, inkludert kontoomfattende oppgaver, og avhenger ikke av capability-klarhet.
- `required` er `true` når `count` er større enn `0`.
- Et sett med alternativer telles én gang, og bare når hvert alternativ krever et dokument.

Sammendraget er konservativt. Det utelater valgfrie dokumenter, betinget obligatoriske dokumenter og alternativer som blander dokument- og ikke-dokumentruter. Det utelater også krav kunden kan fullføre gjennom hostet verifisering. Derfor beviser ikke `required: false` at ingen dokumentoppgave gjelder. Bruk det til å prioritere kunder, og les deretter oppgavene deres for den autoritative listen over hva som skal samles inn. Uten utvidelsen utelater svaret `documentRequirements`.

## Les kundens overføringsvolum {#read-customer-transfer-volume}

For å vise hvor mye penger en kunde har flyttet, kall `GET /v3/customers/{customerId}/transfer-totals`. API-nøkler trenger `customers:read`. En ukjent kunde returnerer `404 customer_not_found`.

```json Transfer totals
{
  "data": {
    "customerId": "cus_...",
    "received": { "amount": "1000.00", "currency": "USD" },
    "sent": { "amount": "25.00", "currency": "USD" }
  }
}
```

- Bare fullførte overføringer teller. Ventende og mislykkede overføringer er utelatt.
- `received` summerer pay-ins og innkommende lommebokoverføringer fra andre kunder. `sent` summerer payouts og utgående lommebokoverføringer.
- USD, USDC og USDT teller 1:1 som USD. Beløp i andre valutaer er utelatt.
- Overføringer mellom kundens egne lommebøker er utelatt.
- Hvert `amount` er en desimalstreng med to desimaler, og `"0.00"` når ingen overføringer kvalifiserer.

Totalene er bevegelsesvolum, ikke en gjeldende saldo.

Deretter, fortsett til [Capabilities og oppgaver](/no/integration/onboarding/capabilities-and-requirements) for å oppdage og aktivere produktutfallet du trenger.
