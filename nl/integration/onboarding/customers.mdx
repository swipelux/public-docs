Maak de klant aan voordat je een pay-in, uitbetaling of uitgegeven bankrekening bouwt. Capabilities, accounts en transfers zijn scoped aan die klant. Gebruik `externalId` als de stabiele mapping naar het bijbehorende record in jouw systeem.

```bash Environment variables
export API_BASE='https://platform.swipelux.com'
export SWIPELUX_API_KEY='replace-with-your-api-key'
```

## Individuele klanten {#individual-customers}

Een individu vereist alleen `type`. Voeg profielvelden toe die je al kent en voeg er alleen meer toe wanneer de huidige capability of taak ze nodig heeft.

Maak de klant aan met [`POST /v3/customers`](/api-reference/customers/post-v3-customers):

```bash Create individual customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-user-123" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "individual",
  "externalId": "user_123",
  "individual": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Bewaar de geretourneerde `data.id` als `CUSTOMER_ID`. Zie [Individuele onboarding](/nl/knowledge-base/individual-onboarding/overview) voor beleidscontext.

## Zakelijke klanten {#business-customers}

Een bedrijf vereist `business.legalName`. Maak het bedrijf aan met dezelfde operation:

```bash Create business customer
curl --request POST \
  "${API_BASE}/v3/customers" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: customer-company-456" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "type": "business",
  "externalId": "company_456",
  "business": {
    "legalName": "Acme Payments SAS"
  }
}
JSON
```

Bewaar de geretourneerde `data.id` als `CUSTOMER_ID`. Zie [Zakelijke onboarding](/nl/knowledge-base/business-onboarding/overview) voor beleids- en documentcontext.

## Voeg zakelijke related parties toe {#add-business-related-parties}

Voeg bestuurders, eigenaren en andere zakelijke deelnemers toe wanneer ze bekend of gevraagd zijn. Dit voorbeeld maakt een bestuurder aan met [`POST /v3/customers/{customerId}/related-parties`](/api-reference/customers/post-v3-customers-by-customer-id-related-parties):

```bash Add related party
curl --request POST \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}/related-parties" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}" \
  --header "Idempotency-Key: related-party-director-001" \
  --header "Content-Type: application/json" \
  --data @- <<'JSON'
{
  "partyType": "person",
  "roles": ["director"],
  "title": "Chief executive officer",
  "person": {
    "firstName": "Amina",
    "lastName": "Diallo",
    "residenceCountry": "FR"
  }
}
JSON
```

Bewaar de geretourneerde `data.id` als `RELATED_PARTY_ID`.

Als je een klant moet exporteren, gebruik je [`POST /v3/customers/{customerId}/export`](/api-reference/customers/post-v3-customers-by-customer-id-export) en volg je het requestschema. Het `json_basic_data`-formaat retourneert de huidige publieke v3-klantresource als JSON-bijlage; elke aanroep berekent de huidige data opnieuw en sluit documenten en documentmetadata uit.

Stuur voor een portability-token-formaat de client-ID van het ontvangende KYC-project als `forClientId`, niet de Swipelux `customerId`. Gebruik het geretourneerde `data.token` vóór `data.expiresAt`. Hergebruik van dezelfde `Idempotency-Key` en body replayt dat tokenresultaat; gebruik een nieuwe key om een ander token uit te geven.

## Controleer genegeerde velden bij updates {#check-ignored-fields-on-updates}

[`PATCH /v3/customers/{customerId}`](/api-reference/customers/patch-v3-customers-by-customer-id) en `PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}` negeren bodyvelden die ze niet herkennen. Wanneer ze een veld negeren, bevat een geslaagd antwoord de header `Swipelux-Ignored-Fields`. De header toont de JSON Pointers van de genegeerde velden, kommagescheiden en gesorteerd. Aanmaakacties retourneren deze header niet.

Controleer deze header na elke update. Anders wordt een verkeerd benoemd of verkeerd geplaatst veld zonder fout weggegooid. Als je bijvoorbeeld `individual.dateOfBirth` stuurt in plaats van `individual.birthDate`, blijft de geboortedatum leeg.

```http Ignored fields response header
Swipelux-Ignored-Fields: /individual/dateOfBirth,/nickname
```

- De header toont maximaal 20 pointers en 4096 tekens, en eindigt op `...` wanneer Swipelux de lijst inkort. Pointersegmenten zijn procentgecodeerd.
- Velden binnen `metadata` zijn vrij van vorm en worden nooit gemeld.
- Idempotente herhalingen laten de header weg, dus lees hem uit het eerste antwoord.
- Onbekende velden kunnen in een toekomstige versie met `400` worden geweigerd.

## Lees readiness uit capabilities

Een klant heeft geen verificatie- of readiness-status in de API. Lees de klant met [`GET /v3/customers/{customerId}`](/api-reference/customers/get-v3-customers-by-customer-id) voor huidige profieldata en gebruik vervolgens capabilities en hun `openTaskIds` om te bepalen wat de klant vervolgens kan doen.

```bash Get customer
curl --request GET \
  "${API_BASE}/v3/customers/${CUSTOMER_ID}" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

### Klanten filteren op capability-readiness {#filter-customers-by-capability-readiness}

Om klanten in een bepaalde onboardingfase te vinden, filter je [`GET /v3/customers`](/api-reference/customers/get-v3-customers) met deze queryparameters:

- `pooledCapabilityStatus`: de klant heeft een pooled capability met deze status.
- `namedCapabilityStatus`: de klant heeft een named capability met deze status.
- `hasReadyNamedAccount`: `true` retourneert klanten met een `ready` named-rekening. `false` retourneert klanten zonder.

De statusfilters accepteren `pending`, `ready`, `restricted`, `rejected` of `canceled`. Swipelux leest statussen op dezelfde manier als `include=capabilities`. Zie [Pooled vs named accounttypes](/nl/integration/onboarding/capabilities-and-requirements#pooled-vs-named-account-types).

Om capabilities uit te sluiten die alleen wachten, voeg je `namedCapabilityExcludeWait=true` of `pooledCapabilityExcludeWait=true` toe; dit laat resultaten weg waarvan `statusReason.resolution` gelijk is aan `wait`. `namedCapabilityIncludeWait=true` of `pooledCapabilityIncludeWait=true` matcht ook `restricted` capabilities met die resolutie. Elke vlag werkt alleen met het bijbehorende statusfilter, en `ExcludeWait` wint wanneer beide zijn ingesteld.

De filters zijn onderling en met de andere lijstfilters te combineren. Swipelux past ze toe vóór het pagineren, zodat elke pagina alleen overeenkomende klanten bevat. API-sleutels hebben `accounts:read` of `rails:read` nodig om ze te gebruiken. Een ongeldige waarde retourneert `400 validation_error`.

Bijvoorbeeld om klanten te vinden die een bank heeft goedgekeurd voor een named capability en die nog geen ready named-rekening hebben:

```bash Filter customers awaiting a named account
curl --request GET \
  --get "${API_BASE}/v3/customers" \
  --data-urlencode "namedCapabilityStatus=ready" \
  --data-urlencode "hasReadyNamedAccount=false" \
  --header "X-API-Key: ${SWIPELUX_API_KEY}"
```

### Klanten met openstaande documenten vinden

Om te zien welke klanten op een pagina nog verplichte documenten moeten aanleveren, geef je `include=documentRequirements` mee aan [`GET /v3/customers`](/api-reference/customers/get-v3-customers). Je kunt dit combineren met capability-samenvattingen als `include=capabilities,documentRequirements`. API-sleutels hebben `accounts:read` nodig voor de `documentRequirements`-expansie.

Elke klantsamenvatting bevat dan een `documentRequirements`-object:

```json Document requirement summary
{
  "documentRequirements": {
    "required": true,
    "count": 2
  }
}
```

- `count` is het aantal verplichte documentvereisten in `action_required` op taken die ook in `action_required` staan. Het omvat elke taakscope, inclusief accountbrede taken, en is niet afhankelijk van capability-readiness.
- `required` is `true` wanneer `count` groter is dan `0`.
- Een set alternatieven telt één keer, en alleen wanneer elk alternatief een document vereist.

De samenvatting is conservatief. Ze sluit optionele documenten, voorwaardelijk verplichte documenten en alternatieven die document- en niet-documentroutes combineren uit. Ze sluit ook vereisten uit die de klant via hosted verificatie kan voltooien. Daardoor bewijst `required: false` niet dat er geen documenttaak van toepassing is. Gebruik de samenvatting om klanten te prioriteren en lees daarna hun taken voor de gezaghebbende lijst van wat je moet verzamelen. Zonder de expansie laat de response `documentRequirements` weg.

## Lees het overboekingsvolume van een klant {#read-customer-transfer-volume}

Om te tonen hoeveel geld een klant heeft verplaatst, roep je `GET /v3/customers/{customerId}/transfer-totals` aan. API-sleutels hebben `customers:read` nodig. Een onbekende klant retourneert `404 customer_not_found`.

```json Transfer totals
{
  "data": {
    "customerId": "cus_...",
    "received": { "amount": "1000.00", "currency": "USD" },
    "sent": { "amount": "25.00", "currency": "USD" }
  }
}
```

- Alleen voltooide transfers tellen mee. Openstaande en mislukte transfers worden uitgesloten.
- `received` telt pay-ins en inkomende wallettransfers van andere klanten op. `sent` telt payouts en uitgaande wallettransfers op.
- USD, USDC en USDT tellen 1:1 als USD. Bedragen in andere valuta worden uitgesloten.
- Transfers tussen de eigen wallets van de klant worden uitgesloten.
- Elke `amount` is een decimale string met twee decimalen, en `"0.00"` wanneer geen enkele transfer in aanmerking komt.

De totalen zijn bewegingsvolume, geen actueel saldo.

Ga vervolgens naar [Capabilities en tasks](/nl/integration/onboarding/capabilities-and-requirements) om de gewenste productuitkomst te ontdekken en te activeren.
