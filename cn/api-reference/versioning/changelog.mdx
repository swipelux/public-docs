本页列出 Swipelux API 按日期排列的变更。每条记录会注明所影响的版本、变更类型，以及集成方需要采取的任何操作。

如需将现有集成从较早版本升级，请参阅 [迁移到 v3](/cn/api-reference/versioning/migrate-to-v3)。

<Update label="2026-10-08" description="v3" tags={["新增","变更","修复"]}>

### 新增
- 收款方目的地接受 `pix` 和 `pix_safe` 类型，用于在巴西进行 BRL 出金。Pix 目的地向 Pix 密钥付款。Pix Safe 目的地向通过持有人的 CPF 或 CNPJ、银行的 ISPB 代码、支行和账号识别的银行账户付款。两者都需要客户已就绪的 Pix 能力（`pix_pooled`），其出金由 USDC 提供资金，且不收取开发者费用。请参阅[收款方](/cn/integration/recipients)和[发送资金](/cn/integration/send-funds#pix-payouts)。
- `GET /v3/customers/{customerId}/tasks/{taskId}` 接受带有文档要求 ID 的 `documentCandidatesFor`，对于有替代选项的要求，还接受 `documentAlternativeKey`。此时响应会在 `data.documentCandidates` 中列出客户已上传且可满足该要求的文件，并附带任何 `missingMetadata` 或 `conflictingMetadata`。请提交候选文件的 `documentId` 并附上缺失的 `documentMetadata`，而无需重新上传文件。该查询需要 `accounts:read` 和 `customers:read`，无效的选择会返回 `400 validation_error`。

### 变更
- `GET /v3/webhooks/portal` 返回一个在一小时后过期的门户 URL，并带有 `Cache-Control: no-store`。使用具有 `webhooks:write` 的 API 密钥时，门户会显示端点签名密钥，并可管理端点、重试投递以及重放投递。仅具有 `webhooks:read` 时，门户只显示投递记录。请参阅[Webhook](/cn/integration/webhooks)。
- Citi（`citibank`）仅向企业客户提供。所有企业都保留共享 Citi，具名 Citi 仅向在美国境外注册的企业提供。当某客户不提供 Citi 时，支持列表会省略它，指定它会返回 `422 capability_institutions_unsupported`，仅由 Citi 提供的方式会被列为 `disabled`。未指定 `institutions` 的请求会在其余银行中进行选择。现有申请和账户保持不变。
- 具名 CFSB（`cfsb`）能力仅向美国客户提供：在美国注册的企业以及居住在美国的个人。对于其他客户，支持列表会省略具名 CFSB，指定它会返回 `422 capability_institutions_unsupported`。未指定 `institutions` 的请求会在其余银行中进行选择。共享 CFSB、国家未知的客户以及现有申请保持不变。
- Lead Bank（`lead_bank`）的具名 ACH、Wire 和 SWIFT 能力仅向 Lead Bank 能够根据其法律形式和所在国家完成入驻的客户提供。对于其他客户，支持列表会省略 `lead_bank`，指定它会返回 `422 capability_institutions_unsupported`。Lead Bank 已完成入驻的客户，以及未完成请求中已指定 `lead_bank` 的能力，会保留它。现有申请和账户保持不变。
- 针对个人和最终受益人的新身份证件请求可以设置 `constraints.identityMetadataRequired: true`，此时每个文件都需要在 `documentMetadata` 中提供其证件号码和签发国家。针对企业地址证明和所有者居住证明的新请求可以设置 `constraints.maxIssueAgeDays: 90`，此时每个文件都需要提供其签发日期。现有任务保留其原有要求，因此请读取每个任务请求上的约束条件。
- 收款方目的地的 `type` 现在是开放枚举。本参考的早期版本将其描述为封闭枚举，因此请更新任何会拒绝或丢弃未知类型的客户端。目的地响应和 `destination.status_changed` 事件现在可能包含 `pix` 和 `pix_safe`，并且以后可能新增更多类型。
- 对于仅要求提供文档的符合条件的会话，其验证链接现在会打开由 Swipelux 托管的文档上传页面。链接本身保持不变，其他会话仍会打开托管验证流程。
- 个人客户和关联方人员的 `employment.occupation` 最多接受 255 个字符。
- 当资料值或任务答案包含 Swipelux 表单链接（例如 RFI、客户请求或转账追踪链接）时，`POST /v3/customers`, `PATCH /v3/customers/{customerId}`, `POST /v3/customers/{customerId}/related-parties`, `PATCH /v3/customers/{customerId}/related-parties/{relatedPartyId}` 和 `POST /v3/customers/{customerId}/tasks/{taskId}/submissions` 返回 `400 validation_error`。这不适用于 `externalId` 或 `metadata`。每个被拒绝的值都会出现在 `errors[]` 中，带有 `code: public_form_link` 及其 JSON Pointer，且响应绝不会重复该链接。请改为直接发送信息本身。请参阅[错误与重试](/integration/errors#validation-error)。

### 修复
- 出金报价和转账响应会将 USDC 或 USDT 源金额保留到小数点后六位，例如 `4009.711365` 而不是 `4009.71`。法币金额保留两位小数。创建或读取稳定币源金额超过两位小数的出金时，不再返回 `500`。
- [`POST /v3/customers/{customerId}/capabilities/{capabilityId}/cancel`](/api-reference/capabilities/post-v3-customers-by-customer-id-capabilities-by-capability-id-cancel) 参考现在按实际行为描述取消操作。您可以取消处于 `ready` 的能力，`stablecoin_transfers` 能力无法取消，取消只会终止该能力本身，其申请会保留各自的状态、任务和审批。

</Update>

<Update label="2026-10-05" description="v3" tags={["新增","变更","修复"]}>

### 新增
- `GET /v3/customers` 接受 `include=documentRequirements`。此时每条客户摘要都会报告仍有多少必需文档尚未提交，与能力就绪状态无关。可组合使用为 `include=capabilities,documentRequirements`。请参阅[客户](/cn/integration/onboarding/customers)。
- 商户面板的 Webhooks 页面在端点菜单中新增 **Replay missed events**。它会重新发送端点在过去 13 天内从未收到的事件，且不会重复发送同一事件。请参阅[Webhook](/cn/integration/webhooks#recover-deliveries)。
- 商户面板的 **Settings** 页面新增 **Compliance** 部分。所有者和管理员可以设置合规电子邮箱，并选择在 Swipelux 要求提供某位客户的更多信息时是否接收电子邮件。
- 商户可以直接在商户面板的 KYB 页面上回复针对自身的 KYB 合规请求。

### 变更
- 银行受理完成后，客户和关联方更新不再返回 `409 field_conflicts_with_completed_intake`。更新会被保存，每个新的银行申请都会按照自身要求检查最新的客户档案。
- 当能力现有的银行路由无法安全更新时，能力请求会返回 `409 capability_route_header_conflict`。重试前请联系 Swipelux 支持团队。
- 当 `institutions` 指定了该能力不提供的银行时，`GET /v3/customers/{customerId}/capabilities/{capabilityId}/tasks-preview` 会返回 `422 capability_institutions_unsupported`，与能力请求的行为一致。
- 在沙盒中，ACH、Wire 和 SWIFT 能力仅由 JPMorgan Chase 提供。省略 `institutions` 的请求会选择 `jpmorgan`，指定其他银行会返回 `422 capability_institutions_unsupported`。生产环境路由保持不变。请参阅[在沙盒中测试](/cn/integration/sandbox)。
- 当模拟案例无法达到所请求的状态时，强制设置沙盒能力状态会返回 `409 capability_status_blocked` 并附带 `statusReason`。重复执行已生效的强制设置会返回 `200`，且状态不变。请参阅[在沙盒中测试](/cn/integration/sandbox#test-capability-readiness)。
- 对于由运营团队或其他工作流拥有的任务,`POST /v3/sandbox/tasks/{taskId}/review` 会返回 `409 task_not_sandbox_reviewable`。来自 `POST /v3/sandbox/tasks` 的任务以及 Swipelux 收集的能力受理任务仍可审核。参见[在沙盒中测试](/cn/integration/sandbox)。
- 当账户仍在银行预配期间更改结算设置时，`PATCH /v3/customers/{customerId}/accounts/{accountId}` 会返回 `409 account_provisioning_unresolved`。请在预配完成后重试。请参阅[错误与重试](/integration/errors#account-provisioning-unresolved)。
- `POST /v3/transfers` 可能返回 `409 quote_execution_evidence_conflict`。请创建新的报价并执行。请参阅[错误与重试](/integration/errors)。
- 商户面板的 **Pay out** 抽屉会显示完整的目的地详情，通过切换开关隐藏账号和钱包地址，并显示每种付款方式的预计到账时间。
- 商户面板将银行账户并入客户的 **Payment access** 标签页，并提供列出每家银行的任务卡片。**Documents** 标签页已移至 **Profile**。
- 在商户面板中开设具名银行账户现在只需一个步骤，并会列出每家银行的币种、方式和入驻时间。请参阅[账户](/cn/integration/accounts)。
- 因审核而被暂停的银行账户在商户面板中显示为 **On hold**，并显示账户 ID 和 **Contact support** 操作。
- 当 Swipelux 正在准备提交申请且尚未开始审核时，处于 `pending` 的能力现在会报告 `statusReason.code: preparing_submission`，而不是 `review_in_progress`。两个代码都使用 `resolution: wait`。在两者之间切换时状态仍为 `pending`，因此不会发送 `capability.status_changed` 事件。现有能力会在下一次重新评估时采用新代码。请参阅[能力与要求](/cn/integration/onboarding/capabilities-and-requirements#continue-when-the-capability-is-ready)。
- 商户面板中客户 **Payment access** 标签页上的 **Shared methods** 表格，对于能力报告 `preparing_submission` 的共享方式，会显示 **In preparation** 而不是 **In review**。
- 能力的 `applications` 列表现在仅显示其当前申请，适用于能力读取（包括 `GET /v3/customers/{customerId}/capabilities/{capabilityId}/applications`）、能力申请响应以及 `capability.status_changed` 事件。被较新申请替换的申请仍会出现在 `GET /v3/customers/{customerId}/applications` 中，其中 `supersededByApplicationId` 指明其后继申请。被替换申请的未完成任务仍计入能力的 `openTaskIds`。能力的状态和 `openTaskIds` 不会改变，因此此变更本身不会发送任何 webhook 事件。请参阅[能力与要求](/cn/integration/onboarding/capabilities-and-requirements#list-the-customers-applications)。

### 修复
- 在银行批准之前，针对同一已签发账户发送的第二个 `allowPending` 请求会返回 `409`，并在 `holder.accountId` 中指明正在等待的账户，而不是返回 `500`。请参阅[发行银行账户](/cn/integration/issue-bank-account)。
- 取消能力现在会关闭仍在等待银行批准的已签发账户请求，因此之后在同一银行发起的请求会重新开始。
- 重新请求所有银行案例均被拒绝的已取消能力时，只会发布一个从 `canceled` 开始的 `capability.status_changed` 事件。
- 在银行先前的申请被归档后重新请求该银行，现在会提交新的申请。
- 一旦对应能力显示为 `ready`，即可添加收款方目的地，而不再返回 `409 rail_not_ready`。请参阅[收款方](/cn/integration/recipients)。
- 在您首次打开商户面板的 Webhooks 页面之前发送的 Webhook 事件现在会被保留，因此您可以将其重放到新的端点。
- 商户面板中的任务截止日期会以您所在的时区显示；当没有未完成项时，银行审核抽屉会显示 **All requirements submitted**。

</Update>

<Update label="2026-09-28" description="v3" tags={["新增","变更","修复"]}>

### 新增
- `POST /v3/quotes` 现在接受可选的 `institutionId`，用于为加密货币到法币的出金报价选择已获批准的银行通道。省略该字段则保持自动路由。选择对该出金不可用的银行会返回 `422 bank_not_supported_for_customer`，在其他任何报价类型中发送 `institutionId` 会返回 `400 validation_error`。请参阅[发送资金](/cn/integration/send-funds)。
- `POST /v3/customers/{customerId}/accounts` 上签发银行账户的请求接受 `institution`，用于将账户固定到某一家银行且不进行回退；并接受 `allowPending: true`，用于在该银行的申请仍待批准时保存请求。`allowPending` 需要同时提供 `institution`。已保存的请求会报告其所属的 `applicationId`。请参阅[发行银行账户](/cn/integration/issue-bank-account)。
- 商户面板新增原生 **Webhooks** 页面，用于管理端点。请参阅[Webhook](/cn/integration/webhooks)。
- 商户面板新增 **Pay in** 抽屉，包含已命名的银行账户、加密货币入金和审核步骤。
- 商户面板的 **Pay out** 流程会在来源选择器中显示钱包余额，新增 **Max** 金额选项，并包含审核步骤。
- 商户面板中的客户档案新增 **Recipients & destinations** 标签页。
- 任务要求可以包含简短的 `title` 标题。请求的 `prompt` 仍承载指导说明。请参阅[能力与要求](/cn/integration/onboarding/capabilities-and-requirements)。

### 变更
- 共享 Wire 通道上的电汇入金报价现在要求至少 20 美元。低于所在通道最低金额，或金额过小、不足以支付转账费用的报价会返回 `422 amount_not_deliverable`，而不是通用的报价失败。请参阅[接收资金](/cn/integration/receive-funds)。
- Webhook 门户现在按资源对 v3 事件类型进行分组，并显示每个事件的负载架构和示例。旧版事件类型显示在单独的 **Legacy** 分组中，并标记为已弃用。已订阅这些事件类型的端点会继续收到它们；新订阅请使用 v3 事件类型。请参阅[Webhook](/cn/integration/webhooks)。
- 沙盒充值现在会发出 `transfer.created` 和 `transfer.state_changed` Webhook 事件。请参阅[在沙盒中测试](/cn/integration/sandbox)。
- 当客户已拥有处于活跃状态的已签发账户时，`accountProvisioning` 现在会报告 `issued`。请参阅[能力与要求](/cn/integration/onboarding/capabilities-and-requirements)。
- 商户面板中的银行账户详情会在抽屉中打开，并显示银行徽标。请参阅[账户](/cn/integration/accounts)。
- 商户面板将资金流动标记为 **Pay in** 和 **Pay out**，保持登录状态六小时，并通过电子邮件将帮助请求发送给 Swipelux 支持团队。
- 在接受直接提交的受理任务中，已由客户档案或已上传文档支持的符合条件的要求会自动进入 `in_review`。请参阅[能力与要求](/cn/integration/onboarding/capabilities-and-requirements#reused-profile-evidence)。

### 修复
- 重新请求已取消的能力不再因已被取代的申请记录或过时的要求而失败。
- 以已停用的 Fedwire ID 存储的能力现在读取为 `wire`，而不是返回 `500`。

</Update>

<Update label="2026-09-21" description="v3" tags={["新增","变更","移除","修复"]}>

### 新增
- `GET /v3/customers/{customerId}/applications` 列出客户的申请案例，包括针对每个案例请求的能力以及其批准所覆盖的能力。在一家银行获得的一次批准可以覆盖多项能力。保留的历史案例会通过 `supersededByApplicationId` 指向其后继案例。该列表支持游标分页和 `updatedAfter`。请参阅[能力与要求](/cn/integration/onboarding/capabilities-and-requirements)。
- 对于基于申请案例的能力，`POST /v3/customers/{customerId}/capabilities/{capabilityId}` 的响应包含 `selectedApplicationId`。它标识该请求复用的现有申请案例，或其新开启的案例。请参阅[能力与要求](/cn/integration/onboarding/capabilities-and-requirements)。
- 由 `GET /v3/institutions` 和支持的能力列表返回的机构包含可为空的 `logoUrl`。可用时使用它显示银行品牌标识，为 `null` 时回退为显示机构名称。请参阅[能力与要求](/cn/integration/onboarding/capabilities-and-requirements)。
- 美元 SWIFT 出金现已可用。SWIFT 出金最低需要 100 美元。商户面板会收集收款方的 SWIFT 银行指令。请参阅[发送资金](/cn/integration/send-funds)。
- 已签发银行账户可以使用具名收款详情通过 SWIFT 收款。请参阅[发行银行账户](/cn/integration/issue-bank-account)。
- USDT 现在支持作为 ACH 和 Wire 出金的来源。请参阅[发送资金](/cn/integration/send-funds)。
- 已签发银行账户接受值为 `USDC` 或 `USDT` 的 `settlement.currency`，用于选择交付到结算钱包的稳定币，与钱包账户币种无关。省略该字段则继续以钱包的币种结算。请参阅[发行银行账户](/cn/integration/issue-bank-account)。
- SWIFT 银行账户和收款方目的地接受 `bankCity`、`bankState`、`bankPostalCode` 和 `bankAddressLine2`，以及可选的 `beneficiaryTaxId`、`beneficiaryPhoneNumber`、`ifscBranchCode`、`paymentCode` 和中转银行详情。请参阅[发送资金](/cn/integration/send-funds)。
- 当银行提供分开的 ACH 和 Wire 路由号码时，已签发银行账户详情会包含 `achRoutingNumber` 和 `wireRoutingNumber`，并包含收款银行的 `bankLogoUrl`。请参阅[发行银行账户](/cn/integration/issue-bank-account)。
- `capability.created` Webhook 事件包含 `applicationId` 以及值为 `requested` 或 `approval` 的 `origin`，便于您区分自己请求的能力和由批准覆盖的能力。请参阅[Webhook](/cn/integration/webhooks)。
- 要求请求可以声明用于校验的 `constraints.format`，例如 `http_url`、`us_ssn`、`us_ein` 或 `bank_industry_classification`。请参阅[能力与要求](/cn/integration/onboarding/capabilities-and-requirements)。

### 变更
- 商户面板中的银行账户创建现在从选择银行开始，银行账户会显示分开的 ACH 和 Wire 路由号码。请参阅[账户](/cn/integration/accounts)。
- `network` 枚举现在包含 `solana`。这是一个开放枚举，因此请容忍您无法识别的网络值。请参阅[账户](/cn/integration/accounts)。
- 如果任务的剩余要求需要直接提交，为该任务打开托管验证链接会返回 `409 verification_session_not_allowed`。请改为以任务提交的方式提交这些要求。请参阅[错误与重试](/integration/errors#verification-session-not-allowed)。
- 归档预配尚未完成的已签发账户会返回 `409 account_provisioning_unresolved`。请在预配完成后重试。请参阅[错误与重试](/integration/errors#account-provisioning-unresolved)。
- 新的具名银行账户请求会在账户创建后立即排队等待预配，而不是等到下一次客户刷新。请参阅[发行银行账户](/cn/integration/issue-bank-account)。

### 移除
- 新账户不再提供共享的 SWIFT 收款详情。请改用具名 SWIFT 收款详情。请参阅[发行银行账户](/cn/integration/issue-bank-account)。

### 修复
- 出金转账读取现在会返回报价中的收款方。
- 归档现有 ACH 账户后再创建 ACH 账户不再返回 `409`，已归档的待处理账户请求也不再占用账户名额。
- 本币入金报价上的银行费用现在以正确的法币币种报告。

</Update>

<Update label="2026-09-14" description="v3" tags={["新增","变更","修复"]}>

### 新增
- `GET /v3/webhooks/{webhookId}` 可读取单个 Webhook 端点及其 `events` 选择。请参阅[Webhook](/cn/integration/webhooks)。
