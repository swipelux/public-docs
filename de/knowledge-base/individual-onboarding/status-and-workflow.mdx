## Verifizierungsstatus und Workflow

Die richtlinienorientierte KYC-Reise verläuft von der Informationssammlung über die Prüfung bis zu einer Freigabe- oder Ablehnungsentscheidung. Aktuelle API-Ressourcen legen separate Fähigkeits-, Anwendungs-, Aufgaben- und Einreichungs-Lebenszyklen offen.

<Warning>
  Richtlinienbezogene Prüflabels und Zeitschätzungen definieren kein API-Verhalten. Implementieren Sie
  keine Zustandsmaschine anhand der untenstehenden Labels.
</Warning>

## Richtlinienorientierte Prüfungskonzepte

Diese richtlinienorientierten Prüfungskonzepte beschreiben die Onboarding-Reise. Sie sind keine aktuellen API-Enums, Webhook-Werte oder garantierte Übergänge.

| Richtlinien-Label | Bedeutung |
| --- | --- |
| `not_started` | Der Kunde existiert, aber KYC-Arbeit hat nicht begonnen |
| `incomplete` | KYC-Arbeit hat begonnen, aber erforderliche Informationen fehlen |
| `pending_verification` | Die Prüfung wartet auf die Fertigstellung durch den Kunden |
| `under_review` | Eingereichte Informationen oder Dokumente werden geprüft |
| `approved` | Die Richtlinienprüfung hat den Kunden für die zutreffenden Abläufe freigegeben |
| `rejected` | Die Richtlinienprüfung hat den Kunden abgelehnt |

Verwenden Sie diese Labels nur bei der Erörterung der Richtlinienreise. Senden Sie sie nicht als aktuelle Statuswerte, es sei denn, ein aktuelles generiertes Schema fordert denselben Wert in seinem eigenen Kontext explizit an.

## Standard-KYC-Prüfungsablauf

1. Legen Sie den Einzelkunden an.
2. Entdecken und fordern Sie eine berechtigte Fähigkeit an.
3. Lesen Sie das aktuelle Aufgabendetail.
4. Senden Sie den Kunden zu einer gehosteten Erstpartei-Verifizierungssession oder reichen Sie die vollständigen von der Aufgabe angeforderten Antworten ein.
5. Lassen Sie die Prüfung laufen, während aktuelle Ressourcen ihre eigenen Prüfzustände melden.
6. Rufen Sie die aktuellen Ressourcen erneut ab, um festzustellen, ob weitere Aktionen erforderlich sind oder die Fähigkeit bereit, eingeschränkt, abgelehnt oder abgebrochen ist.

Die Richtlinienreise kann dies als not_started, pending_verification, under_review und dann approved oder rejected beschreiben. Diese Begriffe definieren nicht die API-Übergangssequenz.

## Enhanced-KYC-Prüfungsablauf

1. Erledigen Sie die aktuell angeforderte Standard-Identitäts- und Liveness-Arbeit.
2. Lesen Sie die neueste Aufgabe, wenn die erweiterte Prüfung zusätzliche Informationen anfordert.
3. Stellen Sie angeforderte Adress-, Geldherkunfts- oder andere Nachweise über die aktuelle gehostete Session oder Aufgabeneinreichung bereit.
4. Laden Sie Dokumente nur hoch, wenn die aktuelle Aufgabe dies verlangt.
5. Überwachen Sie die aktuellen Ressourcen während der manuellen Prüfung weiter.
6. Stoppen oder fahren Sie fort basierend auf den aktuellen Fähigkeits-, Anwendungs-, Aufgaben- und Einreichungszuständen.

Das Compliance-Team kann eine erweiterte Prüfung auch über die registrierte E-Mail-Adresse des Kunden koordinieren.

## Häufige Ablehnungsgründe

| Grund | Lösung |
| --- | --- |
| Dokument nicht lesbar | Stellen Sie ein klares, hochauflösendes Bild bereit |
| Dokument abgelaufen | Stellen Sie ein gültiges, nicht abgelaufenes Identitätsdokument bereit |
| Gesicht stimmt nicht überein | Stellen Sie sicher, dass das Selfie klar mit dem Foto des Identitätsdokuments übereinstimmt |
| Unvollständige Informationen | Stellen Sie jeden von der aktuellen Aufgabe angeforderten Punkt bereit |
| Verdächtige Aktivität | Kontaktieren Sie den Support für eine manuelle Prüfung |

## Verifizierungszeitplan

| Phase | Typische Dauer |
| --- | --- |
| Dokumenten-Upload | Sofort |
| Automatisierte Prüfungen | 1-3 Minuten |
| Standardprüfung | 1-24 Stunden |
| Erweiterte Prüfung | 1-3 Arbeitstage |

Diese Dauern sind typische Richtlinienschätzungen, kein garantiertes API-Verhalten.

## Aktuelle API-Zustandsvokabulare

Die aktuellen Ressourcen verwenden separate geschlossene Vokabulare:

- **Fähigkeitsstatus:** `pending`, `ready`, `restricted`, `rejected`, `canceled`
- **Anwendungsstatus:** `requested`, `in_review`, `action_required`, `ready`, `rejected`, `disabled`, `canceled`
- **Aufgabenstatus:** `action_required`, `in_review`, `satisfied`, `rejected`, `canceled`
- **Einreichungsergebnis:** `in_review`, `accepted`, `changes_requested`, `rejected`

Fassen Sie diese Vokabulare nicht zu einem Verifizierungsstatus zusammen.

## Ereignisse und aktueller Zustand

Verwenden Sie aktuell dokumentierte [Webhooks](/de/integration/webhooks) als Änderungsbenachrichtigungen und rufen Sie dann die aktuellen Kunden-, Fähigkeits-, Anwendungs- und Aufgabenressourcen erneut ab. Ereignisse ersetzen keine maßgeblichen Ressourcenabrufe, und kein richtlinienorientiertes Label impliziert ein bestimmtes Ereignis.

Siehe [Fähigkeiten und Aufgaben](/de/integration/onboarding/capabilities-and-requirements#complete-current-tasks) für die aktuelle Aktionsschleife.
